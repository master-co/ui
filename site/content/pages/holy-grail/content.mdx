It was hard for fifteen years. It is the [app shell](/pages/app-shell) with every optional region in use.

## How it is built \{#how-it-is-built\}

- **`shell-header` and `shell-footer` span the frame**; `shell-sidebar`, `shell-main` and `shell-aside` share the row between them.
- **The source order is yours.** Each region is placed by its class, not by its position in the markup. Here `<main>` comes right after the header, before both side columns, so it is first for a screen reader, for a search engine and for the tab order.
- **The side columns are fixed and the middle is fluid.** Set the widths with `--shell-sidebar` and `--shell-aside`; the main region takes the rest and never grows past it.
- **The row of columns is at least as tall as the viewport**, so the side columns can stay in view for the whole read, and the footer starts below the fold.
- **The hairlines are utilities.** `bxe(1) bxe-solid b-line-hair` draws a line at the end of the start column, and `bxs(…)` at the start of the end column; both follow the writing direction.

## When to use \{#when-to-use\}

Use three columns when the two side columns do different jobs for the same content: where else to go, and what else relates. When one of them is only the contents of the page, the [documentation](/pages/docs) layout says the same thing with less. When there is no second side column, it is an [app shell](/pages/app-shell).

## Accessibility \{#accessibility\}

- The start column is an `<aside>` around a labelled `<nav>` ("Sections") and needs no label of its own; the end column has no navigation in it, so the `<aside>` carries the label ("Related").
- With the main region first in the source, the tab order goes header, main, then the side columns. That is the point: check that it matches what your readers expect, and move `<main>` after the navigation if it does not.
