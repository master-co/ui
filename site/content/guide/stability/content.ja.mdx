プロジェクトは、クラス名、カスタムプロパティ、インポート、コマンドを通じて Master UI に依存します。ライブラリの上に構築するときは以下の公開インターフェースを使い、アップグレードするときはそれらを確認してください。

Master UI は実験段階にあり、0.x のリリースでは公開インターフェースであっても変更される可能性があります。公開とは、現在のバージョンでサポートされる使い方を示すものであり、次のバージョンとの互換性を約束するものではありません。プロジェクトに影響する変更を確認するために、[意図的にアップグレード](#experimental)してください。

## 公開 \{#public\}

| 対象 | 記載されている場所 | 例 |
| --- | --- | --- |
| クラス名 | コントラクトの `classes` | `btn`、`btn-primary`、`dialog-header` |
| クラスが必要とする要素と属性 | そのクラスの `elements`、`attributes`、`label` | `switch` は `type="checkbox"` と `role="switch"` を持つ `<input>` に付け、アクセシブルな名前が必要です |
| 状態のマーク | コントラクトの `states` | `btn` の `aria-pressed="true"`、`switch` の `:checked` |
| コンポーネントのカスタムプロパティ | コントラクトの `properties` | `--btn-height`、`--splitter-size` |
| テーマトークン | `theme.css` の `@theme`。`@master/ui/theme.json` に各トークンとその値が並びます | `--color-surface-raised`、`--radius-control`、`--lift` |
| ミックスイン名 | `theme.css` の `@mixin` | `--surface-sheet`、`--focus-ring`、`--anchored` |
| コントラクトのスキーマ | `@master/ui/contract.schema.json` | コントラクトのフィールドと、それぞれの意味 |
| ビヘイビア | `@master/ui/behaviors` のエクスポート | `combobox(root)`、`attach()`、`calendarMonth()`、それぞれが返す関数とその `value` |
| フレームワークコンポーネントの名前 | `master-ui add` が読み取る `frameworks/manifest.json` | `combobox`、`dialog`、`toast` |
| チェッカー | `@master/ui/check` のエクスポート | `check`、`createIndex`、`parse`、`format`、`owners` |
| コマンド | `master-ui` | `list`、`contract`、`check`、`init`、`own`、`add`、`status`、`diff`、`accept` |
| インポートパス | パッケージの `package.json` の `exports` | 下の表 |

コントラクトには、インストール済みのバージョンにおける 1 つのコンポーネントのインターフェースが並びます。クラスやプロパティに依存する前に、それを出力して確認してください。

```bash
npx master-ui contract button
```

コントラクトの `properties` リストが、コンポーネント固有の拡張ポイントを定めます。リストにない内部プロパティは変更される可能性があります。共有のテーマトークンは、`theme.css` で定義される別の公開インターフェースです。

### インポートパス \{#import-paths\}

| パス | 内容 |
| --- | --- |
| `@master/ui`、`@master/ui/master.css` | テーマ、すべてのコンポーネント、レイアウトクラス（Master CSS のソースとして） |
| `@master/ui/theme.css` | 既定のテーマのトークンとミックスイン |
| `@master/ui/components/<name>.css`、`@master/ui/layouts/<name>.css` | 1 つのスタイルシート |
| `@master/ui/components/<name>.json`、`@master/ui/layouts/<name>.json` | そのコントラクト |
| `@master/ui/themes/<name>.css` | `paper` のような別のテーマ |
| `@master/ui/contract.schema.json` | コントラクトの JSON Schema |
| `@master/ui/contracts.json` | すべてのコントラクトを 1 つにまとめたファイル |
| `@master/ui/theme.json` | テーマのすべてのトークンとその値 |
| `@master/ui/standalone.css` | テーマとすべてのコンポーネントをプレーンな CSS にコンパイルしたもの |
| `@master/ui/base.css` | コンポーネントが前提とする小さなリセット |
| `@master/ui/behaviors`、`@master/ui/behaviors/<name>.js` | `attach()` を含むすべてのビヘイビア、または 1 つのビヘイビア（TypeScript 用の型付き） |
| `@master/ui/check` | モジュールとしてのコントラクトチェッカー |

コンパイル済みのファイルは、CDN が配信するパスである `@master/ui/dist/` 配下からも参照できます。`dist/standalone.css`、`dist/base.css`、`dist/themes/<name>.css`、`dist/contracts.json`、`dist/theme.json` です。

## 非公開 \{#private\}

| 対象 | 例 | 代わりに使うもの |
| --- | --- | --- |
| コントラクトに記載されていない、コンポーネントの内部プロパティ | ボタンが自身のルール間で移動量を受け渡すために使う `--btn-lift` | 記載されたプロパティ、またはテーマトークン `--lift` |
| セレクターの構造 | ルールのネストの仕方、どの疑似要素がマークを描画するか、`components` レイヤー内でのルールの詳細度 | クラスと状態のマーク。要素に付けたユーティリティは、どのコンポーネントのルールよりも優先されます |
| 既定のテーマの値 | `--shadow-raised` の背後にある影のリスト、`--surface-sheet` のグラデーションの停止点 | 独自のテーマで再定義した、トークン名またはミックスイン名 |
| スタイルシート内の宣言とルールの順序 | 2 つのルールのどちらが後に来るか | ファイルの外からこれに依存するものはありません |
| `behaviors/internal.js` | combobox、command、listbox、menu の各ビヘイビアが共有するヘルパー。ファイル自身のヘッダーに、ビヘイビアではないと書かれています | ビヘイビアの関数。または[ビヘイビアを所有](/guide/behaviors#own-a-behavior)し、このファイルのコピーをその隣に置きます |
| `dist/` 配下にある、このページで名前を挙げていないファイル | ビルドがそこに残すその他のファイル | 上の表にあるパス |
| `frameworks/` 配下のファイル | パッケージが保持している [React、Svelte、Vue のコンポーネント](/guide/frameworks)。インポートするモジュールではなくコピーするためのソースであり、その props はリリース間で変わる可能性があります | 1 つをコピーする `npx master-ui add <name>`。コピーはあなたのものであり、リリースによって変わりません |

実装の詳細は、コントラクトが同じままでも変わることがあります。たとえば、コンポーネントが受け付けるマークアップを変えずに、影が調整されたり、マークが別の疑似要素に移ったりすることがあります。それでも結果の見た目は変わりうるため、目視での確認は引き続きアップグレードの一部です。

```css name=app.css
/* Public: the button contract lists --btn-height. */
.checkout .btn {
  --btn-height: 2.75rem;
}

/* Private: no contract lists --btn-lift, so a release may rename it. */
.checkout .btn {
  --btn-lift: 0px;
}

/* The public way to say the same thing is the theme token. */
.checkout {
  --lift: 0px;
}
```

## 変更の意味 \{#what-a-change-means\}

| 変更 | 破壊的か |
| --- | --- |
| 公開されている名前の削除または改名：クラス、必須の属性、状態のマーク、記載されたプロパティ、トークン、ミックスイン、エクスポート、コマンド、インポートパス | はい |
| 既定のテーマの調整：トーン、影、グラデーション、時間 | いいえ |
| 非公開リストにあるものの変更 | いいえ |
| パッケージ内のフレームワークコンポーネントの変更：props、そのマークアップ | いいえ。プロジェクト内のコピーは取り込んだときのまま残り、アップストリームが変わったことは `master-ui status` が伝えます |

見た目の調整は、コントラクトを保ったまま行われることがあります。プロジェクトが管理すべきものはどれか、つまりインストールするリリース、1 つのコンポーネントの実装、テーマの値のいずれなのかを判断してください。

**コンポーネントを所有します。** `own` は、そのスタイルシート、コントラクト、そして存在する場合はビヘイビアをコピーします。ページをそれらのコピーに接続すると、以後のパッケージのリリースでその実装が置き換えられなくなります。コピーしたスタイルシートは引き続きテーマトークンを読み取るため、所有するだけでは見た目は固定されません。[カスタマイズ](/guide/customization#own-a-component)を参照してください。

```bash
npx master-ui own button
```

### ローカルのテーマを保持する \{#pin-the-theme\}

`node_modules/@master/ui/theme.css` をプロジェクトにコピーし、ライブラリの後にインポートします。そのトークンとミックスインの定義は、パッケージの定義より優先されます。これによりコピーした値は保たれますが、新しいトークンや、コンポーネントによるトークンの使い方の変更は、引き続き結果に影響することがあります。このファイルの保守方法は[テーマ設定](/guide/theming)で説明しています。

```css name=app.css
@import '@master/css';
@import '@master/ui';
@import './ui/theme.css';
```

## パッケージが実験段階にある間 \{#experimental\}

Master UI は実験段階にあり、そのバージョンは 0.x です。1.0 までは、上の表は名前が何であるかを示すものであり、それを維持する約束ではありません。どのリリースでも公開されている名前が改名または削除される可能性があり、非推奨期間、互換レイヤー、移行ガイドはいずれも提供されません。変更点はリリースノートに記載されます。

そのため、正確なバージョンをインストールし、意図的にアップグレードしてください。

```bash
npm install @master/ui --save-exact
```

`--save-exact` は、許可するバージョン範囲ではなく、選択したバージョンを記録します。他のチェックアウトで同じ依存関係のセットがインストールされるよう、パッケージマニフェストとロックファイルを一緒にコミットしてください。そうすれば、ローカルのテーマやコンポーネントのコピーを既知のリリースに照らして確認できます。

プロジェクトが所有するコンポーネントについては、コマンドラインツールが変更点を報告します。`status` は所有する各コンポーネントをインストール済みのパッケージと比較し、取り込み以降にアップストリームで変更されたファイルを一覧表示します。

```bash
npx master-ui status
```

所有するコンポーネントがアップストリームで変更されている場合は終了コード 2 で終了するため、アップグレード後に実行するジョブでそれを報告できます。`npx master-ui diff button` は、保存済みのベースとインストール済みのパッケージの差分を表示します。差分を確認して自分でマージした後、`npx master-ui accept button` で保存済みのベースを進めます。このコマンドは作業中のコピーをマージしたり編集したりしません。コマンドの手順は[カスタマイズ](/guide/customization#upstream-changes)で説明しています。

<GuideFigure name="stability" title="アップストリームの変更をマージする">

**比較し、マージしてから、新しいベースを記録します。** `diff` は保存済みのベースとインストール済みのパッケージを比較し、作業中のコピーはその比較に含めません。必要な変更は自分で作業中のコピーにマージします。その後、`accept` がインストール済みのアップストリームのファイルを保存済みのベースにコピーし、所有の記録を更新します。マージ済みの作業中のコピーには手を加えません。図中のファイルのマークは模式的なものであり、特定のリリースの差分ではありません。

</GuideFigure>

アップグレードのたびに、次の手順を行います。

1. リリースノートを読み、正確な依存関係のバージョンとロックファイルを更新します。
2. プロジェクトのマークアップに対して `npx master-ui check` を実行し、コントラクトに合わなくなったクラス、要素、属性を見つけます。
3. 所有したコンポーネントと追加したコンポーネントについて `status` と `diff` を確認します。新しいベースを受け入れる前にマージします。
4. アプリケーションをビルドし、影響を受けるコントロール、オーバーレイ、キーボード操作の経路を試します。ローカルのテーマも含め、ライトとダークの見た目を比較します。

チェッカーはマークアップをコントラクトに照らして検証しますが、アプリケーションの振る舞いやレンダリング結果が変わっていないことまでは確認できません。
