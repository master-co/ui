패키지의 모든 스타일시트 옆에는 계약이 있습니다. `button.css` 옆에 `button.json`이 있는 식입니다. 계약은 스타일시트가 약속하는 내용을 프로그램이 읽을 수 있는 형태로 기술합니다. 클래스, 각 클래스가 놓이는 위치, 스타일시트가 그리는 상태, 공개하는 사용자 지정 속성, 그리고 올바른 최소 마크업입니다.

검사기, 자동 생성되는 컴포넌트 표, 이식 가능한 컴포넌트 페이지, [레지스트리](/guide/registry)가 이 계약을 읽습니다. 클래스 규칙을 하나의 소스에 두면 중복이 줄어들며, 패키지 테스트는 계약과 스타일시트가 일치하는지 확인합니다. 계약은 지원되는 마크업을 기술하지만, 상호작용, 접근성, 시각적 동작에 대한 브라우저 확인을 대신하지는 않습니다.

버튼의 마크업과 공개 속성을 찾으려면 `npx master-ui contract button`부터 시작하세요. `@master/ui/components/button.json`으로 가져올 수도 있고, `@master/ui/contracts.json`이나 `https://ui.master.co/contracts.json`에서 전체를 받을 수도 있습니다. 스키마는 `https://ui.master.co/contract.schema.json`입니다.

## 계약이 담는 내용 \{#keys\}

| 키 | 담는 내용 |
| --- | --- |
| `name`, `title`, `tier`, `category`, `description` | 스타일시트의 파일 이름인 슬러그, 독자가 보는 이름, `component` 또는 `layout`, 속한 그룹, 무엇인지 설명하는 한 문장 |
| `use` | 언제 사용하는지 |
| `instead` | 다른 상황에서 올바른 선택이 되는 이웃 컴포넌트. 각각 `when`과 `use`에 있는 다른 계약의 이름으로 나타냅니다 |
| `composes` | 마크업이 그 클래스를 사용하는 다른 계약. 예를 들어 콤보박스의 `input`과 `listbox`입니다. 이들의 스타일시트도 가져와야 합니다 |
| `script` | `none`, `optional`, `required` |
| `behavior` | 패턴을 구동하는 참조 스크립트 |
| `keyboard` | 네이티브로, 또는 동작을 연결한 뒤 각 키가 하는 일 |
| `platform` | 향상 기능으로 쓰이는 각 플랫폼 기능과, 그 기능이 없는 브라우저에서 보이는 모습 |
| `classes` | 스타일시트가 정의하는 모든 클래스. 그 밖의 클래스는 없습니다 |
| `states` | 스타일시트가 그리는 각 상태와, 그 상태를 표시하는 속성이나 의사 클래스 |
| `properties` | 공개 사용자 지정 속성 |
| `example` | 올바른 최소 마크업 |

`name`, `title`, `tier`, `category`, `description`, `use`, `script`, `classes`, `example`은 필수입니다. 스키마는 이 표에 있는 키와 `$schema` 외의 키를 허용하지 않습니다.

## 클래스 \{#classes\}

각 클래스에는 `name`, `kind`, `description`이 있습니다. kind는 클래스가 놓일 수 있는 위치를 나타냅니다.

<GuideFigure name="contracts" title="루트, 수식자, 부분">

**수식자는 요소를 공유하고, 부분은 그 안에 놓입니다.** 루트 `dialog`와 수식자 `dialog-drawer`는 같은 dialog 요소에 붙습니다. 그 자식인 제목에는 부분 `dialog-title`이 붙습니다. 수식자를 별도의 요소에 추가하면 이 관계를 충족하지 못합니다.

</GuideFigure>

| 종류 | 놓이는 위치 | 예 |
| --- | --- | --- |
| `root` | 단독으로. 스타일시트에 여러 개가 있을 수 있습니다 | `btn`, `btn-group`, `dialog` |
| `part` | `of`에 지정한 루트 안 | `dialog`의 `dialog-title` |
| `modifier` | `of`에 지정한 기반 클래스와 같은 요소 | `btn`의 `btn-primary` |

부분의 수식자는 그 부분을 지정합니다. `menu-item-danger`의 `of`는 `menu-item`입니다. 클래스가 여러 개 중 어느 하나와 함께 쓰일 때 `of`는 목록입니다. 다음은 버튼의 `classes`에 있는 항목 세 개입니다.

```json name=button.json
{ "name": "btn", "kind": "root", "description": "The raised base button", "elements": ["button", "a", "summary", "label", "input"] },
{ "name": "btn-sm", "kind": "modifier", "of": "btn", "exclusive": "size", "description": "32px tall; the default is 38px" },
{ "name": "btn-square", "kind": "modifier", "of": "btn", "label": true, "description": "A square button for one icon; it needs an accessible name" }
```

## 검사기가 강제하는 것 \{#constraints\}

kind만으로도 검사기에는 두 가지 규칙이 생깁니다. 수식자에는 기반 클래스가 필요하고, 부분에는 루트가 필요합니다. 클래스에 붙는 네 가지 선택적 키는 문서의 규칙을 `master-ui check`가 보고하는 항목으로 바꿉니다. 잘못된 제약은 누군가의 프로젝트에서 잘못된 오류가 되므로, 계약은 스타일시트나 플랫폼이 요구할 때만 이 키를 추가합니다.

| 키 | 의미 | 예 |
| --- | --- | --- |
| `elements` | 클래스가 이 요소에서만 동작합니다. 어떤 요소든 괜찮으면 생략합니다 | `dialog`에는 `["dialog"]` |
| `attributes` | 요소가 가져야 하는 속성: 어떤 값이든 되면 `true`, 하나의 값이면 문자열, 여러 값 중 하나이면 배열 | `switch`: `{ "type": "checkbox", "role": "switch" }` |
| `label` | 요소에 접근 가능한 이름이 필요합니다 | `btn-square`, `dialog-close` |
| `exclusive` | 그룹 키. 같은 키를 가진 두 수식자는 한 요소에 함께 쓰지 않습니다 | `btn-sm`과 `btn-lg`는 둘 다 `"size"`입니다 |

다섯 번째 키는 규칙을 완화합니다. `"anywhere": true`는 루트 밖에 놓일 수 있는 부분을 표시합니다. 예를 들어 `field`의 부분이면서 field 밖에도 놓일 수 있는 `field-hint`입니다.

## 상태와 속성 \{#states-and-properties\}

상태는 스타일시트가 그리고, 마크업에서는 네이티브 속성이나 ARIA 속성으로 표시합니다. 상태를 위한 클래스는 절대 없습니다. 각 항목은 표시를 지니는 클래스를 `on`에, 짧은 `name`을, 그리고 마크업이나 CSS에 쓰이는 그대로의 `mark`를 지정합니다.

```json name=button.json
{ "on": "btn", "name": "pressed", "mark": "aria-pressed=\"true\"", "description": "A quiet toggle that is on stays sunk into a well" }
```

`:user-invalid`나 `:popover-open`처럼 콜론으로 시작하는 표시는 브라우저가 설정하는 의사 클래스이므로 직접 작성할 것이 없습니다.

`properties`는 공개 API인 사용자 지정 속성, 즉 프로젝트가 설정해도 되는 속성을 나열합니다. 각 항목에는 `name`과 `description`이 있고, 그 속성을 선언하거나 읽는 클래스가 첫 번째 루트가 아니면 `on`에 그 클래스가 있으며, 스타일시트가 기본값을 선언하면 `default`가 있습니다.

```json name=button.json
{ "name": "--btn-height", "default": "2.375rem", "description": "Minimum block size" }
```

이 목록에 없는 컴포넌트별 사용자 지정 속성은 구현 세부 사항입니다. 테마 토큰은 여러 컴포넌트가 공유하는 별도의 공개 인터페이스이며, 각 역할은 [기본 테마](/guide/theme)를 참고하세요. 테마 토큰과 컴포넌트 속성 중 무엇을 쓸지는 [사용자 지정](/guide/customization#property)에서, 현재 버전 정책은 [안정성](/guide/stability)에서 확인하세요.

## 스크립트와 동작 \{#script\}

`script`는 컴포넌트가 JavaScript에 얼마나 의존하는지 나타냅니다.

| 값 | 의미 |
| --- | --- |
| `none` | 모든 상태가 스크립트 없이 동작합니다 |
| `optional` | 메뉴의 화살표 키처럼 스크립트가 편의 기능을 더하며, 페이지는 스크립트 없이도 동작합니다 |
| `required` | 패턴에 대응하는 네이티브 요소가 없으므로 스크립트가 속성을 바꿉니다 |

`behavior`는 `@master/ui/behaviors/<behavior>.js`로 공개되는 참조 스크립트를 지정합니다. 콤보박스의 계약에는 `"script": "required"`와 `"behavior": "combobox"`가 있습니다.

```js
import { combobox } from '@master/ui/behaviors/combobox.js'

combobox(document.querySelector('.combobox'))
```

동작은 스타일시트가 읽는 속성을 바꿉니다. 스플리터 같은 패턴은 이벤트에서 얻은 값을 공개 사용자 지정 속성으로도 전달하며, 그 값을 어떻게 그릴지는 스타일시트가 결정합니다. `keyboard`는 동작을 연결한 뒤 각 키가 하는 일, 또는 네이티브 요소가 이미 하는 일을 나열합니다. [동작](/guide/behaviors)을 참고하세요.

## 예제 \{#example\}

`example`은 실제 단어가 들어간, 올바른 최소 마크업입니다. 패키지 테스트는 모든 예제에 검사기를 실행하고 진단이 없을 것을 기대합니다. 이를 마크업의 기준으로 삼은 다음, 페이지에 맞는 레이블, 고유한 id, 애플리케이션 액션, 필요한 동작을 제공하세요.

```html
<button type="button" class="btn btn-primary">Save changes</button>
```

## 직접 만든 컴포넌트의 계약 작성하기 \{#your-own\}

프로젝트는 라이브러리에 없는 것, 즉 구성 요소들이 공유하는 재질, 상태, 플랫폼 동작, 기하 구조가 있을 때 자체 컴포넌트를 추가합니다. 스타일시트는 클래스 선택자와 토큰을 사용해 `@layer components` 안에 작성하고, 계약은 그 옆의 `ui/`에 작성하세요. 계약은 라이브러리의 계약과 같은 스키마를 따릅니다.

```css name=ui/price-tag.css
@layer components {
  .price-tag {
    --price-tag-size: 1.125rem;
    display: inline-flex;
    align-items: baseline;
    gap: .375rem;
    color: var(--color-text-strong);
    font-size: var(--price-tag-size);
    font-variant-numeric: tabular-nums;

    &.price-tag-sale {
      color: var(--color-danger);
    }
  }

  .price-tag-was {
    color: var(--color-text-muted);
    font-size: .75em;
  }
}
```

```json name=ui/price-tag.json
{
  "$schema": "https://ui.master.co/contract.schema.json",
  "name": "price-tag",
  "title": "Price tag",
  "tier": "component",
  "category": "Commerce",
  "description": "The price of one product, with the price it replaces.",
  "use": "A price on a product card or in a cart row. Add price-tag-sale and the old price when the product is reduced.",
  "script": "none",
  "classes": [
    { "name": "price-tag", "kind": "root", "description": "The current price, in strong ink and tabular figures" },
    { "name": "price-tag-sale", "kind": "modifier", "of": "price-tag", "description": "A reduced price, in the danger hue" },
    { "name": "price-tag-was", "kind": "part", "of": "price-tag", "elements": ["s"], "description": "The price before the reduction, struck through in muted ink" }
  ],
  "properties": [
    { "name": "--price-tag-size", "default": "1.125rem", "description": "Font size of the current price" }
  ],
  "example": "<p class=\"price-tag price-tag-sale\">$24 <s class=\"price-tag-was\">$32</s></p>"
}
```

예제가 그려지도록 애플리케이션 스타일시트에서 Master UI 다음에 `ui/price-tag.css`를 가져오세요. CLI는 이 CSS 가져오기와 관계없이 옆에 있는 계약을 찾아냅니다.

```css name=app.css
@import '@master/css';
@import '@master/ui';
@import './ui/price-tag.css';
```

그러면 프로젝트의 컴포넌트를 같은 도구에서 사용할 수 있습니다.

- `npx master-ui list`가 이를 나열하고, `npx master-ui contract price-tag`가 출력합니다. 마크업을 작성하기 전에 계약을 읽는 에이전트도 같은 방식으로 찾아냅니다.
- `npx master-ui check`가 마크업이 이를 따르는지 검사합니다. 다음 예에서 `npx master-ui check cart.html`은 세 가지 실수를 보고합니다.

```html name=cart.html
<p class="price-tag-sale">$24</p>
<p class="price-tag">$24 <span class="price-tag-was">$32</span></p>
<p class="price-tag price-tag-large">$24</p>
```

```
cart.html:1:1 error missing-base "price-tag-sale" modifies "price-tag": write class="price-tag price-tag-sale".
cart.html:2:26 error element "price-tag-was" goes on <s>, not <span>.
cart.html:3:1 warning unknown-class "price-tag-large" is not a class of price-tag. It has: price-tag, price-tag-sale, price-tag-was.

1 files checked: 2 errors, 1 warnings.
```

세 가지 세부 사항이 있습니다.

- **계약을 읽는 위치.** 프로젝트의 `ui/` 디렉터리에서 `name`과 `classes` 배열을 가진 모든 `.json` 파일입니다. `master-ui.json`은 `directory`에 다른 디렉터리를, `contracts` 배열에 추가 패턴을 지정할 수 있습니다.
- **스키마 줄.** `"$schema": "https://ui.master.co/contract.schema.json"`이 있으면 편집기가 작성하는 동안 파일을 검증할 수 있습니다.
- **라이브러리에 이미 있는 이름.** 라이브러리 계약과 같은 이름을 가진 프로젝트 계약은 라이브러리 계약을 대체합니다. [소유한 컴포넌트](/guide/customization#own-a-component)가 그 복사본으로 기술되는 방식이 바로 이것입니다.

## 진단 \{#diagnostics\}

`master-ui check`는 발견 항목마다 한 줄을 출력합니다. 파일, 줄과 열, 심각도, 코드, 메시지입니다. `unknown-class`를 제외한 모든 코드는 오류이며, `unknown-class`는 `--strict`를 전달하지 않으면 경고입니다.

| 코드 | 의미 | 해결 방법 |
| --- | --- | --- |
| `unknown-class` | 클래스가 루트 이름과 대시로 시작하지만 어느 계약에도 없습니다 | 메시지에 나열된 클래스 중 하나를 사용하세요. 프로젝트 자체 클래스라면 `ui/`의 계약에 추가하거나, 컴포넌트의 이름 체계 밖의 이름을 붙이세요 |
| `missing-base` | 수식자가 수식하는 클래스가 없는 요소에 있습니다 | 옆에 기반 클래스를 추가하세요: `class="btn btn-primary"` |
| `outside-root` | 부분에 루트 클래스를 가진 조상이 없습니다 | 루트 안으로 옮기거나 컨테이너에 루트 클래스를 추가하세요 |
| `exclusive` | 두 가지 크기처럼 같은 그룹의 수식자 두 개가 한 요소에 있습니다 | 하나만 남기세요 |
| `element` | 계약이 허용하지 않는 요소에 클래스가 있습니다 | 메시지가 지정한 요소를 사용하세요: `dialog`는 dialog 요소에 붙습니다 |
| `attribute` | 클래스가 요구하는 속성이 요소에 없거나 다른 값을 가집니다 | `role="switch"`처럼 메시지가 지정한 속성을 추가하세요 |
| `label` | 컨트롤에 접근 가능한 이름이 없습니다 | 자체 텍스트, `aria-label`, `aria-labelledby`, 또는 컨트롤을 감싸거나 가리키는 레이블을 지정하세요 |

검사기는 페이지를 렌더링하지 않고 소스를 읽습니다. 표현식 안의 리터럴 클래스는 검사할 수 있지만, 계산된 클래스 이름을 해석하거나, 프레임워크 컴포넌트가 자식을 어디에 렌더링하는지 증명하거나, 다른 파일에 있는 루트를 검사하지는 못합니다. 불확실한 경우는 그대로 둡니다. 깨끗한 결과가 포커스 순서, 대비, 브라우저 지원, 또는 선택한 컴포넌트가 작업에 맞는지를 검증하지는 않습니다.
