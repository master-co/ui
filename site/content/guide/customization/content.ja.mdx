変更したい対象に合わせて、カスタマイズ方法を選びます。対象は、個々のインスタンス、共通のデザイン値、コンポーネントの寸法や余白、質感、実装そのもののいずれかです。必要な結果を得られる最小限の変更から始めれば、残りの部分は引き続きパッケージ側で保守されます。

質感と状態の関係に一貫性を持たせるには、[デザイン](/guide/design#customization-boundaries)を参照してください。既定のトークンの役割と値は、[既定のテーマ](/guide/theme)に記載されています。トークンやテーマの変更内容が決まったら、[テーマの作成と調整](/guide/theming)で実装方法を確認できます。

<GuideFigure name="customization" title="カスタマイズする層の選び方">

**最初の4つの方法では、パッケージの実装をそのまま使います。** ユーティリティ、トークン、公開カスタムプロパティ、テーマで、レイアウトや値、質感を変更できます。`init`の後に`master-ui own`を実行すると、コンポーネントのソースがコピーされ、スタイルシートのインポート先がコピーに切り替わります。コピーしたビヘイビアを使うには、それを利用する側のインポート先もローカルファイルに変更します。コピーしたソースはプロジェクトで保守し、ほかのコンポーネントは引き続きパッケージから利用します。各段階の違いは、変更行数ではなく保守の責任範囲にあります。

</GuideFigure>

## カスタマイズの5段階 \{#the-ladder\}

| 段階 | 変更方法 | 用途 | パッケージの更新に追従する範囲 |
| --- | --- | --- | --- |
| 1. ユーティリティ | 要素にユーティリティを追加（`class="btn w-full"`） | 個々のインスタンス | すべて |
| 2. トークン | `@theme`でテーマトークンを上書きするか、要素に設定してそのサブツリーに適用 | ブランドカラー、角の半径、表示密度、フォーカス、移動量、面の色調 | すべて |
| 3. 公開プロパティ | コンポーネントの公開カスタムプロパティを、個々の要素またはプロジェクト独自のクラスで設定 | 特定のコンポーネントの寸法や余白を全体または指定範囲で調整 | すべて |
| 4. テーマ | テーマファイルを作成し、トークンと、質感の定義に必要なミックスインを記述 | フラット、枠線付き、色味付きなど、異なる質感 | すべてのコンポーネント |
| 5. ソースの自前管理 | `npx master-ui own <name>`でスタイルシート、コントラクト、ビヘイビアを`ui/`にコピーし、インポート先をコピーに変更 | 構造、パーツ、状態、ビヘイビア | ほかのコンポーネント。自前管理するものは必要に応じて手動で取り込み |

「パッケージの更新に追従する」とは、インストールしたバージョンのパッケージから実装が提供されることです。アップグレード時には引き続き確認が必要で、上書きした値には引き続き指定した値が使われます。詳しくは[安定性](/guide/stability#experimental)を参照してください。

## 行数よりも変更対象の層で判断 \{#which-layer\}

「宣言の3分の1を上書きしたら自前で管理する」といった割合の基準はありません。判断基準は、変更に必要な行数ではなく、どの層に手を加えるかです。

200個のトークン値を設定しても、変更対象はテーマだけです。これは段階4で、すべてのコンポーネントが引き続きパッケージの更新に追従します。一方、ボタンを押している間の描画を打ち消す変更が、どのトークンやプロパティでも表現できないなら、変更対象はコンポーネントの状態です。宣言が1行でも段階5に当たります。行数で判断すると、前者は実際より上の段階に、後者は実際より下の段階に見えてしまいます。

変更したいのが、個々のインスタンス、全コンポーネントが参照する値、特定のコンポーネントが公開する値、質感、あるいはコンポーネントの構造・状態・ビヘイビアのどれかを確認します。それに応じて段階が決まります。

## 1. ユーティリティ \{#utility\}

コンポーネントのクラスは`components`レイヤーに、ユーティリティはそれより後の`utilities`レイヤーにあります。そのため、要素にユーティリティを指定するだけで優先され、`!important`や独自のスタイルシートのルールは不要です。

```html
<button type="button" class="btn btn-primary w-full">Save changes</button>
```

幅やマージン、レイアウト内の配置など、個々のインスタンスに固有の調整に使います。

## 2. トークン \{#token\}

テーマトークンは、色や影、角の半径など、共通のデザイン値を制御します。インポートの後でトークンを上書きすると、その値を参照するすべてのコンポーネントに反映されます。たとえば、`--color-brand`を変更するとブランドカラーを使う面が変わり、通常のボタンはニュートラルな質感を保ちます。

```css name=app.css
@import '@master/css';
@import '@master/ui';

@theme {
  --color-brand: oklch(58% .19 28);
}
```

質感を保ったまま共通の値を変更するときに使います。関連する値の調整や、ページの一部に限定した上書きについては、[トークンの調整](/guide/theming#retune-tokens)を参照してください。

## 3. 公開カスタムプロパティ \{#property\}

コンポーネントが公開するカスタムプロパティは、コントラクトに記載されています。`npx master-ui contract button`を実行すると、`--btn-height`、`--btn-padding-x`、`--btn-gap`、`--btn-font-size`、`--btn-radius`、`--icon-size`が表示されます。これらは、特定のコンポーネントの寸法や余白を調整するためのものです。

個々の要素を調整するには、プロパティをインラインで設定します。

```html
<button type="button" class="btn" style="--btn-height: 2rem">Filter</button>
```

同じバリエーションを繰り返し使う場合は、公開プロパティだけを設定するプロジェクト独自のクラスを作り、コンポーネントのクラスと併用します。

```css name=app.css
.compact-control {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

```html
<button type="button" class="btn compact-control">Filter</button>
```

ページ内の特定の範囲にあるすべてのボタンを調整するには、その範囲内のボタンにプロパティを設定します。

```css name=app.css
.editor-tools .btn {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

コンポーネントは自身のクラスでこれらのプロパティを宣言するため、祖先要素にだけ設定した値は適用されません。そのため、最後のルールではセレクターに`.btn`を指定しています。このルールはコントラクトで公開された値だけを設定し、面、輪郭、影のスタイルは宣言しません。

プロジェクト独自のクラスには、ライブラリの命名と重ならない名前を付けます。`btn-compact`のように、コンポーネントのルートクラス名にハイフンを続けた名前は、[チェッカー](/guide/contracts#diagnostics)によって`unknown-class`として報告されます。

## 4. テーマ \{#theme\}

フラットな面、線で縁取った輪郭、色味を加えたニュートラルカラーなど、質感を変えるにはテーマを使います。テーマはトークンを記述し、ライブラリの後にインポートするファイルです。パッケージには2つ目のテーマとして Paper が同梱されており、コンポーネントの実装を変更せずに使えます。

```css name=app.css
@import '@master/css';
@import '@master/ui';
@import '@master/ui/themes/paper.css';
```

テーマはトークンを設定し、質感を作るスタイルの組み合わせを定義します。セレクターでコンポーネントを直接指定することはありません。複数の値を組み合わせて異なる質感を表現するときに使います。[テーマの作成と調整](/guide/theming#paper)では、Paper とそのソース、独自テーマを作る際のルールを解説しています。

## コンポーネントを自前で管理する \{#own-a-component\}

段階5は、値の変更だけでは表現できない構造、パーツ、状態、ビヘイビアの変更に使います。コンポーネントのソースをプロジェクトにコピーし、そこで編集します。

次のいずれかに該当する場合は、コンポーネントを自前で管理します。それ以外は段階1〜4で対応します。

- 別のパーツ、異なる入れ子構造、別の要素などに対応するため、既存のスタイルシートにないセレクターが必要です。
- 状態に応じた見た目を、テーマトークンやコンポーネントの公開プロパティで表現できません。
- キー操作、フォーカス、項目を選択することの意味など、ビヘイビアを変更する必要があります。
- プロジェクト側で、このコンポーネントの実装を独立して保守する必要があります。テーマの値だけを管理したい場合は、[ローカルテーマを管理します](/guide/stability#pin-the-theme)。

### ソースをコピーする \{#take-the-source\}

```bash
npx master-ui init      # once: writes ui/index.css with one @import per stylesheet
npx master-ui own menu  # copies ui/menu.css, ui/menu.json and its behavior; repoints the import
```

`init`は`ui/index.css`と`master-ui.json`を書き出します。プリセットの後で、`@import '@master/ui'`に代えて`ui/index.css`をインポートします。

```css name=app.css
@import '@master/css';
@import './ui/index.css';
```

続いて、`own`が次の4つの処理を行います。

| 処理 | 保存先 |
| --- | --- |
| スタイルシートとコントラクトをコピー | `ui/menu.css`, `ui/menu.json` |
| コントラクトにビヘイビアの指定があればコピー | `ui/menu.js` |
| 各ファイルのコピー時点の内容を別途保存 | `ui/.base/` |
| コンポーネントと各ファイルのハッシュを記録 | `master-ui.json` |

さらに、`ui/index.css`の1行を`@import '@master/ui/components/menu.css';`から`@import './menu.css';`に変更します。プロジェクトに該当する行がない場合、`own`は手動で行う置き換えの内容を表示します。`--force`を指定しない限り、`ui/`にある既存ファイルは上書きしません。

コピーした実装も引き続きテーマのトークンを参照し、ミックスインを適用するため、テーマの設定が反映されます。ほかのコンポーネントは引き続きパッケージから利用します。

### コントラクトを実装と一致させる \{#keep-the-contract-true\}

CLI がこのプロジェクトの設定を読み込むと、コピーしたコントラクト`ui/menu.json`がライブラリのコントラクトに代わって使われます。エージェントもこのローカルのコントラクトを参照してください。`ui/menu.css`でクラスを追加、改名、削除したら、`ui/menu.json`も合わせて更新します。次の例では、スタイルシートにパーツを追加し、対応する項目をコントラクトの`classes`配列の末尾に追加します。

```css name=ui/menu.css
@layer components {
  /* A quiet line under the last group: the account that is signed in. */
  .menu-note {
    padding: .4375rem .5rem;
    color: var(--color-text-muted);
    font-size: .71875rem;
  }
}
```

```json name=ui/menu.json
{ "name": "menu-note", "kind": "part", "of": "menu", "description": "A quiet line under the last group" }
```

既存のクラス名と状態属性を維持すれば、ブロック、ビヘイビア、ドキュメントを引き続き利用できます。各キーについては、[コントラクト](/guide/contracts)を参照してください。

新しいパーツを使うマークアップに対して`npx master-ui check`を実行し、その後ブラウザーでコンポーネントを確認します。チェッカーが検証するのはマークアップのコントラクトです。コピーした CSS が意図した状態表示やコントラストを実現しているか、キーボード操作が意図どおりかは、別途確認が必要です。

### パッケージ側の変更を取り込む \{#upstream-changes\}

自前で管理するコンポーネントは、パッケージを更新しても自動では変わりません。3つのコマンドで、パッケージ側の変更を確認し、マージした内容を記録できます。

```bash
npx master-ui status       # which owned components changed upstream since they were taken
npx master-ui diff menu    # the change, against the copy kept in ui/.base/
npx master-ui accept menu  # after merging what is wanted: record the new base
```

`status`は自前で管理するコンポーネントごとに1行を出力し、パッケージ側で変更されたものが1つでもあれば終了コード2を返します。これにより、定期ジョブで変更を報告できます。

```
menu  upstream changed: menu.css (master-ui diff menu); edited here: menu.css
```

`diff`はコピー時点のファイルと現在のパッケージのファイルを比較します。プロジェクト側の編集は差分に含まれず、パッケージ側の変更だけを確認できます。

```
# menu.css: taken (-) and upstream now (+)
    .menu-label {
      padding: .4375rem .5rem .3125rem;
      color: var(--color-text-muted);
+     font-size: .71875rem;
-     font-size: .6875rem;
      user-select: none;
      -webkit-user-select: none;
    }
```

必要な変更を`ui/menu.css`に手動でマージします。続いて`accept`を実行すると、現在のパッケージのバージョンが比較の基準になります。`ui/`にある作業用のコピーには変更を加えません。

### パッケージのコンポーネントに戻す \{#give-back\}

スタイルシートのインポート先をパッケージに戻し、アプリケーションやフレームワークでそのビヘイビアをインポートしている箇所は、参照先を`@master/ui/behaviors`に戻します。`master-ui.json`内の`owned`から対象コンポーネントの項目を削除すると、ライブラリのコントラクトが再び適用されます。

自前で管理している、または追加したほかのコンポーネントが使っていない作業用ファイルと比較基準ファイルだけを削除します。複数のビヘイビアで`ui/internal.js`などのコピー済みヘルパーを共有していたり、フレームワークのコンポーネントがローカルのビヘイビアをインポートしていたりすることがあります。ファイルを削除する前にインポートを確認し、削除後はビルドして、パッケージに戻したコンポーネントの動作を確かめます。

### ライブラリの多くを自前で管理する場合 \{#own-all\}

ローカルのコピーとパッケージのスタイルを併用するよりも、プロジェクト全体で一貫した実装を保守する方が容易なら、自前で管理するソースを増やすことを検討します。コピーしたコンポーネントの数だけで、残りも自前で管理する必要があるとは判断できません。トークン、コントラクト、チェッカー、[スキル](/guide/ai#the-skill)は引き続き使えます。[ソースの自前管理](/guide/registry)では、パッケージとレジストリを使うワークフローを比較しています。

## サポート対象外の上書き \{#what-is-not\}

次の方法でも結果は変えられますが、サポートされているカスタマイズ方法を経由しないため、上書きした実装の変更はプロジェクト側で追跡する必要があります。

- **ライブラリのクラスをセレクターで指定し、面、輪郭、影のスタイルを再宣言するルール。** トークンや公開プロパティを使うか、コンポーネントを自前で管理します。
- **ドキュメントに記載されていないコンポーネントのプロパティ。** コントラクトに記載されているプロパティか、別途ドキュメント化されているテーマトークンを使います。コンポーネント内部のプロパティは予告なく変更されることがあります。
- `.my-btn.btn`に質感を定義する宣言を加えるなど、**新しいクラスでライブラリのコンポーネントの外観を外部から上書きすること。** プロジェクト独自のクラスでは、公開プロパティやレイアウトを設定できます。クラスで新しい質感を実装する場合は、コンポーネントを新規作成するか、自前で管理します。
- **詳細度などで優先順位を無理に上げること。** コンポーネントのスタイルに優先させるために、セレクターの詳細度を上げたり、`!important`を使ったりしないでください。ユーティリティはレイヤーの順序によって優先されます。それでも上書きできない変更が必要なら、コンポーネントを自前で管理します。

```css name=app.css
/* Not a customization: it redraws what button.css draws, and will not follow it. */
.btn {
  background: white;
  box-shadow: 0 1px 2px rgb(0 0 0 / .2);
}
```
