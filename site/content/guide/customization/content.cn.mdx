先确定要改的是单个实例、共享的设计取值、组件的几何尺寸、材质，还是实现本身，再选择对应的自定义方式。从能达到预期效果的最小改动入手，其余部分继续由软件包维护。

参考[设计](/guide/design#customization-boundaries)，保持材质与状态之间的关系一致。默认令牌的用途和取值见[默认主题](/guide/theme)。确定要修改的令牌或主题后，按[主题定制](/guide/theming)中的步骤实现。

**前四个自定义层级都沿用软件包的实现。** 工具类、令牌、公开属性和主题可以调整布局、取值或材质。完成 `init` 后，`master-ui own` 会复制组件源码，并将样式表的导入指向本地副本。要运行复制的行为脚本，还需将使用该脚本的代码改为导入本地文件。复制的源码由项目维护，其余组件仍由软件包提供。这些层级按维护责任划分，与代码行数无关。

## 自定义层级 \{#the-ladder\}

| 层级 | 操作 | 用途 | 仍沿用上游实现的部分 |
| --- | --- | --- | --- |
| 1. 工具类 | 为元素添加工具类，例如 `class="btn w-full"` | 单个实例 | 全部 |
| 2. 令牌 | 在 `@theme` 中覆盖主题令牌，或在某个元素上覆盖，使其作用于该元素的子树 | 品牌色、圆角半径、密度、焦点样式、位移幅度、表面色调 | 全部 |
| 3. 属性 | 在单个元素上直接设置组件的公开自定义属性，或通过项目自定义的类设置 | 在全局或指定范围内调整某个组件的尺寸或间距 | 全部 |
| 4. 主题 | 编写主题文件，定义令牌，并在样式方案需要时提供 mixin | 其他材质，如平面、带边框或带色调的材质 | 所有组件 |
| 5. 自行维护 | `npx master-ui own <name>` 将样式表、契约和行为脚本复制到 `ui/`，并将样式表的导入指向副本 | 结构、组成部分、状态、行为 | 其余组件，当前组件可按需跟进 |

“沿用上游实现”指实现由已安装的软件包版本提供。升级时仍需检查变更，已覆盖的取值继续以项目中的设置为准。参见[稳定性](/guide/stability#experimental)。

## 按改动涉及的层级选择 \{#which-layer\}

是否需要自行维护组件，没有“覆盖三分之一的声明”之类的比例门槛。按改动涉及的层级判断即可，代码行数不影响选择。

即使一个主题设置了两百个令牌值，改动也仅涉及主题，属于第 4 层，所有组件仍沿用上游实现。如果一条声明要撤销样式表对按钮按下状态的绘制效果，而令牌和属性都无法表达这一改动，就涉及组件状态。即使只有一行，也属于第 5 层。按行数判断会高估前一项的层级，低估后一项。

确认要改的是单个实例、所有组件都读取的共享值、某个组件公开的值、材质，还是组件的结构、状态和行为，即可确定相应的层级。

## 1. 工具类 \{#utility\}

组件类位于 `components` 层，工具类位于顺序靠后的 `utilities` 层。因此，直接添加到元素上的工具类优先，无需 `!important`，也无需在项目的样式表中添加规则。

```html
<button type="button" class="btn btn-primary w-full">Save changes</button>
```

用工具类调整单个实例的宽度、外边距或在布局中的位置。

## 2. 令牌 \{#token\}

主题令牌控制颜色、阴影和圆角半径等共享设计值。在导入之后覆盖令牌，所有读取该令牌的组件都会采用新值。例如，修改 `--color-brand` 会调整品牌色表面，普通按钮仍使用中性材质：

```css name=app.css
@import '@master/css';
@import '@master/ui';

@theme {
  --color-brand: oklch(58% .19 28);
}
```

需要调整共享值并保留现有材质时，选择这一层。[调整令牌](/guide/theming#retune-tokens)介绍相关取值，以及如何将覆盖限定在页面的某个区域。

## 3. 公开自定义属性 \{#property\}

契约列出组件公开的自定义属性。`npx master-ui contract button` 会输出这些属性：`--btn-height`、`--btn-padding-x`、`--btn-gap`、`--btn-font-size`、`--btn-radius` 和 `--icon-size`。这些属性用于调整单个组件的尺寸和间距。

只需调整一个元素时，直接在元素上内联设置该属性：

```html
<button type="button" class="btn" style="--btn-height: 2rem">Filter</button>
```

需要重复使用某个变体时，编写一个项目自有类，只设置公开属性，再把它和组件类一起用在元素上：

```css name=app.css
.compact-control {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

```html
<button type="button" class="btn compact-control">Filter</button>
```

要调整页面某个区域内的所有按钮，在该作用域内直接为按钮设置此属性：

```css name=app.css
.editor-tools .btn {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

组件在自己的组件类上声明这些属性，因此只在祖先元素上设置的值无法传给组件。所以上一条规则直接选中 `.btn`，只为契约公开的属性赋值，避免声明面层、边缘或阴影。

为项目自有类命名时，避开库的命名范围。如果类名以组件的根类名加连字符开头，例如 `btn-compact`，[检查器](/guide/contracts#diagnostics) 会将它报告为 `unknown-class`。

## 4. 主题 \{#theme\}

要更改材质，例如改用平坦的面层、线条勾勒的边缘或带色调的中性色，就使用主题。主题是一个在库之后导入的令牌文件。Paper 是软件包附带的第二套主题，不修改任何组件的实现。

```css name=app.css
@import '@master/css';
@import '@master/ui';
@import '@master/ui/themes/paper.css';
```

主题只负责设置令牌和定义材质配方，选择器不指向组件。需要让多个值配合呈现另一种材质时，使用主题。[主题定制](/guide/theming#paper) 会介绍 Paper、它的源码以及编写自定义主题的规则。

## 自行维护组件 \{#own-a-component\}

第 5 步适用于无法通过调整取值实现的改动，涉及组件的结构、部件、状态或行为。将组件源码复制到项目中，再在项目内编辑。

满足以下任一条件时，自行维护组件。其余情况使用第 1 至第 4 步。

- 改动需要样式表中尚未定义的选择器，例如要使用不同的部件、嵌套结构或元素。
- 所需的状态样式无法通过主题令牌或组件的公开属性实现。
- 需要更改行为，例如按键操作、焦点管理或选中操作的含义。
- 项目需要独立维护此组件的实现。如果只需控制主题值，[保留本地主题](/guide/stability#pin-the-theme) 即可。

### 复制源码 \{#take-the-source\}

```bash
npx master-ui init      # once: writes ui/index.css with one @import per stylesheet
npx master-ui own menu  # copies ui/menu.css, ui/menu.json and its behavior; repoints the import
```

`init` 会写入 `ui/index.css` 和 `master-ui.json`。在预设之后导入 `ui/index.css`，替换原先导入的 `@import '@master/ui'`：

```css name=app.css
@import '@master/css';
@import './ui/index.css';
```

随后，`own` 执行以下四项操作：

| 操作 | 位置 |
| --- | --- |
| 复制样式表和契约 | `ui/menu.css`, `ui/menu.json` |
| 如果契约指定了行为脚本，则复制该脚本 | `ui/menu.js` |
| 为每个文件保留一份刚复制时的原始副本 | `ui/.base/` |
| 记录组件及每个文件的哈希值 | `master-ui.json` |

该命令还会把 `ui/index.css` 中的一行从 `@import '@master/ui/components/menu.css';` 改为 `@import './menu.css';`。如果项目中没有这一行，`own` 会输出供手动替换的内容。只有传入 `--force` 时，才会覆盖 `ui/` 中已有的文件。

组件副本继续读取主题令牌并应用主题的混入，因此仍会随主题变化。其他组件仍由软件包提供。

### 让契约与实现保持一致 \{#keep-the-contract-true\}

CLI 读取项目配置时，会用复制到项目中的契约 `ui/menu.json` 替代库中的契约。智能体也应读取这份本地契约。在 `ui/menu.css` 中添加、重命名或删除类名时，同步更新 `ui/menu.json`。下面先展示如何在样式表中添加一个部件，再给出要追加到契约的 `classes` 数组中的条目：

```css name=ui/menu.css
@layer components {
  /* A quiet line under the last group: the account that is signed in. */
  .menu-note {
    padding: .4375rem .5rem;
    color: var(--color-text-muted);
    font-size: .71875rem;
  }
}
```

```json name=ui/menu.json
{ "name": "menu-note", "kind": "part", "of": "menu", "description": "A quiet line under the last group" }
```

保留现有类名和状态属性，区块、行为脚本和文档就能继续适用。[契约](/guide/contracts) 介绍了每个键。

对使用新部件的标记运行 `npx master-ui check`，然后在浏览器中检查组件。检查器只验证标记是否符合契约。还需在浏览器中确认复制的 CSS 是否实现了预期的状态、对比度和键盘行为。

### 跟进上游变更 \{#upstream-changes\}

软件包更新时，自行维护的组件会保留项目中的版本。三个命令可以查看软件包中的变更，并记录已合并的内容。

```bash
npx master-ui status       # which owned components changed upstream since they were taken
npx master-ui diff menu    # the change, against the copy kept in ui/.base/
npx master-ui accept menu  # after merging what is wanted: record the new base
```

`status` 为每个自行维护的组件输出一行。只要其中任一组件在上游有变更，命令就会以退出码 2 退出，便于定时任务报告变更：

```
menu  upstream changed: menu.css (master-ui diff menu); edited here: menu.css
```

`diff` 将最初复制的文件与包中的当前文件进行比较，因此只显示上游的改动，排除项目自己的修改：

```
# menu.css: taken (-) and upstream now (+)
    .menu-label {
      padding: .4375rem .5rem .3125rem;
      color: var(--color-text-muted);
+     font-size: .71875rem;
-     font-size: .6875rem;
      user-select: none;
      -webkit-user-select: none;
    }
```

将需要的改动手动合并到 `ui/menu.css`。随后，`accept` 将包中的当前版本设为基准，`ui/` 中的副本保持原样。

### 恢复使用库中的组件 \{#give-back\}

将样式表的导入路径改回包中的路径，并将应用或框架中该组件行为脚本的导入路径恢复为 `@master/ui/behaviors`。从 `master-ui.json` 中的 `owned` 删除该组件的条目，库的契约便会重新生效。

只删除其他自行维护或已添加的组件都不再使用的工作文件和基准文件。多个行为脚本可能共用 `ui/internal.js` 之类复制到本地的辅助文件，框架组件也可能导入本地行为脚本。删除文件前先检查这些导入，然后构建项目并验证恢复使用的组件能否正常运行。

### 自行维护库中大量组件时 \{#own-all\}

如果在整个项目中维持一致的实现比协调本地副本与包中的样式更容易，可以考虑自行维护更多源码。是否接手其余组件，要看维护成本，不能只看已复制的组件数量。主题令牌、契约、检查器和[技能](/guide/ai#the-skill)仍然适用。[自行维护源码](/guide/registry)对比了使用包和使用注册表的工作流程。

## 超出支持范围的定制方式 \{#what-is-not\}

以下覆盖方式可以改变效果，但会绕过受支持的定制方式。采用这些方式后，需要自行跟踪被覆盖实现的变化：

- **用规则选中库的类，并重新声明其表面、边缘或阴影样式。** 请使用主题令牌或属性，或自行维护该组件。
- **使用未在文档中列出的组件属性。** 请使用组件契约列出的属性，或另有文档说明的主题令牌。组件的内部属性可能随时变更，且不另行通知。
- **通过外部新增的类改写库组件的样式**，例如在 `.my-btn.btn` 中声明材质样式。项目自定义的类可以设置公开属性和布局。需要新材质时，可以创建新组件，或自行维护现有组件。
- **强行覆盖组件样式。** 切勿通过提高选择器优先级或使用 `!important` 来覆盖组件。工具类所在的层本就优先于组件层。如果仍需用更强的手段覆盖，就应自行维护该组件。

```css name=app.css
/* Not a customization: it redraws what button.css draws, and will not follow it. */
.btn {
  background: white;
  box-shadow: 0 1px 2px rgb(0 0 0 / .2);
}
```
