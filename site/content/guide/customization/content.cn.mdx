根据需要改变的对象来选择自定义方式：单个实例、共享的设计值、组件的几何尺寸、材质，或者实现本身。从能够表达预期结果的最小修改开始，这样软件包就能继续维护其余部分。

参考[设计](/guide/design#customization-boundaries)，保持材质与状态之间关系的一致性。默认令牌的作用和值请参阅[默认主题](/guide/theme)。确定要修改令牌或主题之后，[主题定制](/guide/theming)介绍了具体实现。

<GuideFigure name="customization" title="选择自定义层级">

**四个自定义点会保留软件包的实现。** 工具类、令牌、公开属性和主题用于改变布局、值或材质。执行 `init` 之后，`master-ui own` 会复制组件的源码，并把它的样式表导入改为指向副本。若要运行复制过来的行为，还需要把用到它的代码改为从本地文件导入。这份源码由你的项目维护；其他组件仍然来自软件包。这些步骤描述的是责任归属，而不是代码长度。

</GuideFigure>

## 阶梯 \{#the-ladder\}

| 步骤 | 你要做什么 | 用于什么 | 仍然跟随上游的部分 |
| --- | --- | --- | --- |
| 1. 工具类 | 为元素添加工具类：`class="btn w-full"` | 单个实例 | 全部 |
| 2. 令牌 | 在 `@theme` 中覆盖主题令牌，或在某个元素上为其子树覆盖 | 品牌色、圆角、密度、焦点、位移距离、表面的色调 | 全部 |
| 3. 属性 | 设置组件的公开自定义属性，可以在单个元素上设置，也可以通过项目自己的 class 设置 | 某个组件在所有位置或某个范围内的尺寸或间距 | 全部 |
| 4. 主题 | 编写主题文件：令牌，以及配方需要时的 mixin | 另一种材质：扁平、带边框、带色调 | 所有组件 |
| 5. 接管 | `npx master-ui own <name>`：将样式表、契约和行为复制到 `ui/`，并把导入改为指向副本 | 结构、部件、状态、行为 | 其他组件；这个组件则按需跟随 |

“跟随上游”是指实现来自你所安装的软件包版本。升级仍然需要审查，而你的覆盖会继续替换它们所选定的值；参见[稳定性](/guide/stability#experimental)。

## 看层级，而不是看行数 \{#which-layer\}

不存在某个比例，达到后就应该接管组件，例如“一旦覆盖了三分之一的声明”。衡量标准是修改触及哪个层级，而不是它需要多少行。

一个包含两百个令牌值的主题只触及主题。它属于第 4 步，每个组件仍然跟随上游。反过来，如果一条声明撤销了样式表为按下状态的按钮所绘制的效果，而这又无法用任何令牌或属性表达，它触及的就是组件的状态；无论多短，都属于第 5 步。按行数计算会把第一种修改放得太高，把第二种放得太低。

因此，请问自己修改的对象是什么：单个实例、每个组件都会读取的值、某个组件公开的值、材质，还是组件的结构、状态和行为。答案就是对应的步骤。

## 1. 工具类 \{#utility\}

组件 class 位于 `components` 层，工具类位于更靠后的 `utilities` 层，因此元素上的工具类无需 `!important`，也无需在样式表中编写规则就能生效。

```html
<button type="button" class="btn btn-primary w-full">Save changes</button>
```

把它用于只属于单个实例的内容：宽度、外边距，以及它在布局中的位置。

## 2. 令牌 \{#token\}

主题令牌控制颜色、阴影和圆角等共享的设计值。在导入之后覆盖一个令牌，所有读取它的组件都会随之改变。例如，修改 `--color-brand` 会重新调整品牌表面，而普通按钮保留其中性的材质：

```css name=app.css
@import '@master/css';
@import '@master/ui';

@theme {
  --color-brand: oklch(58% .19 28);
}
```

当某个共享值需要改变、而材质保持不变时，使用这一步。[调整令牌](/guide/theming#retune-tokens)介绍了相关的值，以及限定在页面局部的覆盖。

## 3. 公开的自定义属性 \{#property\}

契约列出了组件公开的自定义属性。`npx master-ui contract button` 会输出它们：`--btn-height`、`--btn-padding-x`、`--btn-gap`、`--btn-font-size`、`--btn-radius` 和 `--icon-size`。它们用于单个组件的尺寸和间距。

在单个元素上，以内联方式设置属性：

```html
<button type="button" class="btn" style="--btn-height: 2rem">Filter</button>
```

对于反复出现的变体，编写一个项目自己的 class，只设置公开属性而不做其他事，并把它放在组件 class 旁边：

```css name=app.css
.compact-control {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

```html
<button type="button" class="btn compact-control">Filter</button>
```

若要作用于页面某一部分中的所有按钮，就把属性交给该范围内的按钮：

```css name=app.css
.editor-tools .btn {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

组件在自己的 class 上声明这些属性，因此只设置在祖先元素上的值无法传递到组件。这就是最后一条规则要指明 `.btn` 的原因。指明它是为了设置契约公开的值；它不声明任何表面、边缘或阴影。

项目 class 的命名应避开库的名称。[检查器](/guide/contracts#diagnostics)会把以组件根 class 加连字符开头的 class（例如 `btn-compact`）报告为 `unknown-class`。

## 4. 主题 \{#theme\}

当修改针对的是材质，例如扁平表面、描线边缘或带色调的中性色时，它就是一个主题：一个在库之后导入的令牌文件。Paper 是软件包中发布的第二个主题，它没有改动任何组件。

```css name=app.css
@import '@master/css';
@import '@master/ui';
@import '@master/ui/themes/paper.css';
```

主题设置令牌并定义材质配方；它从不选择组件。当多个值需要协同构成另一种材质时，使用这一步。[主题定制](/guide/theming#paper)详细介绍了 Paper、它的源码，以及构建你自己主题的规则。

## 接管组件 \{#own-a-component\}

第 5 步用于修改结构、部件、状态或行为，这些是任何值都无法表达的。组件的源码会复制到项目中，并在那里编辑。

只要满足以下任意一项，就接管组件。在此之前，请停留在第 1 到第 4 步。

- 修改需要一个样式表中没有的选择器：另一个部件、另一种嵌套、另一个元素。
- 所需的状态处理无法通过主题令牌或组件的公开属性表达。
- 修改涉及行为：按键、焦点、选择的含义。
- 项目需要独立维护这个组件的实现。如果你只需要控制主题的值，请改为[保留一份本地主题](/guide/stability#pin-the-theme)。

### 获取源码 \{#take-the-source\}

```bash
npx master-ui init      # once: writes ui/index.css with one @import per stylesheet
npx master-ui own menu  # copies ui/menu.css, ui/menu.json and its behavior; repoints the import
```

`init` 会写入 `ui/index.css` 和 `master-ui.json`。在预设之后导入 `ui/index.css`，代替 `@import '@master/ui'`：

```css name=app.css
@import '@master/css';
@import './ui/index.css';
```

随后 `own` 会做四件事：

| 内容 | 位置 |
| --- | --- |
| 复制样式表和契约 | `ui/menu.css`、`ui/menu.json` |
| 当契约指定了行为时，复制该行为 | `ui/menu.js` |
| 为每个文件额外保存一份获取时的副本 | `ui/.base/` |
| 记录该组件以及每个文件的哈希值 | `master-ui.json` |

它还会修改 `ui/index.css` 中的一行，把 `@import '@master/ui/components/menu.css';` 改为 `@import './menu.css';`。如果项目中没有这一行，`own` 会输出需要手动完成的替换。除非传入 `--force`，否则它不会覆盖 `ui/` 中已存在的文件。

副本仍然读取主题的令牌并应用其 mixin，因此会跟随主题。其他每个组件仍然来自软件包。

### 保持契约准确 \{#keep-the-contract-true\}

当 CLI 读取此项目的配置时，复制的契约 `ui/menu.json` 会取代库中的契约。智能体也应该读取这份本地契约。在 `ui/menu.css` 中添加、重命名或删除 class 时，要同时修改 `ui/menu.json`。下面的示例为样式表添加了一个部件，随后是要追加到契约 `classes` 数组中的条目：

```css name=ui/menu.css
@layer components {
  /* A quiet line under the last group: the account that is signed in. */
  .menu-note {
    padding: .4375rem .5rem;
    color: var(--color-text-muted);
    font-size: .71875rem;
  }
}
```

```json name=ui/menu.json
{ "name": "menu-note", "kind": "part", "of": "menu", "description": "A quiet line under the last group" }
```

保留现有的 class 名称和状态属性，区块、行为和文档就仍然适用。[契约](/guide/contracts)介绍了每个键。

针对使用新部件的标记运行 `npx master-ui check`，然后在浏览器中检查该组件。检查器验证的是标记契约；它无法证明复制的 CSS 实现了你所期望的状态、对比度或键盘行为。

### 跟进上游变化 \{#upstream-changes\}

已接管的组件不再随软件包的更新而改变。三个命令可以显示软件包改变了什么，并记录已合并的内容。

```bash
npx master-ui status       # which owned components changed upstream since they were taken
npx master-ui diff menu    # the change, against the copy kept in ui/.base/
npx master-ui accept menu  # after merging what is wanted: record the new base
```

`status` 为每个已接管的组件输出一行，只要其中任何一个在上游发生了变化，就以代码 2 退出，因此定时任务可以据此报告：

```
menu  upstream changed: menu.css (master-ui diff menu); edited here: menu.css
```

`diff` 将获取时的副本与软件包当前的文件进行比较，因此它只显示上游所做的修改，不包括项目自己的编辑：

```
# menu.css: taken (-) and upstream now (+)
    .menu-label {
      padding: .4375rem .5rem .3125rem;
      color: var(--color-text-muted);
+     font-size: .71875rem;
-     font-size: .6875rem;
      user-select: none;
      -webkit-user-select: none;
    }
```

请手动把需要的内容合并到 `ui/menu.css` 中。然后 `accept` 会把软件包的当前版本作为新的基准。它不会改动 `ui/` 中的副本。

### 归还组件 \{#give-back\}

把样式表导入改回指向软件包，并把应用或框架中对其行为的导入恢复为 `@master/ui/behaviors`。从 `master-ui.json` 的 `owned` 中删除该组件的条目；之后库的契约将重新生效。

只删除其他已接管或已添加的组件不再使用的工作文件和基准文件。多个行为可能共享一个复制过来的辅助文件，例如 `ui/internal.js`，而框架组件也可能导入本地行为。删除文件之前请先检查这些导入，然后构建项目并实际操作归还的组件。

### 接管了库的大部分内容时 \{#own-all\}

当在整个项目中维护一致的实现，比协调本地副本与软件包样式更容易时，可以考虑接管更多源码。仅凭已复制组件的数量，并不足以成为接管其余部分的理由。令牌、契约、检查器和[技能](/guide/ai#the-skill)依然适用；[接管源码](/guide/registry)比较了软件包与注册表两种工作流程。

## 哪些不算自定义 \{#what-is-not\}

以下覆盖方式可以改变结果，但它们绕过了受支持的自定义点，你需要自行跟踪它们所替换的实现：

- **选择库 class 并重新声明其表面、边缘或阴影的规则。** 请使用令牌、属性，或接管该组件。
- **未记录在文档中的组件属性。** 请使用其契约中列出的属性，或另行记录的主题令牌。组件的内部属性可能在不另行通知的情况下变化。
- **从外部重新设置库组件样式的新 class**，例如带有材质声明的 `.my-btn.btn`。项目 class 可以设置公开属性和布局。新的材质就是新组件，或是已接管的组件。
- **强行胜出。** 绝不要通过提高选择器优先级或使用 `!important` 来压过组件。工具类已经凭借其所在的层生效，如果覆盖需要的不止于此，就说明应该接管该组件。

```css name=app.css
/* Not a customization: it redraws what button.css draws, and will not follow it. */
.btn {
  background: white;
  box-shadow: 0 1px 2px rgb(0 0 0 / .2);
}
```
