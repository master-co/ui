무엇을 바꿔야 하는지에 따라 맞춤 설정 방식을 선택하세요. 인스턴스 하나의 설정, 공유 디자인 값, 컴포넌트의 크기나 간격, 재질, 구현 자체 중 어디에 해당하는지 살펴보세요. 원하는 결과를 내는 가장 작은 변경부터 시작하면 나머지 구현은 패키지에서 계속 관리할 수 있습니다.

재질과 상태 표현의 관계를 일관되게 유지하려면 [디자인](/guide/design#customization-boundaries)을 참고하세요. 토큰의 기본 역할과 값은 [기본 테마](/guide/theme)에서 확인할 수 있습니다. 변경할 토큰이나 테마를 정했다면 [테마 적용](/guide/theming)에서 구현 방법을 확인하세요.

<GuideFigure name="customization" title="맞춤 설정 계층 선택">

**처음 네 단계에서는 패키지 구현을 그대로 사용합니다.** 유틸리티, 토큰, 공개 속성, 테마로 레이아웃, 값, 재질을 바꿀 수 있습니다. `init` 이후에는 `master-ui own`으로 컴포넌트 소스를 복사하고 스타일시트의 가져오기 경로를 복사본으로 바꿉니다. 복사한 동작을 실행하려면 해당 컴포넌트를 사용하는 코드에서도 로컬 파일을 가져오도록 수정하세요. 복사한 소스는 프로젝트에서 관리하며, 나머지 컴포넌트는 계속 패키지에서 가져옵니다. 각 단계는 코드 길이가 아니라 구현을 관리하는 주체를 기준으로 구분합니다.

</GuideFigure>

## 맞춤 설정 단계 \{#the-ladder\}

| 단계 | 설정 방법 | 용도 | 패키지 구현을 따르는 범위 |
| --- | --- | --- | --- |
| 1. 유틸리티 | 요소에 유틸리티 추가: `class="btn w-full"` | 인스턴스 하나 | 전체 |
| 2. 토큰 | `@theme`에서 테마 토큰을 재정의하거나, 특정 요소에서 재정의해 해당 하위 트리에 적용 | 브랜드 색상, 모서리 반경, 밀도, 포커스, 이동 거리, 표면의 색조 | 전체 |
| 3. 속성 | 개별 요소 또는 프로젝트에서 정의한 클래스로 컴포넌트의 공개 사용자 지정 속성 설정 | 특정 컴포넌트의 크기나 간격을 전체 또는 지정된 범위에서 조정 | 전체 |
| 4. 테마 | 테마 파일에 토큰을 정의하고, 재질 표현에 필요한 경우 믹스인 추가 | 평평한 표면, 테두리가 있는 표면, 색조를 입힌 표면 등 다른 재질 | 모든 컴포넌트 |
| 5. 직접 관리 | `npx master-ui own <name>`: 스타일시트, 계약, 동작을 `ui/`에 복사하고, 가져오기 경로를 복사본으로 변경 | 구조, 구성 요소, 상태, 동작 | 나머지 컴포넌트는 계속 따름. 이 컴포넌트는 요청할 때만 업스트림 변경 반영 |

“패키지 구현을 따른다”는 말은 설치한 버전의 패키지에서 구현을 가져온다는 뜻입니다. 버전을 올릴 때는 변경 사항을 검토해야 하며, 재정의한 값은 계속 적용됩니다. 자세한 내용은 [안정성](/guide/stability#experimental)을 참고하세요.

## 변경 계층을 기준으로 한 단계 선택 \{#which-layer\}

“선언의 3분의 1을 재정의하면 직접 관리한다”와 같은 비율 기준은 없습니다. 필요한 코드 줄 수와 관계없이, 변경이 어느 계층에 영향을 주는지로 판단합니다.

토큰 값이 200개인 테마도 영향을 주는 계층은 테마뿐입니다. 따라서 4단계에 해당하며, 모든 컴포넌트는 계속 패키지 구현을 따릅니다. 반면 버튼을 누른 상태에서 스타일시트가 그리는 표현을 없애는 선언은, 토큰이나 속성으로 표현할 수 없다면 컴포넌트의 상태를 변경하는 것입니다. 한 줄이어도 5단계에 해당합니다. 줄 수로 판단하면 첫 번째 변경은 실제보다 높은 단계에, 두 번째 변경은 실제보다 낮은 단계에 놓이게 됩니다.

변경 대상이 인스턴스 하나인지, 모든 컴포넌트가 참조하는 값인지, 특정 컴포넌트가 공개하는 값인지, 재질인지, 컴포넌트의 구조·상태·동작인지 확인하세요. 변경 대상에 따라 단계가 정해집니다.

## 1. 유틸리티 \{#utility\}

컴포넌트 클래스는 `components` 레이어에 있고, 유틸리티는 그보다 뒤에 오는 `utilities` 레이어에 있습니다. 따라서 `!important`를 쓰거나 프로젝트 스타일시트에 규칙을 추가하지 않아도 요소에 지정한 유틸리티가 우선합니다.

```html
<button type="button" class="btn btn-primary w-full">Save changes</button>
```

너비, 바깥 여백, 레이아웃에서의 위치처럼 특정 인스턴스에만 해당하는 값을 바꿀 때 사용하세요.

## 2. 토큰 \{#token\}

테마 토큰은 색상, 그림자, 모서리 반경처럼 여러 컴포넌트에서 공유하는 디자인 값을 제어합니다. 가져오기 이후에 토큰을 재정의하면 해당 토큰을 참조하는 모든 컴포넌트에 새 값이 적용됩니다. 예를 들어 아래처럼 `--color-brand`를 바꾸면 브랜드 색상을 쓰는 표면의 색상이 조정되고 일반 버튼에는 중립 재질이 유지됩니다:

```css name=app.css
@import '@master/css';
@import '@master/ui';

@theme {
  --color-brand: oklch(58% .19 28);
}
```

재질을 유지하면서 공유 값을 바꿔야 할 때 이 단계를 사용하세요. 함께 조정할 값과 페이지 일부에만 재정의를 적용하는 방법은 [토큰 조정](/guide/theming#retune-tokens)에서 다룹니다.

## 3. 공개 사용자 지정 속성 \{#property\}

계약에는 컴포넌트가 공개하는 사용자 지정 속성이 나열됩니다. `npx master-ui contract button`은 해당 속성인 `--btn-height`, `--btn-padding-x`, `--btn-gap`, `--btn-font-size`, `--btn-radius`, `--icon-size`를 출력합니다. 이 속성은 해당 컴포넌트의 크기와 간격을 조정하는 데 사용합니다.

요소 하나에 적용하려면 속성을 인라인으로 설정하세요:

```html
<button type="button" class="btn" style="--btn-height: 2rem">Filter</button>
```

같은 변형을 반복해서 쓰려면 공개 속성만 설정하는 프로젝트 전용 클래스를 만들고, 컴포넌트 클래스와 함께 지정하세요:

```css name=app.css
.compact-control {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

```html
<button type="button" class="btn compact-control">Filter</button>
```

페이지의 특정 영역에 있는 모든 버튼에 적용하려면 해당 범위의 버튼에 속성을 직접 설정하세요:

```css name=app.css
.editor-tools .btn {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

컴포넌트는 자체 클래스에서 이 속성들을 선언하므로 조상 요소에만 설정한 값은 컴포넌트에 적용되지 않습니다. 그래서 마지막 규칙은 `.btn`을 선택자로 지정합니다. 이 규칙은 계약에 공개된 속성의 값만 설정하며, 표면, 가장자리, 그림자를 직접 선언하지 않습니다.

프로젝트에서 정의하는 클래스에는 라이브러리의 명명 규칙과 겹치지 않는 이름을 붙이세요. [검사기](/guide/contracts#diagnostics)는 `btn-compact`처럼 컴포넌트의 루트 클래스 이름 뒤에 하이픈이 붙는 형태로 시작하는 클래스를 `unknown-class`로 보고합니다.

## 4. 테마 \{#theme\}

평평한 표면, 선을 두른 가장자리, 색조를 입힌 중립색처럼 재질 자체를 바꿀 때는 테마를 사용하세요. 테마는 라이브러리 뒤에 가져오는 토큰 파일입니다. Paper는 패키지에서 제공하는 두 번째 테마로, 컴포넌트 자체는 수정하지 않습니다.

```css name=app.css
@import '@master/css';
@import '@master/ui';
@import '@master/ui/themes/paper.css';
```

테마는 토큰을 설정하고 재질을 표현하는 규칙을 정의하며, 컴포넌트를 직접 선택하지 않습니다. 여러 값을 함께 조정해 다른 재질을 표현해야 할 때 이 단계를 사용하세요. [테마 적용](/guide/theming#paper)에서는 Paper와 그 소스, 직접 테마를 만드는 데 필요한 규칙을 설명합니다.

## 컴포넌트 직접 관리 \{#own-a-component\}

5단계는 값으로 표현할 수 없는 구조, 구성 요소, 상태, 동작을 바꿀 때 사용합니다. 컴포넌트 소스를 프로젝트에 복사한 뒤 그곳에서 수정합니다.

다음 중 하나라도 해당하면 컴포넌트를 직접 관리하세요. 그전까지는 1~4단계를 사용하세요.

- 컴포넌트 내부의 다른 구성 요소, 다른 중첩 구조, 다른 요소를 대상으로 하는 등 기존 스타일시트에 없는 선택자가 필요합니다.
- 원하는 상태 표현을 테마 토큰이나 컴포넌트의 공개 속성으로 구현할 수 없습니다.
- 키 입력 처리, 포커스, 선택의 의미 등 동작을 바꿔야 합니다.
- 프로젝트에서 이 컴포넌트의 구현을 독립적으로 관리해야 합니다. 테마 값만 조정하면 되는 경우에는 [로컬 테마를 유지](/guide/stability#pin-the-theme)하세요.

### 소스 복사 \{#take-the-source\}

```bash
npx master-ui init      # once: writes ui/index.css with one @import per stylesheet
npx master-ui own menu  # copies ui/menu.css, ui/menu.json and its behavior; repoints the import
```

`init`은 `ui/index.css`와 `master-ui.json`을 생성합니다. 프리셋 뒤에서 `@import '@master/ui'` 대신 `ui/index.css`를 가져오세요.

```css name=app.css
@import '@master/css';
@import './ui/index.css';
```

이어서 `own`은 다음 네 가지 작업을 수행합니다:

| 작업 내용 | 저장 위치 |
| --- | --- |
| 스타일시트와 계약을 복사합니다 | `ui/menu.css`, `ui/menu.json` |
| 계약에 동작이 명시되어 있으면 해당 동작을 복사합니다 | `ui/menu.js` |
| 각 파일을 가져온 시점의 상태로 한 부 더 보관합니다 | `ui/.base/` |
| 컴포넌트와 각 파일의 해시를 기록합니다 | `master-ui.json` |

또한 `ui/index.css`에서 한 줄을 `@import '@master/ui/components/menu.css';`에서 `@import './menu.css';`로 바꿉니다. 프로젝트에 해당 줄이 없으면 `own`은 수동으로 적용할 변경 내용을 출력합니다. `--force`를 전달한 경우에만 `ui/`에 이미 있는 파일을 덮어씁니다.

복사본도 테마의 디자인 토큰을 읽고 믹스인을 적용하므로 테마를 따릅니다. 나머지 컴포넌트는 모두 계속 패키지에서 가져옵니다.

### 계약과 구현의 일치 유지 \{#keep-the-contract-true\}

CLI가 이 프로젝트의 설정을 읽을 때는 복사한 계약인 `ui/menu.json`을 라이브러리 계약 대신 사용합니다. 에이전트도 이 로컬 계약을 읽어야 합니다. `ui/menu.css`에서 클래스를 추가하거나 이름을 바꾸거나 삭제할 때는 `ui/menu.json`도 함께 수정하세요. 아래에서는 스타일시트에 구성 요소를 추가한 뒤 계약의 `classes` 배열 끝에 넣을 항목을 보여 줍니다.

```css name=ui/menu.css
@layer components {
  /* A quiet line under the last group: the account that is signed in. */
  .menu-note {
    padding: .4375rem .5rem;
    color: var(--color-text-muted);
    font-size: .71875rem;
  }
}
```

```json name=ui/menu.json
{ "name": "menu-note", "kind": "part", "of": "menu", "description": "A quiet line under the last group" }
```

기존 클래스 이름과 상태 속성을 유지하면 블록, 동작, 문서를 계속 그대로 사용할 수 있습니다. [계약](/guide/contracts)에서 모든 키를 설명합니다.

새 구성 요소를 사용하는 마크업에 `npx master-ui check`를 실행한 뒤 브라우저에서 컴포넌트를 확인하세요. 검사기는 마크업이 계약을 따르는지 확인합니다. 검사기 결과만으로는 복사한 CSS가 의도한 상태, 대비, 키보드 동작을 구현하는지 알 수 없습니다.

### 업스트림 변경 사항 추적 \{#upstream-changes\}

직접 관리하는 컴포넌트는 패키지를 업데이트해도 바뀌지 않습니다. 세 가지 명령으로 패키지의 변경 사항을 확인하고 병합한 내용을 기록할 수 있습니다.

```bash
npx master-ui status       # which owned components changed upstream since they were taken
npx master-ui diff menu    # the change, against the copy kept in ui/.base/
npx master-ui accept menu  # after merging what is wanted: record the new base
```

`status`는 직접 관리하는 컴포넌트마다 한 줄씩 출력하며, 하나라도 업스트림에서 변경되었으면 종료 코드 2를 반환합니다. 예약 작업에서 이 코드로 변경 여부를 보고할 수 있습니다.

```
menu  upstream changed: menu.css (master-ui diff menu); edited here: menu.css
```

`diff`는 처음 가져온 복사본과 현재 패키지의 파일을 비교해 업스트림 변경 사항만 보여 줍니다. 프로젝트에서 자체적으로 수정한 내용은 비교에서 제외됩니다.

```
# menu.css: taken (-) and upstream now (+)
    .menu-label {
      padding: .4375rem .5rem .3125rem;
      color: var(--color-text-muted);
+     font-size: .71875rem;
-     font-size: .6875rem;
      user-select: none;
      -webkit-user-select: none;
    }
```

반영할 변경 사항을 `ui/menu.css`에 수동으로 병합하세요. 그런 다음 `accept`를 실행하면 현재 패키지 버전이 기준이 됩니다. `ui/`의 복사본은 이 명령의 변경 대상에서 제외됩니다.

### 패키지 컴포넌트로 되돌리기 \{#give-back\}

스타일시트를 다시 패키지에서 가져오도록 바꾸고, 애플리케이션이나 프레임워크에서 해당 동작을 가져오는 구문이 있다면 모두 `@master/ui/behaviors`에서 가져오도록 복원하세요. `master-ui.json`에 있는 `owned`에서 해당 컴포넌트의 항목을 제거하면 라이브러리 계약이 다시 적용됩니다.

직접 관리하거나 추가한 다른 컴포넌트가 사용하지 않는 작업 파일과 기준 파일만 삭제하세요. 여러 동작이 `ui/internal.js`처럼 복사해 둔 헬퍼를 공유할 수 있고, 프레임워크 컴포넌트에서 로컬 동작을 가져올 수도 있습니다. 파일을 삭제하기 전에 해당 import 구문을 확인하고, 삭제한 뒤에는 프로젝트를 빌드해 패키지로 되돌린 컴포넌트가 제대로 동작하는지 확인하세요.

### 라이브러리의 많은 부분을 직접 관리하는 경우 \{#own-all\}

로컬 복사본과 패키지 스타일을 함께 관리하는 것보다 프로젝트 전체에서 구현을 일관되게 유지하기가 더 쉽다면, 소스를 직접 관리하는 범위를 넓히는 방안을 고려하세요. 복사한 컴포넌트가 많다는 이유만으로 나머지까지 직접 관리할 필요는 없습니다. 디자인 토큰, 계약, 검사기, [스킬](/guide/ai#the-skill)은 계속 적용됩니다. [소스 직접 관리](/guide/registry)에서는 패키지와 레지스트리의 작업 방식을 비교합니다.

## 지원 범위를 벗어나는 커스터마이징 \{#what-is-not\}

아래 방식으로도 결과를 바꿀 수 있지만, 공식적으로 지원하는 커스터마이징 지점을 우회하므로 덮어쓴 구현의 변경 사항을 직접 추적해야 합니다.

- **라이브러리 클래스를 선택해 표면, 가장자리, 그림자 중 하나를 다시 선언하는 규칙.** 디자인 토큰이나 속성을 사용하거나 컴포넌트를 직접 관리하세요.
- **문서에 없는 컴포넌트 속성.** 해당 계약에 명시된 속성이나 별도로 문서화된 테마의 디자인 토큰을 사용하세요. 컴포넌트 내부 속성은 예고 없이 바뀔 수 있습니다.
- **라이브러리 컴포넌트의 스타일을 외부에서 바꾸는 새 클래스**. 예를 들어 재질을 정의하는 선언을 넣은 `.my-btn.btn`이 이에 해당합니다. 프로젝트 클래스에서는 공개 속성과 레이아웃을 설정할 수 있습니다. 새 재질이 필요하면 새 컴포넌트를 만들거나 기존 컴포넌트를 직접 관리하세요.
- **우선순위 강제.** 컴포넌트 스타일을 덮어쓰기 위해 명시도를 높이거나 `!important`를 사용하지 마세요. 유틸리티는 캐스케이드 레이어의 순서에 따라 이미 우선합니다. 그 이상의 재정의가 필요하다면 컴포넌트를 직접 관리하세요.

```css name=app.css
/* Not a customization: it redraws what button.css draws, and will not follow it. */
.btn {
  background: white;
  box-shadow: 0 1px 2px rgb(0 0 0 / .2);
}
```
