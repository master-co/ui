무엇을 바꿔야 하는지에 따라 사용자 지정 방법을 선택하세요. 하나의 인스턴스, 공유 디자인 값, 컴포넌트의 기하 구조, 재질, 또는 구현 자체입니다. 결과를 표현할 수 있는 가장 작은 변경부터 시작하면 나머지는 패키지가 계속 유지 관리할 수 있습니다.

재질과 상태의 관계를 일관되게 유지하려면 [디자인](/guide/design#customization-boundaries)을 참고하세요. 기본 토큰의 역할과 값은 [기본 테마](/guide/theme)를 참고하세요. 토큰이나 테마 변경을 선택했다면 그 구현은 [테마 설정](/guide/theming)에서 다룹니다.

<GuideFigure name="customization" title="사용자 지정 계층 선택하기">

**네 가지 사용자 지정 지점은 패키지의 구현을 유지합니다.** 유틸리티, 토큰, 공개 속성, 테마는 레이아웃, 값 또는 재질을 바꿉니다. `init` 이후 `master-ui own`은 컴포넌트의 소스를 복사하고 스타일시트 가져오기가 그 사본을 가리키도록 바꿉니다. 복사한 동작을 실행하려면 그 동작을 사용하는 쪽의 가져오기도 로컬 파일로 바꾸세요. 그 소스는 프로젝트가 유지 관리하며, 다른 컴포넌트는 패키지에 남습니다. 각 단계는 코드의 길이가 아니라 책임을 나타냅니다.

</GuideFigure>

## 사다리 \{#the-ladder\}

| 단계 | 하는 일 | 용도 | 여전히 업스트림을 따르는 것 |
| --- | --- | --- | --- |
| 1. 유틸리티 | 요소에 유틸리티 추가: `class="btn w-full"` | 하나의 인스턴스 | 전부 |
| 2. 토큰 | `@theme`에서, 또는 하위 트리를 위해 요소에서 테마 토큰을 재정의 | 브랜드 색상, 모서리 반경, 밀도, 포커스, 이동 거리, 표면의 톤 | 전부 |
| 3. 속성 | 하나의 요소에서 또는 프로젝트 자체 클래스를 통해 컴포넌트의 공개 사용자 지정 속성을 설정 | 한 컴포넌트의 크기나 간격을 전체에서 또는 특정 범위에서 | 전부 |
| 4. 테마 | 테마 파일 작성: 토큰, 그리고 레시피에 필요한 경우 믹스인 | 다른 재질: 평면, 테두리, 색조 | 모든 컴포넌트 |
| 5. 소유 | `npx master-ui own <name>`: 스타일시트, 계약, 동작이 `ui/`로 복사되고 가져오기가 그 사본을 가리킴 | 구조, 부분, 상태, 동작 | 다른 컴포넌트, 그리고 요청 시 이 컴포넌트 |

"업스트림을 따른다"는 것은 구현이 설치한 패키지 버전에서 온다는 뜻입니다. 업그레이드는 여전히 검토가 필요하며, 재정의는 계속해서 자신이 정한 값으로 기존 값을 대체합니다. [안정성](/guide/stability#experimental)을 참고하세요.

## 몇 줄이 아니라 어느 계층인지 \{#which-layer\}

"선언의 3분의 1이 재정의되면" 같은, 컴포넌트를 소유해야 하는 비율은 없습니다. 기준은 변경이 몇 줄인지가 아니라 어느 계층에 닿는지입니다.

200개의 토큰 값으로 이루어진 테마는 테마에만 닿습니다. 이는 4단계이며, 모든 컴포넌트는 여전히 업스트림을 따릅니다. 스타일시트가 눌린 버튼에 그리는 것을 되돌리는 선언 하나로, 어떤 토큰이나 속성으로도 표현할 수 없는 것은 컴포넌트의 상태에 닿습니다. 아무리 짧더라도 이는 5단계입니다. 줄 수로 판단하면 첫 번째 변경은 너무 높게, 두 번째 변경은 너무 낮게 두게 됩니다.

따라서 변경 대상이 무엇인지 물어보세요. 하나의 인스턴스, 모든 컴포넌트가 읽는 값, 한 컴포넌트가 공개하는 값, 재질, 또는 컴포넌트의 구조, 상태, 동작입니다. 그 답이 곧 단계입니다.

## 1. 유틸리티 \{#utility\}

컴포넌트 클래스는 `components` 레이어에, 유틸리티는 그 뒤의 `utilities` 레이어에 있으므로, 요소에 적용한 유틸리티는 `!important`나 스타일시트의 규칙 없이도 우선합니다.

```html
<button type="button" class="btn btn-primary w-full">Save changes</button>
```

하나의 인스턴스에 속하는 것, 즉 너비, 여백, 레이아웃에서의 위치에 사용하세요.

## 2. 토큰 \{#token\}

테마 토큰은 색상, 그림자, 모서리 반경 같은 공유 디자인 값을 제어합니다. 가져오기 뒤에 토큰을 재정의하면 그 토큰을 읽는 모든 컴포넌트가 따라갑니다. 예를 들어 `--color-brand`를 바꾸면 브랜드 표면이 조정되지만, 일반 버튼은 중립적인 재질을 유지합니다.

```css name=app.css
@import '@master/css';
@import '@master/ui';

@theme {
  --color-brand: oklch(58% .19 28);
}
```

재질은 그대로 두고 공유 값을 바꿔야 할 때 이 단계를 사용하세요. 관련 값과 페이지 일부로 범위를 한정한 재정의는 [토큰 조정하기](/guide/theming#retune-tokens)에서 다룹니다.

## 3. 공개 사용자 지정 속성 \{#property\}

계약에는 컴포넌트가 공개하는 사용자 지정 속성이 나열되어 있습니다. `npx master-ui contract button`은 `--btn-height`, `--btn-padding-x`, `--btn-gap`, `--btn-font-size`, `--btn-radius`, `--icon-size`를 출력합니다. 이 속성들은 한 컴포넌트의 크기와 간격을 위한 것입니다.

하나의 요소에서는 속성을 인라인으로 설정합니다.

```html
<button type="button" class="btn" style="--btn-height: 2rem">Filter</button>
```

반복되는 변형이라면 공개 속성만 설정하는 프로젝트 자체 클래스를 작성하고, 컴포넌트 클래스 옆에 두세요.

```css name=app.css
.compact-control {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

```html
<button type="button" class="btn compact-control">Filter</button>
```

페이지의 한 부분에 있는 모든 버튼에 적용하려면 그 범위 안의 버튼에 속성을 전달하세요.

```css name=app.css
.editor-tools .btn {
  --btn-height: 2rem;
  --btn-padding-x: .75rem;
}
```

컴포넌트는 이 속성들을 자신의 클래스에서 선언하므로, 조상 요소에만 설정한 값은 컴포넌트에 도달하지 않습니다. 그래서 마지막 규칙은 `.btn`을 지정합니다. 이 규칙은 계약이 공개한 값을 설정하기 위해 `.btn`을 지정할 뿐이며, 면, 가장자리, 그림자를 선언하지 않습니다.

프로젝트 클래스의 이름은 라이브러리의 이름 체계 밖에서 지으세요. [검사기](/guide/contracts#diagnostics)는 `btn-compact`처럼 컴포넌트의 루트와 대시로 시작하는 클래스를 `unknown-class`로 보고합니다.

## 4. 테마 \{#theme\}

평면적인 면, 선으로 그린 가장자리, 색조가 있는 중립색처럼 재질을 바꾸는 경우 그것은 테마입니다. 테마는 라이브러리 뒤에 가져오는 토큰 파일입니다. Paper는 패키지에 게시된 두 번째 테마이며, 어떤 컴포넌트도 바꾸지 않습니다.

```css name=app.css
@import '@master/css';
@import '@master/ui';
@import '@master/ui/themes/paper.css';
```

테마는 토큰을 설정하고 재질 레시피를 정의하며, 컴포넌트를 선택하지 않습니다. 여러 값이 함께 다른 재질로 작동해야 할 때 이 단계를 사용하세요. [테마 설정](/guide/theming#paper)에서 Paper와 그 소스, 그리고 직접 테마를 만드는 규칙을 살펴봅니다.

## 컴포넌트 소유하기 \{#own-a-component\}

5단계는 어떤 값으로도 표현할 수 없는 구조, 부분, 상태 또는 동작의 변경을 위한 것입니다. 컴포넌트의 소스를 프로젝트로 복사해 그곳에서 편집합니다.

다음 중 하나라도 해당되면 컴포넌트를 소유하세요. 그 전까지는 1~4단계에 머무르세요.

- 변경에 스타일시트에 없는 선택자가 필요합니다: 다른 부분, 다른 중첩, 다른 요소.
- 원하는 상태 표현을 테마 토큰이나 컴포넌트의 공개 속성으로 표현할 수 없습니다.
- 변경이 동작에 관한 것입니다: 키, 포커스, 선택의 의미.
- 프로젝트가 이 컴포넌트의 구현을 독립적으로 유지 관리해야 합니다. 테마 값에 대한 통제만 필요하다면 대신 [로컬 테마를 유지하세요](/guide/stability#pin-the-theme).

### 소스 가져오기 \{#take-the-source\}

```bash
npx master-ui init      # once: writes ui/index.css with one @import per stylesheet
npx master-ui own menu  # copies ui/menu.css, ui/menu.json and its behavior; repoints the import
```

`init`은 `ui/index.css`와 `master-ui.json`을 작성합니다. 프리셋 다음에 `@import '@master/ui'` 대신 `ui/index.css`를 가져오세요.

```css name=app.css
@import '@master/css';
@import './ui/index.css';
```

그런 다음 `own`은 네 가지 일을 합니다.

| 하는 일 | 위치 |
| --- | --- |
| 스타일시트와 계약을 복사 | `ui/menu.css`, `ui/menu.json` |
| 계약에 동작이 명시된 경우 동작을 복사 | `ui/menu.js` |
| 가져온 시점의 각 파일 사본을 하나 더 보관 | `ui/.base/` |
| 컴포넌트와 각 파일의 해시를 기록 | `master-ui.json` |

또한 `ui/index.css`의 한 줄을 `@import '@master/ui/components/menu.css';`에서 `@import './menu.css';`로 바꿉니다. 프로젝트에 해당 줄이 없으면 `own`은 직접 바꿔야 할 내용을 출력합니다. `--force`를 전달하지 않는 한 `ui/`에 이미 있는 파일을 덮어쓰지 않습니다.

사본은 여전히 테마의 토큰을 읽고 믹스인을 적용하므로 테마를 따릅니다. 다른 모든 컴포넌트는 여전히 패키지에서 옵니다.

### 계약을 정확하게 유지하기 \{#keep-the-contract-true\}

복사된 계약 `ui/menu.json`은 CLI가 이 프로젝트의 설정을 읽을 때 라이브러리의 계약을 대체합니다. 에이전트도 이 로컬 계약을 읽어야 합니다. `ui/menu.css`에서 클래스를 추가, 이름 변경 또는 제거하면 `ui/menu.json`도 함께 바꾸세요. 다음은 스타일시트에 부분을 추가한 예와, 계약의 `classes` 배열에 덧붙일 항목입니다.

```css name=ui/menu.css
@layer components {
  /* A quiet line under the last group: the account that is signed in. */
  .menu-note {
    padding: .4375rem .5rem;
    color: var(--color-text-muted);
    font-size: .71875rem;
  }
}
```

```json name=ui/menu.json
{ "name": "menu-note", "kind": "part", "of": "menu", "description": "A quiet line under the last group" }
```

기존 클래스 이름과 상태 속성을 유지하면 블록, 동작, 문서가 계속 맞아떨어집니다. 모든 키는 [계약](/guide/contracts)에서 설명합니다.

새 부분을 사용하는 마크업에 대해 `npx master-ui check`를 실행한 다음, 브라우저에서 컴포넌트를 확인하세요. 검사기는 마크업 계약을 검증할 뿐, 복사한 CSS가 의도한 상태, 대비, 키보드 동작을 구현한다는 것을 증명하지는 않습니다.

### 업스트림 변경 따라가기 \{#upstream-changes\}

소유한 컴포넌트는 패키지가 업데이트되어도 더 이상 바뀌지 않습니다. 세 가지 명령으로 패키지가 무엇을 바꿨는지 확인하고 병합한 내용을 기록합니다.

```bash
npx master-ui status       # which owned components changed upstream since they were taken
npx master-ui diff menu    # the change, against the copy kept in ui/.base/
npx master-ui accept menu  # after merging what is wanted: record the new base
```

`status`는 소유한 컴포넌트마다 한 줄씩 출력하며, 그중 하나라도 업스트림에서 바뀌었다면 종료 코드 2로 종료하므로 예약된 작업이 이를 보고할 수 있습니다.

```
menu  upstream changed: menu.css (master-ui diff menu); edited here: menu.css
```

`diff`는 가져온 사본과 패키지의 현재 파일을 비교하므로, 프로젝트 자체의 편집과는 별개로 업스트림이 한 일만 보여 줍니다.

```
# menu.css: taken (-) and upstream now (+)
    .menu-label {
      padding: .4375rem .5rem .3125rem;
      color: var(--color-text-muted);
+     font-size: .71875rem;
-     font-size: .6875rem;
      user-select: none;
      -webkit-user-select: none;
    }
```

원하는 내용은 `ui/menu.css`에 직접 병합하세요. 그런 다음 `accept`는 패키지의 현재 버전을 기준으로 삼습니다. `ui/`의 사본은 건드리지 않습니다.

### 컴포넌트 되돌려 주기 \{#give-back\}

스타일시트 가져오기가 다시 패키지를 가리키도록 하고, 동작에 대한 애플리케이션이나 프레임워크의 가져오기를 `@master/ui/behaviors`로 복원하세요. `master-ui.json`의 `owned`에서 컴포넌트 항목을 제거하면 라이브러리의 계약이 다시 적용됩니다.

소유하거나 추가한 다른 컴포넌트가 더 이상 사용하지 않는 작업 파일과 기준 파일만 삭제하세요. 동작은 `ui/internal.js` 같은 복사된 헬퍼를 공유할 수 있으며, 프레임워크 컴포넌트는 로컬 동작을 가져올 수 있습니다. 파일을 제거하기 전에 이러한 가져오기를 확인한 다음, 빌드하고 되돌린 컴포넌트를 직접 사용해 보세요.

### 라이브러리의 상당 부분을 소유할 때 \{#own-all\}

로컬 사본을 패키지 스타일과 조율하는 것보다 프로젝트 전체에서 일관된 구현을 유지 관리하는 편이 더 쉬울 때 더 많은 소스를 소유하는 것을 고려하세요. 복사한 컴포넌트의 수만으로는 나머지를 떠맡을 이유가 되지 않습니다. 토큰, 계약, 검사기, [스킬](/guide/ai#the-skill)은 여전히 적용됩니다. 패키지와 레지스트리 워크플로의 비교는 [소스 소유하기](/guide/registry)를 참고하세요.

## 사용자 지정이 아닌 것 \{#what-is-not\}

다음 재정의는 결과를 바꿀 수는 있지만, 지원되는 사용자 지정 지점을 우회하며 대체한 구현을 추적할 책임을 사용자에게 남깁니다.

- **라이브러리 클래스를 선택해 그 면, 가장자리, 그림자를 다시 선언하는 규칙.** 토큰이나 속성을 사용하거나 컴포넌트를 소유하세요.
- **문서화되지 않은 컴포넌트 속성.** 계약에 나열된 속성이나 별도로 문서화된 테마 토큰을 사용하세요. 컴포넌트의 내부 속성은 예고 없이 바뀔 수 있습니다.
- **라이브러리 컴포넌트를 외부에서 다시 스타일링하는 새 클래스**, 예를 들어 재질 선언을 가진 `.my-btn.btn`. 프로젝트 클래스는 공개 속성과 레이아웃을 설정할 수 있습니다. 새로운 재질은 새로운 컴포넌트이거나 소유한 컴포넌트입니다.
- **힘으로 이기기.** 컴포넌트를 이기기 위해 명시도를 높이거나 `!important`를 사용하지 마세요. 유틸리티는 이미 레이어 덕분에 우선하며, 그 이상이 필요한 재정의는 컴포넌트를 소유해야 한다는 신호입니다.

```css name=app.css
/* Not a customization: it redraws what button.css draws, and will not follow it. */
.btn {
  background: white;
  box-shadow: 0 1px 2px rgb(0 0 0 / .2);
}
```
