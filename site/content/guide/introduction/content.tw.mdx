Master UI 為 HTML 介面提供一組共用的元件 class、設計 token 與記載於文件中的狀態。你撰寫原生標記，例如 `<button class="btn">`，並在伺服器樣板、React、Svelte 或 Vue 中使用相同的 class。套件提供 CSS、標記的契約，以及需要腳本的模式所用的腳本。

當你想保有對標記的掌控，同時在整個專案中共用元件的外觀與行為時，就可以使用它。你可以從預設的 moonstone 與 obsidian 主題開始，重新調整它的 token，或把某個元件的原始碼帶進你的專案。Master UI 仍處於實驗階段：[請固定安裝的版本並審視每次升級](/guide/stability#experimental)。

## 契約與實作 \{#a-contract-and-an-implementation\}

契約描述樣式表能理解的標記：class、元素、狀態屬性與公開的自訂屬性。它讓人與程式設計代理使用同一套詞彙，也提供檢查常見錯誤的方法。實作則提供實際的外觀與行為。

<GuideFigure name="introduction" title="標記、契約與實作">

**契約將標記與其實作連結起來。** 按鈕的 `btn` class 在 HTML 與 CSS 中指稱同一個介面。契約也描述元素、狀態屬性與公開屬性。更換主題會替換材質的值，而這些名稱依然可用。對於需要腳本的模式，輸入會改變屬性，再由 CSS 繪製對應的狀態。

</GuideFigure>

| 部分 | 提供什麼 | 如何使用 |
| --- | --- | --- |
| [契約](/guide/contracts) | 每個樣式表旁的 JSON 描述，包含一個正確的範例 | 撰寫標記前，先閱讀已安裝的契約 |
| 實作 | 繪製契約的樣式表 | 調整 [token、主題或你自己的副本](/guide/customization) |
| [行為](/guide/behaviors) | 參考腳本，供需要處理鍵盤、值或焦點的模式使用 | 直接掛上，或透過提供的框架元件掛上 |
| 檢查 | 針對檢查器能讀取的標記進行靜態診斷 | 在編輯後與 CI 中執行，再確認渲染後的介面 |

契約是封閉的：除非契約有寫，否則不存在 `btn-outline`，而照樣寫了的話，檢查器會回報它。實作是開放的：可以用 token 重新調整、用[主題](/guide/theming)替換它的材質，或把某個元件的原始碼帶進你的專案。token 與主題的變更不會破壞契約。如果你自己擁有某個元件並改變它的結構或狀態，請一併更新它的本地契約與使用它的地方。[搭配 AI 使用](/guide/ai)說明代理會讀取與執行哪些內容。

## 各部分如何配合 \{#how-it-fits-together\}

| 層 | 擁有者 | 範例 |
| --- | --- | --- |
| 設計 token | Master CSS 預設組與 `@master/ui/theme.css` | `--color-surface-raised`、`--shadow-raised` |
| 元件樣式 | `@master/ui` | `.btn`、`.btn-primary`、`.input` |
| 版面 class | `@master/ui` | `.page`、`.shell`、`.auto-grid`、`.form` |
| 局部調整 | 你的標記 | `w-full`、`mt-md`、`px-lg` |

元件 class 位於 `components` 層，utility 位於較後的 `utilities` 層，因此單一實例上的 utility 一定會生效，不需要 `!important` 或選擇器技巧：

```html
<button type="button" class="btn btn-primary w-full">Save changes</button>
```

## 元件、版面、區塊與頁面 \{#tiers\}

這個元件庫分為四個層級，從一個部件到一整個畫面。區分它們的不是大小，而是是否有值得放在 class 背後的知識。

| 層級 | 它是什麼 | 如何發布 |
| --- | --- | --- |
| [元件](/components) | 具有材質、狀態、平台行為，或其各部件共用之幾何的部件 | `@master/ui` 中的語意 class |
| [版面](/components#layouts) | 區域內的空間如何安排：堆疊、自動格線、bento、masonry、讓圖片突出的欄 | utility，以及在 utility 無法表達時使用的版面 class。它們與元件列在一起 |
| [區塊](/blocks) | 頁面中具有目的的一段：主視覺、價格表、頁尾 | 可複製的標記：由元件與 utility 組成 |
| [頁面](/pages) | 一整個畫面：它的區域放在哪裡、哪些部分會捲動 | 可複製的標記，建立在 `page` 與 `shell` 兩種框架之一上 |

當一樣東西至少具備以下四種知識之一時，才值得擁有一個 class：

1. **材質。** 必須位於材質階梯上的表面、輪廓、陰影或圓角。
2. **狀態。** 懸停、焦點、選取、開啟、停用或無效，從原生屬性或 ARIA 讀取。
3. **平台行為。** 錨點定位、捲動狀態查詢、進入頂層：utility 寫不出來的東西。
4. **其各部件共用的幾何。** 依內縮量巢狀的圓角、尺寸隨容器而變的子元素。

按鈕結合了材質、狀態與幾何。由分欄連結組成的頁尾不需要新的元件 class：它是以 utility 建構的區塊。由此得出三條規則。

- **元件不擁有頁面。** 它從不決定自己的位置，除非位置本身就是它的行為：導覽列會固定，對話框會進入頂層。
- **版面不擁有材質。** 它決定區域與捲動；這些區域中的表面是 sheet、tray 與卡片。
- **擁有 class 的門檻是知識，而不是重複。** 重複的標記用複製的，而不是為它命名。

少數版面包含 utility 無法表達的內容，例如以 `dvh` 表示的高度、手機的安全區域、容器門檻值或格線軌道清單。這些就是版面 class：兩種框架 [`page`](/pages/page) 與 [`shell`](/pages/app-shell)，以及 [`auto-grid`](/components/auto-grid)、[`bento`](/components/bento)、[`masonry`](/components/masonry)、[`breakout`](/components/breakout)、[`sticky-stack`](/components/sticky-stack) 與 [`form`](/components/form)。

## 原則 \{#principles\}

- **原生元素優先。** 元件使用本來就具有正確語意的元素，並盡可能保留其原生行為。若某個模式沒有原生元素，樣式表會從 ARIA 繪製它的狀態，並[由一小段腳本改變這些狀態](#patterns-that-need-a-script)。
- **平台先於腳本。** 瀏覽器現在已能自行做到的事，元件不會重新實作。請參閱下方的[平台](#the-platform)。
- **光線，而非裝飾。** 凸起的表面會捕捉一道光，並落在短而漸淡的陰影上；凹槽則沉於周圍之下。狀態以深度而非顏色表現，邊緣柔和。請參閱[預設主題](/guide/theme)。
- **使用 token，而非寫死的值。** 表面、線條、高度層次、圓角與動態都來自主題 token，若元件自行寫入顏色，測試就會失敗；覆寫一次 token，即可重新調整所有元件。
- **精簡的公開詞彙。** 一個基礎 class、少數修飾 class（例如 `btn-primary` 與 `btn-sm`），以及記載於文件中的自訂屬性（例如 `--btn-height`）。
- **一份樣式表兼顧淺色與深色。** 語意 token 透過 `light-dark()` 解析，跟隨頁面的色彩配置。

## 平台 \{#the-platform\}

原生元素會處理它們本來就支援的工作：核取方塊儲存勾選的值，下拉選單參與表單，而強制回應對話框會讓背後的頁面變為 inert。Master UI 為它們的屬性與狀態設定樣式。

樣式表仍有一個瀏覽器基準。串接層、巢狀與 `light-dark()` 等功能是必要的；錨點定位與連續曲率圓角等選用功能，則是在可運作的基準上加以強化。有些備援方式需要應用程式的程式碼：不支援 invoker commands 的瀏覽器，需要一個呼叫 `dialog.showModal()` 的點擊處理函式。

請閱讀[瀏覽器支援](/guide/browser-support)，了解基準、強化功能的備援方式，以及如何測試你的應用程式所使用的功能。元件頁面會在範例旁註明相關的備援方式。

## 需要腳本的模式 \{#patterns-that-need-a-script\}

少數模式目前還沒有原生元素：[combobox](/components/combobox)、[命令面板](/components/command)、[日曆](/components/calendar)、以方向鍵瀏覽的[樹狀結構](/components/tree)、[右鍵選單](/components/menu#context-menu)、會自行跳到下一格的 [OTP 欄位](/components/otp)、在兩個窗格之間拖曳的[分隔條](/components/splitter)，以及就地切換面板的[分頁](/components/tabs#tab-panels)。Master UI 仍為它們各自提供一份樣式表。分工方式每次都相同：

- **樣式表從 ARIA 繪製每個狀態**：`aria-selected` 表示目前作用中的選項，`aria-checked` 表示已選取的選項，`aria-expanded` 表示展開的分支，`aria-current="date"` 表示今天，`aria-orientation` 表示分隔條的方向。它也負責放置表面並為其加上動畫，並以 `:has()` 推導它能推導的狀態，例如空狀態。
- **腳本處理輸入並更新狀態。** 套件附帶參考[行為](/guide/behaviors)，並以其契約列出的按鍵進行測試。它們會更新原生屬性與 ARIA 屬性；指標位置或其他 CSS 無法推導的值，可以透過自訂屬性傳入。材質與定位規則則由 CSS 負責。
- **只要有原生容器，就使用原生容器。** 命令面板是由 `command="show-modal"` 開啟的 `<dialog>`；日期選擇器的日曆放在 `popover` 中；不使用腳本的樹狀結構則是巢狀的 `<details>`。

依照這些屬性撰寫的標記就是契約，因此無論由誰渲染都能持續運作：樣板、框架元件，或代理。

## 在 React、Svelte 與 Vue 中 \{#in-a-framework\}

在框架中，元件庫的大部分內容與在一般頁面上相同：原生元素上的 class，以框架自己的語法撰寫。只是把 `btn btn-primary` 換個名字的 `<Button>` 毫無助益，還會讓[檢查器](/guide/ai#check-the-markup)看不到這個 class。

只有在框架擁有某些東西時，才會有框架元件：應用程式讀取或設定的值、由資料渲染的列、將兩個部分連結起來的 id，或生命週期。例子包括上述的模式、由狀態開啟的對話框、toast 佇列，以及附帶標籤與錯誤訊息的欄位。每個框架元件都會渲染契約的標記並掛上行為，而行為仍留在套件中；元件本身則是你透過 `npx master-ui add combobox` 複製到專案中的原始碼。[React、Svelte 與 Vue](/guide/frameworks) 列出了這些元件。

## 這個 alpha 版發布的內容 \{#what-comes-next\}

契約、樣式表、行為、第二個主題、檢查器、可複製原始碼的[登錄庫](/guide/registry)，以及用於具有狀態之模式的 React、Svelte 與 Vue 元件。框架元件以原始碼形式隨 `@master/ui` 發布，而不是另外的綁定套件。共用的互動邏輯留在行為中；每個框架元件各自處理自己的渲染與生命週期。[穩定性](/guide/stability)說明哪些是公開的、哪些可能變動。
