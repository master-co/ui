Master UI 為 HTML 介面提供一套共用的元件類別、設計 token，以及有文件說明的狀態。你可以撰寫 `<button class="btn">` 等原生 HTML 標記，並在伺服器端範本、React、Svelte 或 Vue 中使用同一套類別。套件提供 CSS、標記契約，以及特定介面模式所需的腳本。

如果你想自行掌控標記，同時讓整個專案共用元件的外觀與行為，就可以使用 Master UI。你可以從採用 moonstone 與 obsidian 的預設主題開始，調整主題的 token，或將元件的原始程式碼納入專案。Master UI 目前仍在實驗階段，請[鎖定安裝版本並檢查升級內容](/guide/stability#experimental)。

## 契約與實作 \{#a-contract-and-an-implementation\}

契約說明樣式表能辨識哪些標記，包括類別、元素、狀態屬性與公開自訂屬性。開發者和 AI 代理可以使用同一套詞彙，並依契約檢查常見錯誤。實作則提供實際的外觀與行為。

<GuideFigure name="introduction" title="標記、契約與實作">

**契約將標記與實作連結起來。** 按鈕的 `btn` 類別在 HTML 和 CSS 中都指向同一個介面。契約也說明元素、狀態屬性和公開自訂屬性。切換主題會替換材質設定值，原有名稱仍可使用。對於需要腳本的介面模式，輸入會改變屬性，再由 CSS 呈現對應的狀態。

</GuideFigure>

| 部分 | 提供內容 | 使用方式 |
| --- | --- | --- |
| [契約](/guide/contracts) | 每份樣式表隨附的 JSON 說明，內含正確的標記範例 | 撰寫標記前，先閱讀已安裝版本的契約 |
| 實作 | 呈現契約所定義介面的樣式表 | 調整 [token、主題或你自己的副本](/guide/customization) |
| [行為](/guide/behaviors) | 為需要處理鍵盤操作、值或焦點的介面模式提供參考腳本 | 直接接上腳本，或透過套件提供的框架元件使用 |
| 檢查 | 對檢查器能讀取的標記提供靜態診斷 | 修改後及在 CI 中執行檢查，再確認實際呈現的介面 |

契約的範圍是封閉的：只有契約明訂時才能使用 `btn-outline`，否則寫了就會被檢查器指出。實作可自由調整：你可以調整 token、用[主題](/guide/theming)替換材質設定，或將元件的原始程式碼納入專案。調整 token 或主題時，契約維持不變。如果你自行維護元件並變更了它的結構或狀態，請一併更新專案內的契約及使用該元件的程式碼。[與 AI 協作](/guide/ai)說明代理會讀取哪些內容、執行哪些操作。

## 各層如何配合 \{#how-it-fits-together\}

| 層級 | 維護方 | 範例 |
| --- | --- | --- |
| 設計 token | Master CSS 預設組態與 `@master/ui/theme.css` | `--color-surface-raised`, `--shadow-raised` |
| 元件樣式 | `@master/ui` | `.btn`, `.btn-primary`, `.input` |
| 版面配置類別 | `@master/ui` | `.page`, `.shell`, `.auto-grid`, `.form` |
| 局部調整 | 你的標記 | `w-full`, `mt-md`, `px-lg` |

元件類別位於 `components` 層，utility 位於順序較後的 `utilities` 層。因此，在個別元件實例上套用 utility 時，該 utility 的樣式一律優先，無須使用 `!important` 或任何選擇器技巧：

```html
<button type="button" class="btn btn-primary w-full">Save changes</button>
```

## 元件、版面配置、區塊與頁面 \{#tiers\}

這套函式庫從單一部件到完整畫面分為四個層級。大小並非劃分依據，關鍵在於是否有值得封裝進類別的設計規則。

| 層級 | 定義 | 發布形式 |
| --- | --- | --- |
| [元件](/components) | 具備材質、狀態、平台行為，或各部分共用幾何規則的部件 | `@master/ui` 中的語意類別 |
| [版面配置](/components#layouts) | 區域內部的空間安排，例如堆疊、自動網格、便當盒版面、瀑布流，或允許插圖超出欄寬的欄配置 | 以 utility 提供。utility 無法表達時，則提供版面配置類別。版面配置與元件一同列出 |
| [區塊](/blocks) | 頁面上有特定用途的一段內容，例如主視覺區、定價表或頁尾 | 可複製的標記，由元件與 utility 組成 |
| [頁面](/pages) | 完整畫面，定義各區域的位置及哪些區域可以捲動 | 可複製的標記，採用 `page` 和 `shell` 兩種框架之一 |

只要具備以下四種設計特性之一，就值得定義一個類別：

1. **材質。** 表面、輪廓、陰影或圓角必須符合材質的層級規則。
2. **狀態。** 從原生屬性或 ARIA 讀取游標懸停、焦點、選取、開啟、停用或無效等狀態。
3. **平台行為。** 例如錨點定位、捲動狀態查詢，或讓元素進入頂層。這些行為無法用 utility 表達。
4. **各部分共用的幾何規則。** 例如依內縮距離調整的內外圓角，或隨容器調整尺寸的子元素。

按鈕結合材質、狀態與各部分共用的幾何規則。由多欄連結組成的頁尾，用 utility 就能組成區塊，無須新增元件類別。以下是三條規則。

- **元件不主導頁面。** 元件不會指定自己在頁面上的位置，除非定位本身就是它的行為。例如，導覽列會吸附在指定位置，對話框會進入頂層。
- **版面配置不決定材質。** 它負責劃分區域並決定如何捲動。區域中的表面由面板、托盤與卡片等元件呈現。
- **只有封裝特定知識，才值得新增類別。** 重複的標記直接複製即可，無須另取名稱。

少數版面配置包含 utility 無法表達的資訊，例如以 `dvh` 表示的高度、手機的安全區域、容器查詢的門檻，或一組網格軌道。這些就是版面配置類別，包括 [`page`](/pages/page) 和 [`shell`](/pages/app-shell) 兩個框架，以及 [`auto-grid`](/components/auto-grid)、[`bento`](/components/bento)、[`masonry`](/components/masonry)、[`breakout`](/components/breakout)、[`sticky-stack`](/components/sticky-stack) 和 [`form`](/components/form)。

## 設計原則 \{#principles\}

- **優先採用原生元素。** 元件選用語意相符的元素，並盡可能保留其原生行為。如果某種互動模式沒有對應的原生元素，樣式表就依 ARIA 屬性呈現狀態，再由[一小段腳本更新狀態](#patterns-that-need-a-script)。
- **優先使用瀏覽器原生功能。** 瀏覽器已能自行處理的功能，元件無須重做。請參閱下方的[瀏覽器平台](#the-platform)。
- **用光影呈現層次。** 凸起的表面邊緣帶有一道高光，下方是短而漸淡的陰影。凹槽則低於周圍表面。狀態以表面的浮起或凹陷程度區分，邊緣也保持柔和。請參閱[預設主題](/guide/theme)。
- **樣式值統一取自主題 token。** 表面、線條、高度層次、圓角和動態效果都由主題 token 提供。元件若自行指定顏色，就無法通過測試。覆寫一次 token，就能同步調整所有元件。
- **精簡公開介面。** 公開介面包含一個基礎類別、少數修飾類別（如 `btn-primary` 和 `btn-sm`），以及文件中列出的自訂屬性（如 `--btn-height`）。
- **一份樣式表支援淺色與深色。** 語意 token 透過 `light-dark()` 依頁面的淺色或深色色彩配置取值。

## 瀏覽器平台 \{#the-platform\}

原生元素各自處理已支援的功能。核取方塊會保存勾選狀態，下拉式選單可參與表單運作，模態對話框會停用背景頁面的互動。Master UI 依這些元素的屬性與狀態套用樣式。

樣式表仍有最低瀏覽器支援要求。瀏覽器必須支援串疊層、巢狀規則和 `light-dark()` 等功能。錨點定位與連續曲率圓角等選用功能則在可正常運作的基礎上提供增強效果。部分備援做法需要應用程式碼。例如，瀏覽器若不支援觸發指令，就需要在點擊事件處理函式中呼叫 `dialog.showModal()`。

請參閱[瀏覽器支援](/guide/browser-support)，了解最低支援要求、增強功能的備援做法，以及如何測試應用程式用到的功能。各元件頁面會在範例旁標明適用的備援做法。

## 需要腳本的互動模式 \{#patterns-that-need-a-script\}

有些互動模式還沒有對應的原生元素，例如[組合方塊](/components/combobox)、[指令面板](/components/command)、[月曆](/components/calendar)、可用方向鍵瀏覽的[樹狀清單](/components/tree)、[操作選單](/components/menu#context-menu)、會自動跳到下一格的[一次性密碼欄位](/components/otp)、可在兩個窗格之間拖曳的[分隔器](/components/splitter)，以及能在原處切換面板的[分頁標籤](/components/tabs#tab-panels)。Master UI 仍為每種模式各提供一份樣式表，分工方式也一致。

- **樣式表依 ARIA 屬性呈現各種狀態**。`aria-selected` 表示目前作用中的選項，`aria-checked` 表示已選取的選項，`aria-expanded` 表示已展開的分支，`aria-current="date"` 表示今天，`aria-orientation` 表示分隔器的方向。樣式表也負責表面的定位與動畫，並透過 `:has()` 判斷可由 CSS 推導的狀態，例如內容是否為空。
- **腳本處理輸入並更新狀態。** 套件提供可供參考的[行為](/guide/behaviors)實作，並依各自契約列出的按鍵進行測試。這些實作會更新原生屬性與 ARIA 屬性。指標位置或其他 CSS 無法推導的值，可透過自訂屬性傳入。材質與定位規則由 CSS 負責。
- **有適用的原生元素時，就用它作為容器。** 指令面板使用 `<dialog>`，並由 `command="show-modal"` 開啟。日期選擇器的月曆放在 `popover` 內。沒有腳本的樹狀清單則使用巢狀的 `<details>`。

依這些屬性撰寫的標記就是契約。無論由範本、框架元件還是代理產生，標記都能照常運作。

## 在 React、Svelte 和 Vue 中使用 \{#in-a-framework\}

這個函式庫的大部分用法在框架和一般頁面中都相同，只要用框架自己的語法，在原生元素上加上類別即可。如果 `<Button>` 只是替 `btn btn-primary` 換個名稱，既沒有增加功能，也會讓[檢查工具](/guide/ai#check-the-markup)看不到該類別。

只有需要由框架負責的事項，才值得建立框架元件，例如管理由應用程式讀取或設定的值、依資料產生列、用 ID 串接不同部分，或管理生命週期。上述互動模式、依狀態開啟的對話框、短暫通知佇列，以及帶有標籤和錯誤訊息的欄位，都屬於這類情況。每個元件都會產生符合契約的標記，並接上套件提供的行為。元件本身以原始碼提供，可用 `npx master-ui add combobox` 複製到專案中。完整清單請見 [React、Svelte 和 Vue](/guide/frameworks)。

## 這個 alpha 版包含什麼 \{#what-comes-next\}

這個版本提供契約、樣式表、行為、第二套主題、檢查工具、供複製原始碼的[登錄庫](/guide/registry)，以及為需要管理狀態的互動模式提供的 React、Svelte 和 Vue 元件。框架元件統一以原始碼放在 `@master/ui` 中，無須為各框架安裝個別的繫結套件。共用的互動邏輯由行為實作負責，各框架元件各自處理畫面呈現與生命週期。請參閱[穩定性](/guide/stability)，了解哪些項目屬於公開介面，以及哪些可能變更。
