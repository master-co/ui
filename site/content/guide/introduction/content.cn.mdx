Master UI 为 HTML 界面提供一套通用的组件类名和设计令牌，并记录组件支持的状态。你可以编写 `<button class="btn">` 这样的原生标记，在服务端模板、React、Svelte 或 Vue 中沿用同一个类名。软件包提供 CSS、标记契约，以及部分交互需要的行为脚本。

如果希望自己决定标记如何编写，同时在整个项目中统一组件外观和行为，可以从默认的 moonstone 和 obsidian 主题开始。你可以调整令牌，也可以把单个组件的源码纳入自己的项目。Master UI 仍处于实验阶段，请[锁定安装版本，每次升级前检查变更](/guide/stability#experimental)。

## 契约与实现 \{#a-contract-and-an-implementation\}

契约规定样式表支持哪些类名、元素、状态属性和公开的自定义属性。开发者和编程智能体可以用同一套术语编写标记，并依据契约检查常见错误。实现负责呈现组件的外观和行为。

<GuideFigure name="introduction" title="标记、契约与实现">

**契约将标记与实现衔接起来。** 按钮的 `btn` 类名在 HTML 和 CSS 中指代同一个接口。契约也规定元素、状态属性和公开属性。切换主题时，材质取值会变，这些名称仍可使用。遇到需要脚本的交互，脚本响应输入并更新属性，CSS 根据属性呈现状态。

</GuideFigure>

| 部分 | 提供什么 | 如何使用 |
| --- | --- | --- |
| [契约](/guide/contracts) | 每份样式表旁的 JSON 说明，内含一个符合契约的示例 | 编写标记前，先查看已安装版本的契约 |
| 实现 | 按契约渲染组件的样式表 | [调整令牌、更换主题或修改源码副本](/guide/customization) |
| [行为脚本](/guide/behaviors) | 供需要处理键盘、值或焦点的交互使用的参考实现 | 直接绑定到标记，或使用配套的框架组件 |
| 检查 | 对检查器能读取的标记给出静态诊断 | 编辑后和 CI 中运行检查，再验证渲染结果 |

只有契约声明的名称才有效。例如，只有契约声明了 `btn-outline`，才能使用这个类名。若在未声明时使用，检查器就会报错。实现则可以调整：覆盖令牌、用[主题](/guide/theming)更换材质，或把组件源码纳入项目。令牌和主题的调整兼容原有契约。如果接管组件后改了结构或状态，请同时更新本地契约和使用它的代码。[与 AI 协作](/guide/ai)说明智能体会读取什么、运行什么。

## 各层如何配合 \{#how-it-fits-together\}

| 层级 | 来源 | 示例 |
| --- | --- | --- |
| 设计令牌 | Master CSS 预设和 `@master/ui/theme.css` | `--color-surface-raised`、`--shadow-raised` |
| 组件样式 | `@master/ui` | `.btn`、`.btn-primary`、`.input` |
| 布局类 | `@master/ui` | `.page`、`.shell`、`.auto-grid`、`.form` |
| 局部调整 | 项目自己的标记 | `w-full`、`mt-md`、`px-lg` |

组件类位于 `components` 层，工具类位于层叠顺序更靠后的 `utilities` 层。因此，应用于单个实例的工具类始终优先于组件类，无需 `!important` 或选择器技巧：

```html
<button type="button" class="btn btn-primary w-full">Save changes</button>
```

## 组件、布局、区块和页面 \{#tiers\}

组件库分为四个层级，从局部部件到整个界面。判断依据是其中是否有值得用类封装的规则，尺寸并不影响这一判断。

| 层级 | 职责 | 提供形式 |
| --- | --- | --- |
| [组件](/components) | 封装材质、状态、平台行为或部件间的几何关系 | `@master/ui` 中的语义类 |
| [布局](/components#layouts) | 排列区域内部的内容，例如纵向堆叠、自动网格、便当网格、瀑布流，或允许插图伸出阅读栏 | 通常用工具类，工具类表达不了的规则由布局类提供。布局与组件列在同一个目录 |
| [区块](/blocks) | 完成页面某一段的任务，例如主视觉区、定价表或页脚 | 由组件和工具类组成的可复制标记 |
| [页面](/pages) | 组织整屏区域，确定各自的位置和滚动方式 | 基于 `page` 或 `shell` 框架的可复制标记 |

以下四种规则都可以成为定义一个类的理由：

1. **材质。** 面层、轮廓、阴影或圆角需要遵循统一的材质层级。
2. **状态。** 从原生属性或 ARIA 属性读取悬停、聚焦、选中、打开、禁用或无效等状态。
3. **平台行为。** 例如锚点定位、滚动状态查询或进入顶层，这些行为无法用工具类表达。
4. **部件之间的几何关系。** 例如根据内缩距离匹配的内外圆角，或尺寸随容器变化的子元素。

按钮结合了材质、状态和几何关系。分栏排布链接的页脚可直接用工具类组成一个区块，无需新增组件类。由此得出以下三条规则。

- **组件只在位置本身属于其行为时决定自身位置。** 例如导航栏的粘性定位和对话框进入顶层。
- **布局安排区域及其滚动方式。** 区域中的面板、托盘和卡片各自提供材质。
- **定义类的依据是有规则需要封装。** 仅仅重复出现的标记直接复制即可，无需为它命名。

少数布局需要工具类无法表达的规则，例如以 `dvh` 计算高度、处理手机安全区、设置容器阈值或列出网格轨道。这些规则由布局类实现，包括两个页面框架 [`page`](/pages/page) 和 [`shell`](/pages/app-shell)，以及 [`auto-grid`](/components/auto-grid)、[`bento`](/components/bento)、[`masonry`](/components/masonry)、[`breakout`](/components/breakout)、[`sticky-stack`](/components/sticky-stack) 和 [`form`](/components/form)。

## 设计与实现原则 \{#principles\}

- **优先使用原生元素。** 选择语义合适的元素，尽量保留原生行为。没有合适的原生元素时，样式表根据 ARIA 属性呈现状态，由[简短的脚本更新属性](#patterns-that-need-a-script)。
- **把浏览器能做的事交给浏览器。** 组件无需重新实现浏览器已支持的行为。详见[浏览器原生能力](#the-platform)。
- **光影用于呈现层次。** 凸起表面的边缘有一道高光，下方的阴影短而渐隐。凹槽低于周围表面。状态通过高低层次区分，无需改变颜色。边缘保持柔和。参见[默认主题](/guide/theme)。
- **用令牌统一取值。** 表面、线条、表面高度、圆角和动效的取值都来自主题令牌。组件中若硬编码颜色，测试就会失败。覆盖一处令牌，就能调整所有读取它的组件。
- **精简公开接口。** 每个组件有一个基础类、少量修饰类（例如 `btn-primary`、`btn-sm`）和有文档说明的自定义属性（例如 `--btn-height`）。
- **一份样式表支持浅色和深色。** 语义令牌通过 `light-dark()` 随页面配色方案取值。

## 浏览器原生能力 \{#the-platform\}

原生元素继续承担内建行为：复选框保存选中状态，下拉选择框参与表单，模态对话框打开时禁止与背景页面交互。Master UI 根据这些元素的属性和状态添加样式。

浏览器需要支持层叠层、CSS 嵌套和 `light-dark()` 等基础特性。锚点定位、连续曲率圆角等特性则用于渐进增强。某些回退方案需要应用代码。例如浏览器不支持调用器命令时，需要在点击处理函数中调用 `dialog.showModal()`。

[浏览器支持](/guide/browser-support)列出了基础要求、增强特性的回退方案，以及如何测试应用用到的特性。各组件页面也会在示例旁注明相关回退方案。

## 哪些交互需要脚本 \{#patterns-that-need-a-script\}

有些交互目前没有适用的原生元素，例如[组合框](/components/combobox)、[命令面板](/components/command)、[日历](/components/calendar)、可用方向键浏览的[树形控件](/components/tree)、[上下文菜单](/components/menu#context-menu)、自动跳到下一格的 [OTP 输入框](/components/otp)、可拖动调整两侧窗格的[分隔条](/components/splitter)，以及在原位切换面板的[标签页](/components/tabs#tab-panels)。Master UI 为每一种交互提供独立的样式表，并按以下方式分工：

- **样式表根据 ARIA 属性呈现各个交互状态。** `aria-selected` 表示当前选项，`aria-checked` 表示勾选，`aria-expanded` 表示展开的分支，`aria-current="date"` 表示当天，`aria-orientation` 指定分隔条的方向。CSS 也负责表面的定位和动画，并用 `:has()` 判断可以直接从标记得出的状态，例如内容为空。
- **脚本处理输入并更新状态。** 软件包提供参考[行为脚本](/guide/behaviors)，按契约列出的键盘操作进行测试。脚本更新原生属性和 ARIA 属性；指针位置等 CSS 无法自行推导的值可以通过自定义属性传入。材质和定位规则由 CSS 负责。
- **有合适的原生容器就使用它。** 命令面板使用由 `command="show-modal"` 打开的 `<dialog>`，日期选择器把日历放在 `popover` 中，树形控件的无脚本版本使用嵌套的 `<details>`。

按这些属性编写的标记就是契约。无论由模板、框架组件还是编程智能体渲染，符合契约的标记都能正常工作。

## 在 React、Svelte 和 Vue 中使用 \{#in-a-framework\}

大多数组件在框架中的用法与纯 HTML 相同。按框架自己的语法，把类名加在原生元素上即可。如果 `<Button>` 只是给 `btn btn-primary` 换了个名字，就没有增加任何功能，还会让[检查器](/guide/ai#check-the-markup)看不到实际类名。

只有框架需要负责管理应用读取或设置的值、根据数据渲染行、通过 ID 关联部件，或管理生命周期时，才提供框架组件。除了上面提到的交互，例子还包括由状态控制的对话框、轻提示队列和带标签及错误信息的字段。框架组件按契约渲染标记，再绑定软件包中的行为脚本。组件源码可以用 `npx master-ui add combobox` 这样的命令复制到项目中。完整列表见 [React、Svelte 和 Vue](/guide/frameworks)。

## Alpha 版提供的内容 \{#what-comes-next\}

这个版本提供契约、样式表、行为脚本、第二套主题、检查器、用于复制源码的[注册表](/guide/registry)，以及需要管理状态的 React、Svelte 和 Vue 组件。框架组件以源码随 `@master/ui` 发布，无需单独的框架绑定包。通用交互逻辑留在行为脚本里，框架组件负责各自的渲染和生命周期。[稳定性](/guide/stability)说明哪些接口已公开、哪些内容可能变化。
