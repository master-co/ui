Master UI의 디자인 언어는 표면, 형태, 상태를 조화롭게 구성해 영역의 경계와 위계, 상호작용을 시각적으로 드러냅니다. 이 가이드에서는 이러한 설계의 근거를 설명합니다. [Master Design](https://design.master.co/principles)에서는 일반 원칙을 다루고, [기본 테마](/guide/theme)에서는 실제 구현에 쓰이는 디자인 토큰과 표면 표현 방식을 설명합니다.

## 프로젝트별 담당 범위 \{#ownership\}

| 프로젝트 | 담당 범위 | 담당 범위 밖 |
| --- | --- | --- |
| Master Design | 일반 디자인 원칙, 기초 요소, 패턴, 검증 방법 | 별도의 런타임 스타일시트나 컴포넌트 API |
| Master UI | 자체 디자인 언어와 지침, 컴포넌트 계약, 테마, 재사용 가능한 스타일, 동작, 구현 예제 | 제품별 콘텐츠, 라우팅, 애플리케이션 데이터 |
| Master CSS | 스타일 구문, 컴파일, 런타임 스타일 제공, 범용 프리셋의 기본 요소 | 제품별 상호작용 설계 결정 |
| Master | 브랜드 및 생태계 웹사이트, 공식 사이트 공통 셸, 게시 인프라 | 별도의 재사용 컴포넌트 라이브러리 |

사용자는 재사용 가능한 UI 표현에 Master UI를 쓰고, 개별 화면의 스타일을 조합하는 데 Master CSS를 씁니다. 사이트 셸은 탐색 메뉴, 문서, 사이트 고유의 화면 표현을 한데 묶습니다. 디자인은 문서를 통해 구현에 반영되며 런타임 의존성을 만들지 않습니다.

## 네이티브 동작과 명시적 계약 \{#native-behavior-and-explicit-contracts\}

네이티브 요소와 실제 상태를 나타내는 속성부터 사용하세요. Master UI 클래스는 지원되는 마크업을 나타내며, 컴포넌트 계약은 외부에 공개된 부분과 상태를 명시합니다. 외형을 지정하는 클래스만으로는 빠진 키보드 동작이 구현되지 않습니다. 패턴에 별도 동작이 필요하면 함께 제공되는 동작을 쓰거나 프레임워크 통합에서 필요한 동작을 모두 구현하세요.

비슷한 라이브러리를 참고해 임의로 수정자를 만들지 마세요. 마크업을 작성하기 전에 최신 컴포넌트 계약을 읽고, 작성한 뒤에는 UI 검사기를 실행하고 렌더링된 화면에서 상호작용을 테스트하세요. 정적 검사만으로는 포커스, 스크린 리더 안내, 시각적 대비가 적절한지 확인할 수 없습니다.

## Moonstone과 Obsidian \{#moonstone-and-obsidian\}

기본 표면 표현은 밝은 모드에 **Moonstone**, 어두운 모드에 **Obsidian**을 사용합니다. 두 모드는 중성적인 zinc 색조를 공유하고, 위쪽에서 약간 왼쪽에 있는 가상의 광원을 일관되게 적용합니다. Moonstone은 표면의 은은한 명암 변화, 가는 윤곽선, 짧게 퍼지며 옅어지는 그림자로 옅은 진줏빛을 표현합니다. Obsidian은 채움색의 명도를 단계적으로 조절하고, 빛이 닿는 부분을 은은하게 강조하며, 가장자리를 뚜렷하게 드러내 어두운 표면을 구분합니다. Moonstone의 색상을 단순히 반전하면 이러한 구분이 사라집니다.

영역의 경계와 상호작용을 쉽게 알아볼 수 있게 하면서 장식색이 콘텐츠에서 시선을 빼앗지 않도록 합니다. 일반 표면은 중성적인 빛과 깊이로 구분하고, 상태는 의미가 지정된 색상으로 전달하며, 화면에서 중요한 순간에는 브랜드 강조색을 선별적으로 사용합니다. 이는 Master UI의 기본값이며, 다른 프로젝트의 시각적 정체성에 적용해야 할 요구 사항은 아닙니다. 표면 표현을 절제하더라도 필요한 필드, 동작, 레이어는 쉽게 찾을 수 있어야 합니다.

같은 페이지에 돌출된 버튼, 필드, 열린 메뉴를 놓고 밝은 모드와 어두운 모드에서 각각 확인하세요. 메뉴는 뒤의 콘텐츠와 구분되어야 하고, 필드는 포커스를 받기 전에도 알아볼 수 있어야 하며, 강조를 낮춘 텍스트도 실제로 표시되는 표면 위에서 읽을 수 있어야 합니다. 실제 렌더링 크기와 사용 환경의 디스플레이 픽셀 밀도에서 가는 윤곽선을 확인하세요. 장식용 가장자리가 보인다는 사실만으로는 필수 컨트롤 경계가 대비 요구 사항을 충족한다고 판단할 수 없습니다. [기본 테마](/guide/theme)는 실제 구현에 쓰이는 표면 표현, [선의 역할](/guide/theme#lines), [텍스트의 역할](/guide/theme#text)을 정의합니다.

## 표면 단계별 역할 선택 \{#choose-a-role-on-the-material-ladder\}

표면이 하는 일에 맞춰 역할을 고르고, 구체적인 외형은 테마에 맡기세요. 표면의 단계는 서로의 관계를 나타내며, 컨테이너가 안쪽에 중첩될 때마다 더 밝아지거나 더 높아져야 한다는 규칙은 없습니다.

| 역할 | 설계 목적 | 화면에서 확인할 사항 |
| --- | --- | --- |
| 기본 캔버스 | 섹션마다 별도의 컨테이너로 감싸지 않고 페이지 전체의 바탕을 마련합니다. | 장식용 컨테이너를 제거해도 읽는 순서가 명확합니다. |
| 트레이 | 서로 관련된 표면 뒤에 오목한 받침을 둡니다. | 받침은 관련 표면을 한데 묶으면서 그 표면들보다 두드러지지 않습니다. |
| 돌출된 표면 | 경계가 있는 콘텐츠나 조작할 수 있는 면을 표시합니다. | 가장자리가 바로 주변과 구분되면서 오버레이처럼 보이지 않습니다. |
| 오목한 영역 | 편집 가능한 필드, 트랙, 여러 항목을 담는 영역의 경계를 드러냅니다. | 호버하기 전에도 영역을 찾을 수 있고, 포커스 상태와 유효하지 않은 상태를 서로 구분할 수 있습니다. |
| 떠 있는 표면 | 메뉴나 팝오버를 그 아래에 겹치는 콘텐츠와 구분합니다. | 밝거나 어두운 콘텐츠 위에서도 경계가 뚜렷하게 보이고 잘리지 않습니다. |
| 반전 잉크 | 주요 동작이나 선택 표시를 시각적으로 강조합니다. | 라벨과 작은 표시도 충분한 대비를 유지합니다. 반전 잉크 영역이 여러 곳에서 두드러지더라도 주된 작업은 쉽게 알아볼 수 있습니다. |

모달에는 배경막과 플랫폼에서 제공하는 레이어 동작도 필요합니다. 그림자는 쌓임 순서를 정하거나 배경과의 상호작용을 차단하지 않습니다. 표면을 돌출시킨다고 해서 클릭할 수 있게 되는 것은 아니므로, 요소의 의미와 라벨, 지원되는 상태 표현으로 수행할 수 있는 동작을 전달하세요. 현재 계약과 값은 [표면 구현](/components/surface), [표면 역할](/guide/theme#surfaces), [높이 역할](/guide/theme#elevation), [반전 잉크](/guide/theme#ink)를 참고하세요.

## 동심 구조와 연속 곡률 모서리 \{#concentric-geometry-and-continuous-corners\}

중첩된 가장자리는 서로 일정한 간격을 유지해야 합니다. 바깥쪽 받침의 모서리는 안쪽 컨트롤의 모서리와 둘 사이의 간격을 기준으로 정합니다. 반대로 안쪽으로 들어간 자식 요소의 모서리는 이를 감싸는 표면을 기준으로 정합니다. 이렇게 하면 굽은 부분에서도 간격이 시각적으로 고르게 유지됩니다. 안팎에 간격이 있는데 두 가장자리에 같은 반경을 적용하면, 각각의 반경은 따로 볼 때 괜찮더라도 모서리에서 간격이 좁아지거나 불룩해 보입니다.

Master UI는 이 관계를 트레이와 돌출된 표면, 세그먼트 트랙과 그 안의 선택된 옵션, 입력 그룹 안의 버튼, 카드 안의 미디어에 적용합니다. 안쪽 간격, 모서리 역할, 컴포넌트 크기를 함께 조정하세요. 스크린샷에서 우연히 맞아 보일 때까지 하위 요소 하나의 모서리만 둥글게 조정해 안팎의 불일치를 해결하지 마세요. 손잡이나 아바타처럼 완전한 원형 요소는 자체 형태를 유지합니다.

브라우저가 지원하는 경우 연속 곡률 모서리는 직선에서 곡선으로 이어지는 부분을 부드럽게 표현합니다. 테마는 모서리의 형태와 시각적인 둥글기를 함께 조정합니다. 원호 모서리 폴백도 자연스러워 보여야 하며, 콘텐츠가 차지하는 영역은 그대로 유지해야 합니다. 연속 곡률은 표면 표현을 위한 선택이며, 접근성이나 올바른 동작을 위한 필수 조건은 아닙니다.

지원되는 각 크기에서 선택된 세그먼트와 입력 그룹 버튼 둘레의 간격을 확인하세요. 밝은 모드와 어두운 모드에서 모두 확인하고, 모서리 폴백을 적용한 경우도 점검하세요. 안쪽 간격은 시각적으로 고르게 유지되어야 하며, 텍스트와 포커스 표시가 잘리면 안 됩니다. [형태 구현](/guide/theme#shape), [세그먼트 컨트롤](/components/segmented), [입력 그룹](/components/input), [카드](/components/card)를 참고하세요. 형태를 정하는 기하학적 근거는 [기하 구조](https://design.master.co/craft/geometry)를 참고하세요.

## 배치를 유지하는 컨트롤의 상태 피드백 \{#state-feedback-on-a-stable-control\}

기본 표면 표현에서는 평상시 컨트롤이 주변보다 살짝 높아 보입니다. 호버를 지원하는 포인터로 호버하면 가장자리가 더 뚜렷해지고 표면이 더 떠 보이며, 누르면 오목한 면처럼 들어가 보입니다. 이 변화는 컨트롤이 레이아웃에서 차지하는 영역을 그대로 유지하면서 입력이 반영되었음을 알려 줍니다. 색상 변화에만 의존해 상태를 구분하지 마세요. 터치 환경에서도 호버 없이 가능한 동작을 알아볼 수 있어야 합니다.

포커스, 선택, 누름, 유효성 검사, 사용 가능 여부를 각각 별개의 정보로 다루세요. 포커스는 다음 키보드 입력을 받을 위치를 나타내고, 선택된 세그먼트나 체크 표시는 유지되는 값을 나타냅니다. 유효하지 않은 필드에도 포커스가 놓일 수 있습니다. 처리 중인 동작에는 진행 상태를 명시적으로 표시해야 하며, 애플리케이션과 연동할 때 의도치 않은 중복 제출을 방지해야 합니다. 비활성화된 것처럼 보이게 하는 스타일만으로는 실제 비활성화 동작이 구현되지 않습니다.

포인터로 누르기와 떼기, 입력 취소, 키보드로 활성화, 선택과 포커스가 겹친 상태, 유효하지 않으면서 포커스를 받은 상태, 비활성화 상태, 처리 중 상태를 확인하세요. 사용자 값과 라벨은 그대로 유지되고 레이아웃은 갑자기 움직이지 않아야 하며, 포커스 표시가 표면 표현에 묻혀서는 안 됩니다. 동작 줄이기가 활성화되어 있으면 표면이 떠오르거나 크기가 변하지 않아도 상태를 알아볼 수 있어야 합니다. 강제 색상 모드에서는 장식용 그림자가 사라져도 필수 경계와 선택 상태를 확인할 수 있어야 합니다. [버튼 계약](/components/button), [선택 컨트롤](/components/segmented), [모션 구현](/guide/theme#motion), [동작 담당 범위](/guide/behaviors)를 참고하세요.

## Paper 테마의 표면 표현 \{#paper-demonstrates-a-different-material\}

**Paper**는 동일한 컴포넌트 계약을 따르는 대안 테마입니다. 기본 테마의 방향성 있는 빛 대신 따뜻한 중성색, 평평한 면, 선으로 그은 가장자리, 반경이 더 작은 원호 모서리를 사용합니다. 공통 높이 설정에 따라 호버하거나 눌러도 표면이 떠오르거나 가라앉지 않으며, 스위치 손잡이가 위치를 바꾸는 것처럼 상태를 전달하는 움직임은 유지됩니다. 메뉴와 대화 상자에는 깊이감을 은은하게 남겨 둡니다. 가장자리의 선만으로는 어느 표면이 위에 겹쳐 있는지 충분히 드러나지 않을 수 있기 때문입니다.

Paper는 컴포넌트에서 재사용하는 것이 Moonstone 특유의 마감이 아니라 구조와 동작, 서로 맞물리는 역할임을 보여 줍니다. 그라데이션과 하이라이트를 없애면 테두리선과 채움의 차이가 각 역할을 구분하는 데 더 중요해집니다. 모든 역할에 같은 표면을 적용하면 일관된 플랫 테마가 되는 대신 시각적 위계가 사라집니다.

Paper와 기본 테마에서 같은 버튼, 입력 필드, 선택된 컨트롤, 반전된 표면, 열린 오버레이를 비교하세요. 마크업, 접근성 이름, 값의 소유권, 키보드 동작은 같아야 합니다. Paper의 두 색상 모드 모두에서 경계와 포커스, 동시에 적용되는 상태를 알아볼 수 있어야 하며, 동작 줄이기와 강제 색상도 계속 적용됩니다. 기준은 [Paper 구현 및 미리 보기](/guide/theming#paper)와 [테마 레시피](/guide/theming#recipes)에 있으며, 이 가이드에서는 디자인 토큰 표를 별도로 제공하지 않습니다.

## 사용자 지정 범위 \{#customization-boundaries\}

재질 전반을 바꾸려면 의미적 역할을 변경하세요. 특정 컴포넌트에 지원되는 변형을 적용하려면 문서에 명시된 컴포넌트 사용자 지정 속성을 변경하고, 페이지 배치만 바꾸려면 해당 페이지의 구성 방식을 조정하세요. 완성된 테마에서는 표면, 그 위의 전경색, 테두리선, 깊이, 모서리, 상태 표현이 서로 조화를 이룹니다. 배경만 바꾸면 그 위에 표현된 요소 간의 관계가 모두 어긋날 수 있습니다.

테마는 디자인 토큰과 공통 재질 레시피를 제공합니다. 개별 컴포넌트의 구조를 다시 정의하는 선택자가 테마에 쌓이지 않도록 하세요. Paper는 주로 디자인 토큰을 사용하며, 컨트롤 자체의 색상에 따라 표면이 달라지는 색조형 컨트롤에는 레시피를 재정의합니다. 디자인 토큰은 런타임에 적용 범위를 제한할 수 있습니다. 레시피 정의는 컴파일 시 확정되며 빌드에 영향을 줍니다. 특정 영역에만 예외를 적용하려면 이 차이를 고려해야 합니다.

사용자 지정 시 문서에 공개된 컴포넌트 파트와 네이티브 시맨틱을 유지하세요. 스크린샷을 깔끔하게 보이게 하려고 포커스나 선택 표시를 없애거나, 브랜드 색상만으로 오류를 알리거나, 컨트롤을 시각적으로 줄여도 조작 대상 영역이 충분하다고 가정하지 마세요. 모서리 형태를 바꿀 때는 그 형태에 맞는 크기 체계를 함께 적용하고, 모션을 바꿀 때도 상태 변화를 알아볼 수 있어야 합니다. 라벨, 데이터, 유효성 검사, 문서에 명시된 컴포넌트 동작 범위 밖의 포커스 흐름은 애플리케이션에서 계속 관리합니다.

재정의를 적용하기 전에 대표적인 버튼, 입력 필드, 중첩된 컨트롤, 오버레이에 실제 콘텐츠와 더 긴 라벨을 넣고 키보드로 조작해 보세요. 두 색상 모드와 대비 높이기, 동작 줄이기, 강제 색상을 모두 확인하세요. [사용자 지정](/guide/customization), [테마 규칙](/guide/theming#rules), [계약](/guide/contracts), [브라우저 지원](/guide/browser-support)을 참고하고, 각 문서에 명시된 최신 API와 지원 범위를 기준으로 삼으세요.

## 컴포넌트, 레이아웃, 블록, 페이지 \{#components-layouts-and-blocks\}

컴포넌트의 파트들이 재질, 상태, 플랫폼 동작 또는 형태와 치수를 서로 맞춰야 할 때 공통 계약이 필요합니다. 레이아웃은 영역 안의 공간을 배치하며, 영역의 재질은 별도로 정합니다. 기본 레이아웃 요소는 [컴포넌트](/components#layouts) 목록에 있습니다. [블록](/blocks)은 컴포넌트와 레이아웃을 조합해 페이지의 특정 구간을 구성합니다. [페이지](/pages)는 `page` 또는 `shell` 프레임 위에 화면 전체를 구성하고 영역과 스크롤 방식을 정의합니다.

사이트 전용 문구나 한 번만 쓰는 히어로 섹션 배치를 범용 컴포넌트로 만들지 마세요. 재사용 가능한 대화 상자, 버튼, 입력 필드는 사이트 셸에서 따로 구현하지 마세요. 어댑터는 사이트 구성과 호환성에 실제로 필요한 범위로 제한하세요.

## 설계 지침과 구현 \{#guideline-to-implementation\}

| 설계 항목 | Master UI 참고 문서 | 적용 환경의 검증 항목 |
| --- | --- | --- |
| 의미적 색상, 표면, 깊이 | [기본 테마](/guide/theme) 및 [테마 적용](/guide/theming) | 두 색상 모드에서 실제로 맞닿는 표면의 대비 |
| 타이포그래피, 간격, 치수, 재정의 | [사용자 지정](/guide/customization) | 긴 콘텐츠, 배치 밀도, 텍스트 크기 조절, 조작 대상 영역의 범위 |
| 마크업, 파트, 상태 | [계약](/guide/contracts) | 네이티브 시맨틱과 동시에 적용되는 상태 |
| 키보드 조작, 값 처리, 포커스 동작 | [동작](/guide/behaviors) | 전체 입력 순서, 종료 시 정리, 포커스 복귀 |
| 런타임 및 폴백 요구 사항 | [브라우저 지원](/guide/browser-support) | 지원 브라우저, 선택적 개선 기능, 실제로 사용할 수 있는 폴백 |
| 프레임워크 통합 | [프레임워크](/guide/frameworks) | 값의 소유권, 생명 주기, 중복 초기화 |

위 링크는 각 항목의 구현을 어디에서 관리하는지 안내합니다. 가능한 모든 구성의 검증을 보장하지는 않습니다. 현재 제공되는 컴포넌트와 예제는 [Master UI 카탈로그](/components)에서 확인하세요. 제안 단계의 패턴은 계약, 동작, 검증 근거가 마련되기 전까지 지원되는 컨트롤로 소개하지 마세요.

## 변경 사항 공동 검토 \{#review-a-change-together\}

관련 설계 원칙과 사용 지침을 먼저 확인하세요. Master UI에서 구현을 변경한 뒤 실제로 사용하는 대표 페이지에서 검증하세요. 의도한 동작이 달라지면 문서도 갱신하세요. 소스, 예제, 계약, 테스트를 서로 일치시키세요. 스크린샷만으로 접근성을 포괄적으로 보장한다고 주장하지 말고, 브라우저와 보조 기술에서 확인한 제약을 기록하세요.
