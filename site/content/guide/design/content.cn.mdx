Master UI 的设计语言通过协调一致的表面、几何形状和状态，让包含关系、层级和交互清晰可见。本指南解释这些选择。[Master Design](https://design.master.co/principles) 介绍通用原则；[默认主题](/guide/theme)记录了可执行的令牌和材质配方。

## 职责归属 \{#ownership\}

| 项目 | 负责 | 不负责 |
| --- | --- | --- |
| Master Design | 通用设计原则、基础、模式和验证方法 | 第二套运行时样式表或组件 API |
| Master UI | 自身的设计语言与指南、组件契约、主题、可复用样式、行为和实现示例 | 产品特有的内容、路由或应用数据 |
| Master CSS | 样式语法、编译、运行时交付和通用预设原语 | 产品的交互决策 |
| Master | 品牌与生态网站、共享的官方站点外壳和发布基础设施 | 另一套平行的可复用组件库 |

使用方用 Master UI 实现可复用的呈现，用 Master CSS 进行局部组合。站点外壳负责组织导航、文档和站点特有的呈现。设计通过文档影响这些实现，而不是通过运行时依赖。

## 原生行为与明确的契约 \{#native-behavior-and-explicit-contracts\}

从原生元素及其实际的状态属性开始。Master UI 的 class 描述受支持的标记；它的契约记录公开的部件和状态。视觉 class 不会补上缺失的键盘行为。当模式需要时，请使用随附的行为或完整的框架集成。

不要照搬类似库的修饰符。编写标记之前先阅读当前的组件契约，然后运行 UI 检查器，并测试渲染后的交互。静态检查无法证明焦点、播报或视觉对比度没有问题。

## Moonstone 与 Obsidian \{#moonstone-and-obsidian\}

默认材质在浅色外观中使用 **Moonstone**，在深色外观中使用 **Obsidian**。两者共用一套中性的锌色色彩词汇，并设想同一个位于上方略偏左的光源。Moonstone 通过表面上克制的变化、精细的轮廓和短而渐隐的阴影，呈现出淡淡的珍珠质感。Obsidian 通过填充层级、受控的高光和清晰可辨的边缘来区分深色表面；简单地反转 Moonstone 的颜色会失去这种区分。

其目的是让包含关系和交互清晰易读，同时不让装饰性的颜色与内容争夺注意力。中性的光影和深度用来标识普通表面；语义色调传达状态，而刻意使用的品牌强调色则标识视图中的关键时刻。这些是 Master UI 的默认设计，并不是对其他项目视觉识别的要求。只有当相关的字段、操作或层级仍然容易找到时，低调的材质才算成功。

在两种外观下，于同一页面中检查一个凸起的按钮、一个字段和一个打开的菜单。菜单必须与其后方的内容区分开，字段在获得焦点之前必须仍可辨认，弱化文字在其实际所在的表面上必须仍然可读。请以实际渲染尺寸和相关的显示密度检查细轮廓；装饰性的边缘并不能证明关键控件的边界满足对比度要求。可执行的材质、[线条角色](/guide/theme#lines)和[文字角色](/guide/theme#text)由[默认主题](/guide/theme)负责。

## 在材质阶梯上选择角色 \{#choose-a-role-on-the-material-ladder\}

根据表面的用途选择表面，再让主题决定其外观。这个阶梯表达的是相互关系，而不是规定每一层嵌套容器都必须更亮或更高。

| 角色 | 设计目的 | 可观察的检查点 |
| --- | --- | --- |
| 基础画布 | 承载页面，而不是把每个区块都框起来 | 去掉装饰性容器后，阅读顺序仍然清晰 |
| 托盘 | 将承载容器凹陷在相关面板之后 | 承载容器有助于分组，但不会与其包含的面板争夺注意力 |
| 凸起面板 | 呈现一段有边界的内容或一个可操作的面 | 其边缘与紧邻的周围区分开，又不会看起来像浮层 |
| 凹槽 | 让可编辑字段、轨道或集合区域呈现为被包含的状态 | 用户无需悬停就能找到该区域；焦点和无效状态仍然清晰可分 |
| 浮动表面 | 将菜单或弹出层与其覆盖的内容区分开 | 其边界在浅色和深色内容之上都清晰可读，并且不会被裁切 |
| 反色墨色 | 赋予主要操作或选中标记很强的视觉分量 | 标签和较小的标记保持对比度；多个相互竞争的反色区域不会掩盖主要任务 |

模态框还需要其背景遮罩和平台的层叠行为。阴影并不能建立堆叠顺序，也不能阻止与背景的交互。同样，凸起面板并不会自动变得可点击：请通过语义、标签和受支持的状态处理来传达操作。当前的契约和数值请参阅[表面实现](/components/surface)、[表面角色](/guide/theme#surfaces)、[层级高度角色](/guide/theme#elevation)和[反色墨色](/guide/theme#ink)。

## 同心几何与连续曲率圆角 \{#concentric-geometry-and-continuous-corners\}

嵌套的边缘应描述同一种关系。承载容器的圆角由内部控件及两者之间的间距推导而来；内嵌子元素的圆角则由外层表面推导而来。这样，间隙在转弯处也能保持视觉上的均匀。如果存在内缩却让两条边缘使用相同的半径，即使每个半径单独看都可以接受，转角处也会显得收紧或鼓胀。

Master UI 将这种关系应用于托盘与面板、分段轨道与其选中选项、输入组中的按钮，以及卡片中的媒体。请把内缩距离、圆角角色和组件尺寸一起协调。一对边缘不匹配时，不要只调整某个孤立后代元素的圆角，直到截图碰巧看起来没问题为止。滑块和头像等真正的圆形保持各自的几何形状。

在浏览器支持时，连续曲率圆角会让直边与弯曲之间的过渡更加柔和。主题负责协调圆角形状和视觉上的圆润程度；圆形回退方案也必须看起来是有意为之，并保持相同的内容边界。连续曲率是一种材质选择，而不是无障碍或正确性的要求。

在每种受支持的尺寸下、两种外观中，以及使用圆角回退方案时，检查选中分段周围和输入组按钮周围的间隙。内缩应保持视觉上的均匀；文字和焦点指示器不得被裁切。请参阅[形状实现](/guide/theme#shape)、[分段控件](/components/segmented)、[输入组](/components/input)和[卡片](/components/card)。底层的几何原理请参阅[几何](https://design.master.co/craft/geometry)。

## 在稳定控件上的状态反馈 \{#state-feedback-on-a-stable-control\}

在默认材质中，静止状态呈现为凸起；在支持悬停的指针设备上，悬停会加强表面的边缘和抬升；按下时则下沉为内凹的面。这种变化确认了输入，同时不会改变控件在布局中占据的空间。不应只靠颜色变化来传达这种区别，并且在触摸设备上，悬停不能是发现操作的唯一方式。

将焦点、选中、按下、验证和可用性视为相互独立的信息。焦点标识下一次键盘输入的去向；选中的分段或勾选标记标识持久的值。无效的字段同样可以获得焦点。忙碌中的操作需要明确的进度反馈，其应用集成也必须防止意外的重复提交。仅有禁用的视觉处理，并不等于实现了禁用行为。

检查指针按下与松开、取消、键盘激活、选中且获得焦点、无效且获得焦点、禁用和忙碌等状态。用户的值和标签应保持稳定，布局不应跳动，焦点也不能隐没在材质之下。在减少动态效果时，即使没有抬升或缩放，状态也必须仍可辨认。在强制颜色模式下，即使失去装饰性的阴影，关键边界和选中状态也必须保留。请参阅[按钮契约](/components/button)、[选择控件](/components/segmented)、[动效实现](/guide/theme#motion)和[行为归属](/guide/behaviors)。

## Paper 展示了另一种材质 \{#paper-demonstrates-a-different-material\}

**Paper** 是在相同组件契约之上的另一套主题。它以温暖的中性色、平面的表面、细线边缘和更紧凑的圆形圆角，取代默认的方向性光照。悬停和按下不再通过共享的抬升设置上浮或下沉；有意义的组件运动（例如开关滑块改变位置）仍然保留。菜单和对话框保留了克制的深度提示，因为仅靠细线边缘未必能说明重叠关系。

Paper 表明，可复用组件的本质是其结构、行为和协调一致的角色，而不是 Moonstone 那种特定的表面处理。去掉渐变和高光后，更多的责任落在线条和填充的差异上。把每个角色都压平成同样的表面，只会消除层级，而不会形成连贯的扁平主题。

在 Paper 和默认主题中比较同样的按钮、字段、选中的控件、反色面板和打开的浮层。标记、无障碍名称、值的归属和键盘行为都应保持不变。在 Paper 的两种配色方案中，边界、焦点和同时存在的多种状态都必须清晰可见；减少动态效果和强制颜色模式同样适用。请以 [Paper 的实现与预览](/guide/theming#paper)和[主题配方](/guide/theming#recipes)为准，本指南不另设一份令牌表。

## 自定义的边界 \{#customization-boundaries\}

当整个材质需要改变时，修改语义角色；当某个组件需要受支持的变化时，修改有文档记录的组件自定义属性；当只有页面的排布需要改变时，使用局部组合。完整的主题会协调表面、其上的前景墨色、线条、深度、圆角和状态处理。单独修改背景，可能会让其上绘制的所有关系失效。

主题提供令牌和共享的材质配方；它不应不断累积改写单个组件结构的选择器。Paper 主要使用令牌，另有一个配方覆盖，用于表面取决于控件自身色相的带色调控件。令牌可以在运行时限定作用域；配方定义则在编译期间解析，并影响构建结果。当某个拟议的例外只应作用于一个区域时，这一区别就很重要。

自定义时请保留已公开的部件和原生语义。不要为了让截图更安静而移除焦点或选中状态，不要把品牌色当作唯一的错误提示，也不要以为视觉上更小的控件仍然拥有足够的点击目标。改变圆角形状需要同步调整与之协调的缩放比例；改变动效时必须保留易于理解的状态反馈。超出组件文档所述行为的标签、数据、验证和焦点流程，仍由应用负责。

在采用某项覆盖之前，请用真实内容、键盘输入和较长的标签，实际操作一个具有代表性的按钮、字段、嵌套控件和浮层。检查两种配色方案、增强对比度、减少动态效果和强制颜色模式。请参阅[自定义](/guide/customization)、[主题规则](/guide/theming#rules)、[契约](/guide/contracts)和[浏览器支持](/guide/browser-support)；以它们当前的 API 和支持限制为准。

## 组件、布局、区块与页面 \{#components-layouts-and-blocks\}

组件之所以拥有共享的契约，是因为它具备材质、状态、平台行为，或其各部分必须协调的几何形状。布局负责排布区域内的空间，但不负责其材质；布局原语与[组件](/components#layouts)列在一起。[区块](/blocks)将组件和布局组合成页面中的一段具体内容。[页面](/pages)在 `page` 或 `shell` 框架上组合出整个屏幕，定义其区域和滚动方式。

不要把站点文案或一次性的主视觉排布提升为通用组件。反过来，可复用的对话框、按钮或字段，也不应在站点外壳中再有第二套实现。适配层应仅限于实际的站点组合和兼容性需求。

## 一并审查变更 \{#review-a-change-together\}

先从相关的基础和用法指南开始。在 Master UI 中修改实现，然后验证一个具有代表性的使用方页面。当预期行为发生变化时，更新文档。保持源码、示例、契约和测试一致；记录浏览器和辅助技术方面的限制，而不是把一张截图变成笼统的无障碍声明。
