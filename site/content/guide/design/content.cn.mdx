Master UI 的设计语言通过协调表面、几何形状和状态，让内容的归属、视觉层级和交互方式清晰可辨。本指南解释这些设计选择。[Master Design](https://design.master.co/principles) 介绍通用原则，[默认主题](/guide/theme) 则记录可直接使用的令牌和材质配方。

## 职责分工 \{#ownership\}

| 项目 | 负责 | 不负责 |
| --- | --- | --- |
| Master Design | 通用设计原则、设计基础、设计模式和验证方法 | 另建一套运行时样式表或组件 API |
| Master UI | 自身的设计语言和指南、组件契约、主题、可复用样式、行为和实现示例 | 特定产品的内容、路由或应用数据 |
| Master CSS | 样式语法、编译、运行时交付和预设中的通用基础能力 | 具体产品的交互决策 |
| Master | 品牌及生态网站、官方站点共用的页面框架和发布基础设施 | 另建一套可复用的组件库 |

使用方借助 Master UI 复用界面呈现方式，并用 Master CSS 完成局部组合。站点框架整合导航、文档和站点特有的界面呈现。各项实现通过文档获得设计指导，无需引入运行时依赖。

## 原生行为与明确的契约 \{#native-behavior-and-explicit-contracts\}

从原生元素及其实际使用的状态属性入手。Master UI 的类说明支持哪些标记写法，契约则记录公开的组成部分和状态。视觉样式类无法补齐缺失的键盘行为。交互模式需要额外行为时，使用库随附的行为脚本或完整的框架集成。

不要参照类似的库自行编造修饰符。编写标记前先阅读当前的组件契约，再运行 UI 检查器并测试渲染后的交互。静态检查无法验证焦点、辅助技术播报或视觉对比度。

## Moonstone 与 Obsidian \{#moonstone-and-obsidian\}

默认材质在浅色外观下使用 **Moonstone**，在深色外观下使用 **Obsidian**。两者共用一套中性的 zinc 色阶，设定的光源都位于上方略偏左。Moonstone 通过面上轻微的明暗变化、纤细的轮廓和短而渐隐的阴影，呈现浅色珍珠般的质感。Obsidian 用深浅分级的填充、克制的高光和清晰可辨的边缘区分深色表面。直接反转 Moonstone 的颜色会让这些表面难以区分。

这些设计让分组关系和交互清晰可辨，同时让内容保持视觉主导。中性的光照和层次标识普通表面，语义色传达状态，有针对性地使用品牌强调色，可以突出视图中的关键时刻。这些是 Master UI 的默认设计，各项目可以保留自己的视觉识别。材质再低调，也必须让相关字段、操作或层级易于找到。

在同一页面的浅色和深色外观下，检查凸起的按钮、字段和展开的菜单。菜单必须与后方内容清楚区分，字段在聚焦前就必须可辨认，弱化文本在实际所在的表面上也必须清晰可读。按实际渲染尺寸，在相关的显示像素密度下检查细轮廓。关键控件边界是否满足对比度要求，需要单独验证，不能仅凭装饰性边缘判断。[默认主题](/guide/theme) 定义可直接使用的材质、[线条角色](/guide/theme#lines)和[文本角色](/guide/theme#text)。

## 在材质层级中选择角色 \{#choose-a-role-on-the-material-ladder\}

按用途选择表面，由主题决定其外观。材质层级用于表达表面之间的关系，嵌套容器无须逐层变亮或抬高。

| 角色 | 设计目的 | 如何验证 |
| --- | --- | --- |
| 基础底面 | 承载整个页面，无须为每个区段都加上容器 | 去掉装饰性容器后，阅读顺序依然清晰 |
| 托盘 | 在相关面板下方形成下凹的承托区域 | 容器将面板归为一组，同时让其中的面板保持视觉主导。 |
| 凸起面板 | 呈现边界明确的内容或可操作的表面。 | 边缘与紧邻的区域清晰区分，且不会让面板看起来像浮层。 |
| 凹槽 | 让可编辑字段、轨道或内容集合所在的区域有清晰的范围 | 用户在悬停前就能找到该区域，聚焦状态和无效状态也各自清晰可辨。 |
| 浮动表面 | 将菜单或弹出层与其覆盖的内容区分开。 | 边界在浅色和深色内容上都清晰可辨，且不会被裁切。 |
| 反色墨色 | 增强主要操作或选中标记的视觉分量。 | 标签和较小的标记保持足够的对比度，多个墨色区域同时出现时，主要任务仍然醒目。 |

模态界面还需要遮罩和平台提供的分层行为。阴影无法建立堆叠顺序，也无法阻止用户与背景交互。凸起面板的外观也无法赋予面板点击行为。用语义、标签和组件支持的状态样式表明它可以执行什么操作。当前的契约和值见[表面实现](/components/surface)、[表面角色](/guide/theme#surfaces)、[层次角色](/guide/theme#elevation)和[反色墨色](/guide/theme#ink)。

## 同心几何与连续曲率圆角 \{#concentric-geometry-and-continuous-corners\}

嵌套边缘应体现同一种几何关系。容器的圆角由内部控件的圆角及两者之间的间距决定，内嵌子元素的圆角则由包围它的表面决定。这样，间隙在转角处看起来也均匀。有内嵌间距时，如果两条边缘使用相同的圆角半径，即使各自看起来合适，组合起来也会让转角显得收紧或鼓起。

Master UI 将这一关系用于托盘及其中的面板、分段轨道及其选中项、输入组内的按钮，以及卡片内的媒体。让内嵌间距、圆角角色和组件尺寸彼此协调。不要为了让截图看起来合适，只调整某个后代元素的圆角来修补内外边缘的不匹配。滑块手柄和头像等正圆元素保留自身的几何形状。

浏览器支持连续曲率圆角时，直边过渡到弯角会更柔和。主题协调圆角形状和视觉上的圆润程度。使用圆弧作为回退方案时，圆角仍应与整体协调，并保持相同的内容边界。连续曲率是材质设计上的选择，无障碍和实现正确性均不以它为前提。

在每种受支持的尺寸下，检查选中分段和输入组按钮周围的间隙，覆盖两种外观及圆角回退方案。内嵌间距在视觉上应保持均匀，文字和焦点指示器都应完整可见。参阅[形状实现](/guide/theme#shape)、[分段控件](/components/segmented)、[输入组](/components/input)和[卡片](/components/card)。有关这一做法背后的几何原理，参阅[几何](https://design.master.co/craft/geometry)。

## 控件保持布局稳定时的状态反馈 \{#state-feedback-on-a-stable-control\}

在默认材质下，控件在常态下看起来略微凸起。对支持悬停的指针，悬停会让表面边缘更鲜明，抬升感更强。按下时，表面会向内下沉，趋于凹陷。这些变化确认用户的输入，同时保持控件占用的布局空间不变。结合颜色以外的线索区分状态，并确保触屏用户无需悬停也能发现可执行的操作。

分别传达聚焦、选中、按下、验证和可用性信息。焦点表明下一次键盘输入会作用在哪里，选中的分段或勾选标记则表明持续保留的值。无效字段也可以获得焦点。操作进行中时，需要明确反馈进度，应用集成也必须防止意外重复提交。禁用样式还需要配合实际的禁用行为。

检查指针按下和松开、取消操作、键盘激活、选中且聚焦、无效且聚焦、禁用和忙碌状态。用户的值和标签应保持稳定，布局应避免跳动，焦点指示器应始终清晰可见。启用减少动态效果时，即使没有抬升或缩放，状态也必须清晰可辨。在强制颜色模式下，即使装饰性阴影消失，关键边界和选中状态也必须清晰可辨。参阅[按钮契约](/components/button)、[选择控件](/components/segmented)、[动态效果实现](/guide/theme#motion)和[行为职责](/guide/behaviors)。

## Paper 展示另一种材质 \{#paper-demonstrates-a-different-material\}

**Paper** 是沿用同一套组件契约的另一款主题。它用暖中性色、平坦的表面、线条勾勒的边缘和更小的圆弧圆角取代默认主题的方向性光照。悬停和按下时，控件不再通过共用的抬升设置浮起或下沉。开关滑块移位等具有实际意义的组件运动仍会保留。菜单和对话框保留低调的层次提示，因为单靠边线有时难以看清叠放关系。

Paper 展示了组件可复用的部分在于结构、行为和相互配合的语义角色，外观则可以脱离 Moonstone 的具体质感。去掉渐变和高光后，更多层次关系由线条和填充的差异来体现。如果所有角色都采用同样的表面，视觉层级就会消失，平面主题也就失去了应有的区分。

对比 Paper 和默认主题中的同一个按钮、字段、选中控件、反色面板和已打开的浮层。两种主题应沿用相同的标记、无障碍名称、值的归属和键盘行为。Paper 的两种配色方案都必须清楚呈现边界、焦点和同时生效的状态，并继续支持减少动态效果和强制颜色。令牌和配方以 [Paper 实现和预览](/guide/theming#paper)及[主题配方](/guide/theming#recipes)为准，本指南不另列令牌表。

## 自定义的边界 \{#customization-boundaries\}

需要整体调整材质时，修改语义角色。需要为单个组件应用受支持的变体时，修改文档列出的组件自定义属性。只调整页面的排列时，在页面局部调整组合方式。完整的主题会协调表面、表面上的前景墨色、线条、层次、圆角和状态表现。单独更改背景，可能破坏其上呈现的所有视觉关系。

主题提供令牌和共享的材质配方，应避免堆积用于改写各个组件结构的选择器。Paper 主要使用令牌，并为一种表面取决于自身色相的带色控件覆盖了材质配方。令牌可以在运行时限定作用范围，配方定义则在编译时解析，会影响构建产物。评估一项例外是否应仅在某个区域生效时，需要区分这两种机制。

自定义时，保留已发布的组件部件和原生语义。即使希望截图更简洁，也要保留焦点和选中状态的提示。不要仅靠品牌色表达错误，视觉尺寸缩小后也要确认交互目标仍然足够大。改变圆角形状时，必须使用与该形状配套的缩放比例。改变动效时，保留清晰易懂的状态反馈。应用仍负责组件文档所述行为之外的标签、数据、验证和焦点流转。

采用覆盖方案前，用真实内容、键盘输入和较长的标签检验有代表性的按钮、字段、嵌套控件和浮层。检查两种配色方案，以及增强对比度、减少动态效果和强制颜色下的表现。查阅[自定义](/guide/customization)、[主题规则](/guide/theming#rules)、[契约](/guide/contracts)和[浏览器支持](/guide/browser-support)，以其中当前的 API 和支持范围为准。

## 组件、布局、区块与页面 \{#components-layouts-and-blocks\}

组件的共享契约建立在材质、状态、平台行为或各部件需要协调的几何关系上。布局负责安排区域内的空间，该区域的材质不由布局定义。布局基础项与[组件](/components#layouts)一同列出。[区块](/blocks)用组件和布局组成页面中承担具体用途的一段。[页面](/pages)在 `page` 或 `shell` 页面框架上组织完整屏幕，定义各个区域及其滚动方式。

不要把站点文案或仅用于一处的主视觉布局做成通用组件。可复用的对话框、按钮或字段应在站点外壳中沿用现有实现。只在站点组合和兼容性确有需要时使用适配层。

## 从设计准则到实现 \{#guideline-to-implementation\}

| 设计要点 | Master UI 参考资料 | 在使用方项目中验证 |

## 共同评审变更 \{#review-a-change-together\}

先查阅相关的设计基础和使用指南。在 Master UI 中修改实现，然后选取一个使用该实现的代表性页面进行验证。预期行为发生变化时，更新文档。保持源码、示例、契约和测试一致，记录浏览器和辅助技术的局限，避免仅凭截图对无障碍支持作出笼统判断。
