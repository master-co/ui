Master UI のデザイン言語では、面、形状、状態表示に一貫性を持たせることで、要素のまとまりや階層、操作に対する反応を視覚的に伝えます。このガイドでは、その設計上の選択を解説します。一般原則は [Master Design](https://design.master.co/principles) を、実装で使うトークンや質感のレシピは[既定のテーマ](/guide/theme)を参照してください。

## 各プロジェクトの責任範囲 \{#ownership\}

| プロジェクト | 担当範囲 | 担当範囲外 |
| --- | --- | --- |
| Master Design | デザインの一般原則、基盤、パターン、検証方法 | 別系統のランタイム用スタイルシートやコンポーネント API |
| Master UI | 独自のデザイン言語とガイドライン、コンポーネントのコントラクト、テーマ、再利用可能なスタイル、ビヘイビア、実装例 | 製品固有のコンテンツ、ルーティング、アプリケーションデータ |
| Master CSS | スタイルの記法、コンパイル、実行時の配信、汎用プリセットの基本要素 | 製品ごとのインタラクション設計 |
| Master | ブランドとエコシステムのウェブサイト、公式サイト共通のシェル、公開基盤 | 別系統の再利用可能なコンポーネントライブラリ |

利用側では、再利用可能な表示スタイルに Master UI を使い、個々の画面や要素の組み立てに Master CSS を使います。サイトシェルは、ナビゲーション、ドキュメント、サイト固有の表示を組み合わせます。デザイン上の方針はドキュメントを通じて実装に反映され、実行時の依存関係にはなりません。

## ネイティブのビヘイビアと明示的なコントラクト \{#native-behavior-and-explicit-contracts\}

まず、ネイティブ要素と、その状態を実際に表す属性を使います。Master UI のクラスは対応するマークアップを示し、コントラクトは公開されているパーツと状態を定義します。見た目を指定するクラスを付けるだけでは、キーボード操作は補えません。パターンに必要な場合は、同梱のビヘイビアを使うか、必要な操作をすべて実装したフレームワーク統合を使います。

類似のライブラリを参考に、未定義の修飾クラスを作らないでください。マークアップを書く前に現行のコンポーネントのコントラクトを読み、実装後は UI チェッカーを実行し、レンダリングした画面で操作を確認します。フォーカス、支援技術による読み上げ、見た目のコントラストは、静的チェックだけでは確認できません。

## Moonstone と Obsidian \{#moonstone-and-obsidian\}

既定の質感には、ライト表示に **Moonstone**、ダーク表示に **Obsidian** を使います。どちらもニュートラルな zinc の色調を用い、上方のやや左に光源がある想定で統一しています。Moonstone は、面の緩やかな明暗の変化、繊細な輪郭、すぐに薄れていく短い影で、淡い真珠のような質感を表現します。Obsidian は、塗りの明度差、控えめなハイライト、見分けやすい輪郭で暗い面同士を区別します。Moonstone の色を単純に反転するだけでは、この区別は失われます。

装飾の色がコンテンツより目立たないようにしながら、要素のまとまりや、操作できる箇所と操作に対する反応をわかりやすくするのが目的です。色味を抑えた光と奥行きで通常の面を区別し、意味を持つ色でステータスを伝え、ブランドカラーのアクセントで画面内の重要な箇所を示します。これらは Master UI の既定の方針であり、各プロジェクトのブランド表現に適用する必須条件ではありません。質感を控えめにしても、必要な入力欄、操作、レイヤーはすぐに見つけられる必要があります。

立体感のあるボタン、入力欄、開いたメニューを同じページに並べ、ライト表示とダーク表示の両方で確認します。メニューは背後のコンテンツと区別でき、入力欄はフォーカス前でも見分けられ、目立たせないテキストも実際に配置される面の上で読める必要があります。細い輪郭は、実際の表示サイズと対象となるディスプレイの画素密度で確認します。装飾的な縁が見えるだけでは、操作部品の識別に欠かせない境界がコントラスト要件を満たすとは判断できません。実装で使う質感の定義、[線の役割](/guide/theme#lines)、[テキストの役割](/guide/theme#text)は、[既定のテーマ](/guide/theme)で定めています。

## 質感の階層から役割を選ぶ \{#choose-a-role-on-the-material-ladder\}

サーフェスは役割に応じて選び、見た目はテーマに委ねます。この段階構成はサーフェス同士の関係を表します。入れ子にするたびにコンテナーを明るくしたり、浮き上がらせたりする必要はありません。

| 役割 | 設計上の目的 | 確認ポイント |
| --- | --- | --- |
| ベースキャンバス | セクションごとに囲いを設けず、ページ全体の土台にする | 装飾用のコンテナーを外しても、読む順序が明確か |
| トレイ | 関連するシートを一段くぼんだ面でまとめる | トレイがシートのまとまりを示し、中のシートより目立たないか |
| 隆起したシート | ひとまとまりのコンテンツや操作できる面を提示する | 輪郭が周囲から見分けられ、オーバーレイのように見えないか |
| くぼみ面 | 編集可能なフィールド、トラック、項目をまとめる領域の範囲を示す | ホバーする前から領域がわかり、フォーカス状態と入力エラー状態を区別できるか |
| 浮遊サーフェス | メニューやポップオーバーを、その下に重なるコンテンツから区別する | 明るいコンテンツの上でも暗いコンテンツの上でも輪郭が見え、途中で切れないか |
| 反転インク | 主要な操作や選択マークを強調する | ラベルや小さなマークのコントラストが保たれ、インクで強調された領域が複数あっても、主な作業が見分けられるか |

モーダルには、バックドロップとプラットフォームのレイヤー制御も必要です。影を付けるだけでは、重なり順の指定や背後のコンテンツへの操作の遮断はできません。同様に、シートを隆起させただけではクリック可能になりません。操作できることは、適切なセマンティクスとラベル、サポートされている状態表現で伝えます。現行のコントラクトと値は、[サーフェスの実装](/components/surface)、[サーフェスの役割](/guide/theme#surfaces)、[エレベーションの役割](/guide/theme#elevation)、[反転インク](/guide/theme#ink)を参照してください。

## 同心の輪郭と連続コーナー \{#concentric-geometry-and-continuous-corners\}

入れ子になった輪郭は、内外の間隔が一貫して見えるように設計します。外側の受け皿の角は、内側のコントロールの角と両者の間隔を基に決め、内側に収まる子要素の角は外側のサーフェスを基に決めます。こうすると、角に沿っても間隔が均等に見えます。間隔があるのに内外の角を同じ半径にすると、それぞれ単独では自然でも、重ねたときに角の間隔が詰まったり広がったりして見えます。

Master UI では、トレイとシート、セグメントのトラックと選択項目、入力グループ内のボタン、カード内のメディアにこの関係を適用します。内側の間隔、角の役割、コンポーネントのサイズはまとめて調整してください。内外の角が合わないときに、スクリーンショット上で整って見えるまで特定の子孫要素の角だけを丸めて調整しないでください。つまみやアバターなどの真円は、その形状を保ちます。

ブラウザーが対応している場合、連続コーナーは直線から曲線へのつながりを滑らかにします。テーマは角の形状と見た目の丸みを揃えます。円弧を使うフォールバックでも、角が自然に見え、コンテンツが収まる範囲が変わらないようにします。連続した曲率は質感を決めるための選択肢であり、アクセシビリティや正常な動作の必須条件ではありません。

選択中のセグメントと入力グループ内のボタンの周囲の間隔を、対応するすべてのサイズで、ライト表示とダーク表示の両方について確認してください。角のフォールバックを使った場合も同じ条件で確認します。内外の間隔は均等に見え、テキストやフォーカスインジケーターは途中で切れないようにします。[形状の実装](/guide/theme#shape)、[セグメントコントロール](/components/segmented)、[入力グループ](/components/input)、[カード](/components/card)を参照してください。形状の考え方は、[ジオメトリ](https://design.master.co/craft/geometry)で解説しています。

## 配置を変えずにコントロールの状態を伝える \{#state-feedback-on-a-stable-control\}

既定の質感では、通常時は面が一段高く見えます。ホバー可能なポインターでホバーすると輪郭が強調され、面がさらに浮き上がって見えます。押下すると面が沈み、くぼんで見えます。この変化で入力への反応を伝えながら、コントロールがレイアウト上で占める領域を保ちます。状態の違いを色の変化だけに頼らず、タッチ操作ではホバーしなくても操作できることがわかるようにします。

フォーカス、選択、押下、検証結果、操作可否は、それぞれ別の情報として扱います。フォーカスは次のキーボード入力の行き先を示し、選択中のセグメントやチェックマークは保持されている値を示します。入力エラーのあるフィールドにもフォーカスを当てられます。処理中の操作には進行状況を明示し、意図しない再送信をアプリケーション側で防ぐ必要があります。無効に見せるだけでは、操作は無効になりません。

ポインターでの押下と解放、操作のキャンセル、キーボードでの実行、選択とフォーカスが重なった状態、入力エラーとフォーカスが重なった状態、操作無効、処理中の各状態を確認してください。ユーザーの入力値とラベルは維持し、レイアウトがずれたり、質感の表現でフォーカスが見えなくなったりしないようにします。動きの軽減が有効な場合は、浮き上がりや拡大縮小がなくても状態を判別できる必要があります。強制カラーでは、装飾的な影がなくても、必要な輪郭や選択状態が見えるようにします。[ボタンのコントラクト](/components/button)、[選択コントロール](/components/segmented)、[モーションの実装](/guide/theme#motion)、[ビヘイビアの責務](/guide/behaviors)を参照してください。

## Paper で見る別の質感 \{#paper-demonstrates-a-different-material\}

**Paper** は、同じコンポーネントコントラクトを使う別のテーマです。既定テーマの方向性のある光の表現に代えて、暖色寄りのニュートラルカラー、フラットな面、罫線で示す輪郭、小さめの円弧で構成した角を使います。浮き上がりを制御する共通設定により、ホバーや押下で面が上下する表現はなくなります。スイッチのつまみが位置を変えるなど、意味のある動きは残ります。メニューやダイアログでは、罫線だけでは重なりが伝わらない場合があるため、控えめな奥行きの表現を残します。

Paper は、コンポーネントの構造、ビヘイビア、役割同士の対応関係が、Moonstone 固有の仕上げを変えても再利用できることを示しています。グラデーションやハイライトをなくすと、線や塗りの違いで役割を伝えることがより重要になります。統一感のあるフラットなテーマにも、役割を区別する視覚的な階層が必要です。すべての役割に同じ面を使うと、その階層が失われます。

同じボタン、フィールド、選択状態のコントロール、反転インクのシート、開いたオーバーレイを Paper と既定テーマで比較してください。マークアップ、アクセシブルな名前、値の管理主体、キーボード操作は、テーマを切り替えても同じであることを確認してください。Paper の両方のカラースキームで、輪郭とフォーカス、同時に成立する状態を判別できる必要があります。動きの軽減と強制カラーにも引き続き対応します。トークン表はこのガイドには再掲していません。参照先は、[Paper の実装とプレビュー](/guide/theming#paper)および[テーマレシピ](/guide/theming#recipes)です。

## カスタマイズの範囲 \{#customization-boundaries\}

質感全体を変える場合はセマンティックな役割を変更し、特定のコンポーネントだけに対応済みのバリエーションを適用する場合は、ドキュメントに記載されたコンポーネントのカスタムプロパティを使います。ページの配置だけを変える場合は、そのページの構成を調整します。テーマでは、サーフェスとその前景色、線、奥行き、角、状態表現を一貫して設計します。背景だけを変えると、その上の要素の視覚的な関係がすべて崩れることがあります。

テーマは、トークンと質感の共通レシピを提供します。個々のコンポーネントの構造を書き換えるセレクターを、テーマに追加し続ける設計は避けてください。Paper は主にトークンを使い、面の色が自身の色相に依存する色付きコントロール向けに、レシピを上書きします。トークンは実行時に適用範囲を限定できます。レシピの定義はコンパイル時に解決され、ビルド結果に反映されます。この違いは、例外を特定の領域だけに適用したい場合に重要です。

カスタマイズするときは、公開されているパーツとネイティブのセマンティクスを維持してください。スクリーンショットをすっきり見せるためにフォーカスや選択の表示を消したり、ブランドカラーだけでエラーを示したりしないでください。コントロールを小さくした場合は、操作領域が十分に確保されているか確認してください。角の形状を変える場合は対応するスケールも調整し、動きを変える場合は状態の変化が伝わるようにします。ラベル、データ、検証、コンポーネントの文書化されたビヘイビアを超えるフォーカスの流れは、引き続きアプリケーションが担います。

上書きを採用する前に、代表的なボタン、フィールド、入れ子のコントロール、オーバーレイを、実際のコンテンツと長めのラベルを使って表示し、キーボードで操作してください。両方のカラースキーム、コントラストの強調、動きの軽減、強制カラーを確認します。現行 API とサポート範囲については、[カスタマイズ](/guide/customization)、[テーマのルール](/guide/theming#rules)、[コントラクト](/guide/contracts)、[ブラウザーサポート](/guide/browser-support)を参照してください。

## コンポーネント、レイアウト、ブロック、ページ \{#components-layouts-and-blocks\}

質感、状態、プラットフォームのビヘイビア、形状などをパーツ間で調整する必要があるものは、共通のコントラクトを持つコンポーネントとして扱います。レイアウトは領域内の配置を担い、質感の指定はサーフェスに委ねます。基本となるレイアウトは[コンポーネント](/components#layouts)の一覧に掲載されています。[ブロック](/blocks)は、ページの特定の区画に向けてコンポーネントとレイアウトを組み合わせたものです。[ページ](/pages)は、`page` または `shell` のフレーム上で画面全体を構成し、領域とスクロールの仕組みを定義します。

サイト固有の文言や一度しか使わないヒーローの構成を、汎用コンポーネントにしないでください。再利用できるダイアログ、ボタン、フィールドを、サイトシェル側で重複して実装することも避けます。アダプターは、サイトの構成や互換性のために実際に必要な範囲に絞ります。

## 設計指針と実装の対応 \{#guideline-to-implementation\}

| 設計項目 | Master UI の参照先 | 利用側での確認項目 |
| --- | --- | --- |
| セマンティックカラー、サーフェス、奥行き | [既定テーマ](/guide/theme)と[テーマ設定](/guide/theming) | 両テーマで実際に隣り合うサーフェスのコントラスト |
| タイポグラフィ、余白、寸法、上書き | [カスタマイズ](/guide/customization) | 長いコンテンツ、表示密度、文字サイズの変更、操作領域の範囲 |
| マークアップ、パーツ、状態 | [コントラクト](/guide/contracts) | ネイティブのセマンティクスと同時に成立する状態 |
| キーボード操作、値、フォーカスのビヘイビア | [ビヘイビア](/guide/behaviors) | 一連の入力操作、終了時の後処理、フォーカスの復帰 |
| 実行時とフォールバックの要件 | [ブラウザーサポート](/guide/browser-support) | 対応ブラウザー、必須ではない機能強化、実用可能なフォールバック |
| フレームワークとの統合 | [フレームワーク](/guide/frameworks) | 値の管理主体、ライフサイクル、初期化の重複 |

リンク先は各実装の担当を示しています。考えられるすべての構成で検証済みであることを示すものではありません。現在利用できるコンポーネントと使用例は、[Master UI カタログ](/components)を参照してください。提案段階のパターンは、コントラクト、ビヘイビア、検証結果が揃うまで、サポート対象のコントロールとして掲載しないでください。

## 変更を共同でレビューする \{#review-a-change-together\}

まず、関連する設計の基礎と使用ガイドを確認します。Master UI の実装を変更してから、利用側の代表的なページで検証してください。想定するビヘイビアが変わる場合は、ドキュメントも更新します。ソース、使用例、コントラクト、テストの整合性を保ち、ブラウザーや支援技術の制約を記録してください。スクリーンショットだけを根拠に、アクセシビリティ全般への対応をうたわないでください。
