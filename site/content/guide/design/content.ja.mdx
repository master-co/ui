Master UI のデザイン言語は、サーフェス、ジオメトリー、状態を連携させることで、包含関係、階層、操作を目に見えるものにします。このガイドでは、それらの選択について説明します。一般的な原則は [Master Design](https://design.master.co/principles) で、実行可能なトークンとマテリアルのレシピは[既定のテーマ](/guide/theme)で扱っています。

## 所有範囲 \{#ownership\}

| プロジェクト | 所有するもの | 所有しないもの |
| --- | --- | --- |
| Master Design | 一般的なデザイン原則、基礎、パターン、検証方法 | 2 つ目のランタイム用スタイルシートやコンポーネント API |
| Master UI | 自身のデザイン言語とガイドライン、コンポーネントのコントラクト、テーマ、再利用可能なスタイル、ビヘイビア、実装例 | プロダクト固有のコンテンツ、ルーティング、アプリケーションデータ |
| Master CSS | スタイリングの構文、コンパイル、ランタイムでの配信、汎用的なプリセットのプリミティブ | プロダクトの操作に関する判断 |
| Master | ブランドとエコシステムのウェブサイト、共有のファーストパーティサイトシェル、公開のためのインフラ | 並行する再利用可能なコンポーネントライブラリ |

利用者は、再利用可能な表示には Master UI を、局所的な構成には Master CSS を使います。サイトシェルは、ナビゲーション、ドキュメント、サイト固有の表示を組み立てます。Design はランタイムの依存関係ではなく、ドキュメントを通じてこれらの実装に影響を与えます。

## ネイティブの振る舞いと明示的なコントラクト \{#native-behavior-and-explicit-contracts\}

ネイティブ要素と、その実際の状態属性から始めてください。Master UI のクラスはサポートされるマークアップを記述し、そのコントラクトは公開されるパーツと状態をドキュメント化します。見た目のためのクラスは、欠けているキーボード操作を補いません。パターンが必要とする場合は、付属のビヘイビアか、完全なフレームワーク統合を使ってください。

似たライブラリからモディファイアを考え出さないでください。マークアップを書く前に現在のコンポーネントのコントラクトを読み、UI チェッカーを実行し、レンダリングされた操作をテストします。静的なチェックでは、フォーカス、読み上げ、視覚的なコントラストを証明できません。

## Moonstone と Obsidian \{#moonstone-and-obsidian\}

既定のマテリアルは、ライトの見た目に **Moonstone** を、ダークの見た目に **Obsidian** を使います。両者はニュートラルなジンクの語彙と、上方やや左にある一貫した仮想の光源を共有しています。Moonstone は、面全体の控えめな変化、細い輪郭、短く消えていく影によって、淡いパールを思わせます。Obsidian は、塗りの段階、抑えたハイライト、読み取れるエッジによって暗いサーフェスを区別します。Moonstone の色を単純に反転させると、この区別が失われます。

目的は、装飾的な色がコンテンツと競合することなく、包含関係と操作を読み取れるようにすることです。ニュートラルな光と奥行きが通常のサーフェスを示し、意味を持つ色相が状態を伝え、意図的なブランドのアクセントがビューの中の重要な場面を示します。これらは Master UI の既定であり、他のプロジェクトのアイデンティティに対する要件ではありません。控えめなマテリアルが成功といえるのは、目的のフィールド、アクション、レイヤーが引き続き見つけやすい場合だけです。

浮き上がったボタン、フィールド、開いたメニューを同じページに置き、両方の見た目で確認してください。メニューは背後のコンテンツから分離して見え、フィールドはフォーカス前から識別でき、控えめなテキストは実際のサーフェス上で読める必要があります。細い輪郭は、レンダリングされたサイズと該当する表示密度で確認します。装飾的なエッジがあることは、重要なコントロールの境界がコントラスト要件を満たしている証拠にはなりません。実行可能なマテリアル、[線の役割](/guide/theme#lines)、[テキストの役割](/guide/theme#text)は[既定のテーマ](/guide/theme)が所有しています。

## マテリアルの段階から役割を選ぶ \{#choose-a-role-on-the-material-ladder\}

サーフェスはその働きで選び、見た目はテーマに解決させます。この段階は関係を表すものであり、入れ子になったコンテナーがすべて明るく、または高くならなければならないというルールではありません。

| 役割 | デザイン上の目的 | 確認できる点 |
| --- | --- | --- |
| ベースキャンバス | すべてのセクションを囲まずにページを支える | 装飾的なコンテナーを取り除いても、読む順序が明確なままである |
| トレイ | 関連するシートの背後に、それらを保持する土台を沈める | 土台がグループ化を支え、中のシートと競合しない |
| 浮き上がったシート | 境界のあるコンテンツや、操作可能な面を示す | エッジがすぐ周囲から分離して見え、オーバーレイのようには見えない |
| くぼんだウェル | 編集可能なフィールド、トラック、コレクション領域を囲まれたものとして見せる | ホバーする前に領域を見つけられ、フォーカスと不正の状態が区別できる |
| 浮いたサーフェス | メニューやポップオーバーを、重なっているコンテンツから分離する | 明るいコンテンツと暗いコンテンツのどちらの上でも境界が読み取れ、切り取られない |
| 反転インク | 主要なアクションや選択のマークに強い視覚的な重みを与える | ラベルと小さなマークがコントラストを保ち、競合する複数のインク領域が主要なタスクを見えにくくしない |

モーダルには、背景のスクリムとプラットフォームの重なり順の振る舞いも必要です。影は重なり順を決めず、背景への操作も遮断しません。同様に、浮き上がったシートが自動的にクリック可能になるわけではありません。アクションを伝えるには、セマンティクス、ラベル付け、サポートされた状態の表現を使ってください。現在のコントラクトと値については、[サーフェスの実装](/components/surface)、[サーフェスの役割](/guide/theme#surfaces)、[エレベーションの役割](/guide/theme#elevation)、[反転インク](/guide/theme#ink)を参照してください。

## 同心のジオメトリーと連続曲率の角 \{#concentric-geometry-and-continuous-corners\}

入れ子になったエッジは、1 つの関係を表すべきです。土台は内側のコントロールと両者の間隔から角を導き、内側に置かれた子は囲むサーフェスから角を導きます。これにより、曲がり角でも間隔が視覚的に均一に保たれます。内側に余白があるのに両方のエッジに同じ半径を与えると、それぞれの半径が単独では問題なく見えても、角が詰まったり膨らんだりして見えます。

Master UI は、この関係をトレイとシート、セグメントのトラックとその選択されたオプション、入力グループ内のボタン、カード内のメディアに適用しています。インセット、角の役割、コンポーネントのサイズを合わせて調整してください。合っていない組み合わせを、スクリーンショットがたまたま正しく見えるまで単独の子孫の角を丸めて直そうとしないでください。つまみやアバターのような真円は、独自のジオメトリーを保ちます。

連続曲率の角は、ブラウザーが対応していれば、直線のエッジから曲がり角への移り変わりを和らげます。テーマが角の形状と見た目の丸みを調整します。円形のフォールバックも意図したとおりに見え、同じコンテンツの境界を保つ必要があります。連続的な曲率はマテリアルの選択であり、アクセシビリティや正しさの要件ではありません。

選択されたセグメントと入力グループのボタンの周囲の間隔を、サポートされる各サイズで、両方の見た目と角のフォールバックで確認してください。インセットは視覚的に均一であるべきで、テキストとフォーカスインジケーターが切り取られてはいけません。[形状の実装](/guide/theme#shape)、[segmented control](/components/segmented)、[input group](/components/input)、[card](/components/card) を使ってください。背景にある幾何学的な考え方は、[ジオメトリー](https://design.master.co/craft/geometry)を参照してください。

## 安定したコントロール上の状態フィードバック \{#state-feedback-on-a-stable-control\}

既定のマテリアルでは、静止状態は浮き上がって見え、ホバーできるポインターでのホバーは面のエッジと持ち上がりを強め、押下はくぼんだ面へと沈みます。この変化はコントロールのレイアウト上の占有領域を変えずに入力を確認させます。色の変化だけで区別を伝えるべきではなく、タッチ操作ではホバーがアクションを見つける唯一の手段であってはいけません。

フォーカス、選択、押下、検証、利用可能性は、それぞれ別の情報として扱ってください。フォーカスは次のキーボード入力が向かう先を示し、選択されたセグメントやチェックマークは持続する値を示します。不正なフィールドがフォーカスされていることもあります。処理中のアクションには明示的な進捗フィードバックが必要で、そのアプリケーション統合は意図しない繰り返し送信を防がなければなりません。無効状態の見た目だけでは、無効状態の振る舞いは実装されません。

ポインターの押下と解放、キャンセル、キーボードでの実行、選択かつフォーカス、不正かつフォーカス、無効、処理中の各状態を確認してください。ユーザーの値とラベルは安定したままで、レイアウトは跳ねず、フォーカスがマテリアルの下に隠れてはいけません。動きを抑える設定では、持ち上がりや拡大縮小がなくても状態が読み取れる必要があります。強制カラーでは、装飾的な影が失われても、重要な境界と選択が残っている必要があります。[button のコントラクト](/components/button)、[選択コントロール](/components/segmented)、[モーションの実装](/guide/theme#motion)、[ビヘイビアの所有](/guide/behaviors)を参照してください。

## Paper が示す別のマテリアル \{#paper-demonstrates-a-different-material\}

**Paper** は、同じコンポーネントのコントラクトの中にある代替テーマです。暖かみのあるニュートラル、平らな面、罫線のエッジ、より小さな円形の角が、既定の方向性のある光に取って代わります。ホバーと押下では、共有の持ち上がり設定による上昇や沈み込みはなくなります。スイッチのつまみが位置を変えるような、意味のあるコンポーネントの動きは残ります。罫線のエッジだけでは重なりを説明しきれない場合があるため、メニューとダイアログには控えめな奥行きの手がかりが残っています。

Paper は、再利用可能なコンポーネントの本質が Moonstone 特有の仕上げではなく、その構造、振る舞い、連携した役割にあることを示しています。グラデーションとハイライトを取り除くと、線と塗りの違いが担う役割が大きくなります。すべての役割を同じ面に平坦化すると、一貫したフラットなテーマにはならず、階層が失われます。

同じボタン、フィールド、選択されたコントロール、反転シート、開いたオーバーレイを、Paper と既定のテーマで比較してください。マークアップ、アクセシブルな名前、値の所有、キーボード操作は同じままであるべきです。Paper の両方のカラースキームで、境界、フォーカス、同時に成り立つ状態が見えている必要があり、動きを抑える設定と強制カラーも引き続き適用されます。参照すべきは [Paper の実装とプレビュー](/guide/theming#paper)と[テーマのレシピ](/guide/theming#recipes)であり、このガイドの中の 2 つ目のトークン表ではありません。

## カスタマイズの境界 \{#customization-boundaries\}

マテリアル全体を変えるべきときはセマンティックな役割を、1 つのコンポーネントにサポートされたバリエーションが必要なときはドキュメント化されたコンポーネントのカスタムプロパティを、ページの配置だけが変わるときは局所的な構成を変更します。完全なテーマは、サーフェス、その前景のインク、線、奥行き、角、状態の表現を連携させます。背景だけを変えると、その上に描かれるすべての関係が成り立たなくなることがあります。

テーマはトークンと共有のマテリアルレシピを提供するものであり、個々のコンポーネントの構造を書き換えるセレクターを溜め込むべきではありません。Paper はほとんどをトークンで構成しており、面がそのコントロール自身の色相に依存するトーン付きコントロールにだけレシピの上書きを使っています。トークンはランタイムでスコープを限定できますが、レシピの定義はコンパイル時に解決され、ビルドに影響します。提案された例外を 1 つの領域にだけ適用すべき場合、この違いが重要になります。

カスタマイズするときは、公開されたパーツとネイティブのセマンティクスを保ってください。より静かなスクリーンショットを得るためにフォーカスや選択を取り除いたり、ブランドカラーを唯一のエラーの手がかりにしたり、見た目の小さいコントロールでも十分なターゲットがあると想定したりしないでください。角の形状を変えるには、それと連携するスケールも必要です。モーションを変えても、理解できる状態フィードバックは残さなければなりません。コンポーネントのドキュメント化された振る舞いを超えるラベル、データ、検証、フォーカスの流れについては、引き続きアプリケーションが責任を負います。

上書きを採用する前に、代表的なボタン、フィールド、入れ子のコントロール、オーバーレイを、実際のコンテンツ、キーボード入力、長めのラベルで試してください。両方のカラースキーム、コントラストの強調、動きを抑える設定、強制カラーを確認します。[カスタマイズ](/guide/customization)、[テーマのルール](/guide/theming#rules)、[コントラクト](/guide/contracts)、[ブラウザーサポート](/guide/browser-support)を参照してください。現在の API とサポートの限界については、それらが正式な情報源です。

## コンポーネント、レイアウト、ブロック、ページ \{#components-layouts-and-blocks\}

コンポーネントが共有のコントラクトを持つに値するのは、パーツが連携しなければならないマテリアル、状態、プラットフォームの振る舞い、ジオメトリーがある場合です。レイアウトは、マテリアルを所有せずに領域内の空間を配置します。レイアウトのプリミティブは[コンポーネント](/components#layouts)と一緒に一覧にしています。[ブロック](/blocks)は、ページの具体的な一区画のためにコンポーネントとレイアウトを組み合わせます。[ページ](/pages)は、`page` または `shell` のフレームの上に画面全体を構成し、その領域とスクロールを定義します。

サイトの文言や一度きりのヒーローの配置を、汎用的なコンポーネントに昇格させないでください。逆に、再利用可能なダイアログ、ボタン、フィールドが、サイトシェルの中で 2 つ目の実装を持つべきではありません。アダプターは、実際のサイト構成と互換性の必要に限定してください。

## ガイドラインから実装へ \{#guideline-to-implementation\}

| デザイン上の関心事 | Master UI の参照先 | 利用側で確認すること |
| --- | --- | --- |
| セマンティックな色、サーフェス、奥行き | [既定のテーマ](/guide/theme)と[テーマ設定](/guide/theming) | 両方のテーマで、実際に隣接するサーフェス上のコントラスト |
| 書体、余白、寸法、上書き | [カスタマイズ](/guide/customization) | 長いコンテンツ、密度、テキストのサイズ変更、ターゲットの範囲 |
| マークアップ、パーツ、状態 | [コントラクト](/guide/contracts) | ネイティブのセマンティクスと同時に成り立つ状態 |
| キーボード、値、フォーカスの振る舞い | [ビヘイビア](/guide/behaviors) | 一連の入力操作全体、解除、フォーカスの戻り |
| ランタイムとフォールバックの要件 | [ブラウザーサポート](/guide/browser-support) | サポートするブラウザー、任意のエンハンスメント、使えるフォールバック |
| フレームワーク統合 | [React、Svelte、Vue](/guide/frameworks) | 値の所有、ライフサイクル、重複した初期化 |

これらのリンクは実装の所有者を示すものであり、考えうるすべての組み合わせが検証済みであると主張するものではありません。現在利用できるコンポーネントとその例は、[Master UI のカタログ](/components)を参照してください。提案段階のパターンを、コントラクト、ビヘイビア、裏付けが揃う前にサポート済みのコントロールとして示してはいけません。

## 変更をまとめてレビューする \{#review-a-change-together\}

関連する基礎と使用方法のガイダンスから始めてください。Master UI で実装を変更し、代表的な利用側のページを検証します。意図した振る舞いが変わったときはドキュメントを更新します。ソース、例、コントラクト、テストの整合性を保ってください。スクリーンショットを包括的なアクセシビリティの主張にするのではなく、ブラウザーと支援技術の制約を記録します。
