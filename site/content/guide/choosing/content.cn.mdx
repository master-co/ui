根据读者需要完成什么，以及结果应当如何表现来选择组件。会阻止下一步操作的确认需要对话框；点击外部即可关闭的详细信息适合弹出层。两者都可以拥有有效的标记，因此检查器无法替你做这个决定。

阅读与任务相符的那一行，然后查看组件页面，了解它的标记、脚本要求和浏览器回退方案。每份契约都在 [`use` 和 `instead`](#in-the-contract) 中为单个组件提供同样的选择指引。

在选择之前，先确定内容是否必须保持可见、某个值是否属于表单，以及该操作是否会阻止其他工作。这些约束通常比控件的外形更重要。

## 不属于组件的情况 \{#not-a-component\}

有些任务在上面的表格中没有对应的行，因为没有组件负责它们。

| 任务 | 它是什么 | 应该写什么 |
| --- | --- | --- |
| 区域内部空间的排布方式：堆叠、平铺、阅读栏 | 一种[布局](/components#layouts) | 工具类，或在工具类无法表达时使用布局 class：[`auto-grid`](/components/auto-grid)、[`bento`](/components/bento)、[`masonry`](/components/masonry)、[`breakout`](/components/breakout)、[`sticky-stack`](/components/sticky-stack)、[`form`](/components/form) |
| 页面中具有特定用途的一段：主视觉、价格表、登录卡片 | 一个[区块](/blocks) | 复制它的标记：由组件和工具类组合而成 |
| 整个屏幕的各区域放在哪里，以及哪些部分滚动 | 一个[页面](/pages) | 复制它的标记，基于两种框架之一：[`page`](/pages/page) 或 [`shell`](/pages/app-shell) |

从这些示例开始，用工具类组合现有的 class。[简介](/guide/introduction#tiers)说明了共享的材质、状态、平台行为或几何关系在什么情况下值得拥有一个组件 class。

## 契约中的同一指引 \{#in-the-contract\}

每份契约都有一个 `use` 字段，说明何时选用该组件；还有一个 `instead` 列表，指出在其他情况下更合适的相邻组件。可以从命令行读取它们：

```bash
npx master-ui contract combobox
```

输出是完整的契约。以下字段回答了“这是不是合适的组件”：

```json
{
  "name": "combobox",
  "use": "One value from a list too long to scan, found by typing.",
  "instead": [
    { "when": "The list is short enough to read without typing", "use": "select" },
    { "when": "The list runs commands instead of filling a field", "use": "command" }
  ]
}
```

`contract` 也接受 class 名称，因此 `npx master-ui contract dialog-drawer` 会输出 dialog 的契约。`npx master-ui list` 会输出每份契约及其描述，每份一行。

本页的表格从任务出发，引向某个组件。`instead` 则从某个组件出发，引向别处。已经选定组件的智能体会读取它的契约，无需阅读本页就能完成第二道检查。

确定某个组件合适之后，复制它的示例，并在把它接入页面之前检查它的 `script` 和 `platform` 字段。运行[标记检查器](/guide/contracts#diagnostics)，然后用键盘和指针实际完成预期的任务；检查通过只能确认标记符合约束，不能确认该组件适合这项任务。
